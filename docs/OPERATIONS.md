# Operations

How Nexus Prime is configured, secured and deployed. For the product and architecture overview, see the [README](../README.md). When something breaks, see the [runbook](RUNBOOK.md).

## Local development

Requires Python 3.12, [`uv`](https://docs.astral.sh/uv/), Node 22 and Docker.

```bash
docker compose up -d db          # Postgres 16 on localhost:5432
cp .env.example .env
uv sync
uv run alembic upgrade head      # the app refuses to start on an unmigrated database
uv run uvicorn --factory nexus.main:create_app --reload
curl localhost:8000/healthz
```

### Checks

```bash
uv run ruff check . && uv run ruff format --check .
uv run mypy
TEST_DATABASE_URL=postgresql://nexus:nexus@localhost:5432/postgres uv run pytest
cd web && npm ci && npm run typecheck && npm test && npm run build && npm run e2e
```

Integration tests create and drop a throwaway database per test on the `TEST_DATABASE_URL` server, and are skipped when it is unset.

## Schema changes

Only through Alembic: `uv run alembic revision -m "..."`, then `uv run alembic upgrade head`. A test checks that the migrations produce exactly the schema in `nexus/infra/db/tables.py`.

## Telegram

The channel is on when `TELEGRAM_BOT_TOKEN` is set, which then also requires `TELEGRAM_WEBHOOK_SECRET` and `ADMIN_TELEGRAM_CHAT_ID` (the owner). Only the owner and `TELEGRAM_ALLOWED_USER_IDS` are served, in private chats. Updates arrive at `POST /telegram/webhook`, checked against the secret token and de-duplicated by `update_id`. The Undo button under a reply comes off after 5 minutes (a `telegram.undo_expire` job; any other buttons on the message stay), so an old message doesn't offer to undo whatever change is now the latest; typing "undo" still works. Undo reverses the newest change of either kind, a ledger write or an itinerary change made from chat (`trip_changes`, migration 0054); everything one chat message changed on a trip is undone together, and repeated Undo walks back through both by time.

The app never registers its own webhook, so deploying it can't take a bot away from another service. `python -m nexus.channels.telegram.register` shows the current webhook and, with `--yes`, points the bot here. See [`CUTOVER.md`](CUTOVER.md) for moving from the old bot, including the one-time history import (`python -m nexus.legacy`).

The model comes from `LLM_PROVIDER` (`openrouter`, `gemini`, `deepseek` or `openai`) with the matching key. With `openrouter`, everything goes through OpenRouter and Gemini is never used, even if a Gemini key is set: `OPENROUTER_MODEL` chats and reads emails, `OPENROUTER_FALLBACK_MODELS` (comma separated) are tried in order if it fails, and `OPENROUTER_VISION_MODEL` reads receipt photos (unset: `OPENROUTER_MODEL`, which must then accept images). `OPENROUTER_PROVIDERS` (comma separated provider slugs) keeps `OPENROUTER_MODEL` to those hosts, in that order, and only ones that support every parameter sent; unset, OpenRouter picks, cheapest first. On 4 October 2026 its cheapest pick for DeepSeek v4.1 Flash, a 4-bit (fp4) host, dropped tool arguments: edits arrived with only the transaction id and logging went wrong, 8 evaluation cases failing that pass on other hosts. Recommended: `OPENROUTER_PROVIDERS=deepinfra,fireworks,atlas-cloud,streamlake` (175/177 on the evaluation set). Other models (receipts, memory, research) aren't pinned, since those hosts may not serve them. To check a host, run the evaluation set with `--providers <slug>`. `CHAT_REASONING` sets how much `OPENROUTER_MODEL` reasons before it answers in chat: `low` (the default), `on`, `off`, or `default` to send nothing and keep the model's own (on, for DeepSeek). On 14 October 2026, low was as accurate as on and a quarter faster, with no reply over 30 seconds; off was faster still but often said it had done things without calling the tool (see EVALS.md). While a reply is worked out, Telegram shows "typing…" (sent again every 4 seconds until the reply goes, for messages and button presses from allow-listed users) and the web chat shows a typing bubble that adds "Still working on it…" after 10 seconds. With the other providers, the optional fallback is a Gemini `LLM_FALLBACK_MODEL` and receipt photos are read by Gemini. The "are you working?" reply names the model in use. Each turn the model also gets a snapshot of the user's money (this month's totals and top categories, budgets, the next 7 days' bills, subscriptions and payday, who owes them, and the last 5 transactions), built once per turn and capped at 2,000 characters; and once a conversation passes 40 messages, all but about the last 20 are condensed into a rolling summary (by the main model, at most 150 words) and dropped, so long chats keep their thread without growing the prompt. Because a chat can run across days, each user message is stamped with its send time (`nexus_sent_at`, UTC, from the service clock) and the model is shown history with the user's local days made plain: a message from an earlier local day is prefixed `[Sat 24 Oct, 22:51] ` in the copy sent to the model (the stored messages are never changed), and the first message of a new day is headed `[It's now Sun 25 Oct; the messages above are from Sat 24 Oct or earlier.]`; messages from before the stamp existed are shown as they were. The summariser is told when its messages were sent and must write absolute dates ("Kamakura on Sun 25 Oct"), never today, tomorrow or tonight; the summary's write time is kept (`summary_at`) and shown to the model as "(a summary, written Sun 25 Oct, 11:28; …)", and the rules tell the model to work out today and tomorrow from the "Now:" line. The summary is made in the background after the reply has gone out (`AgentService` schedules `AgentGraph.condense` under the user's lock), so no one waits on it; until it lands the model still sees only the last 40 messages, a thread waiting on a confirmation is left alone, and a failed summary is logged and retried after the next turn. Questions about the ledger ("grab on weekends", "top merchants", "compare with last month") go through a read-only `query_ledger` tool: fixed filters, groupings and measures (no SQL from the model), the acting user's confirmed transactions only, in the home currency, at most 5,000 transactions a period. Each turn the model is offered the core tools (`CORE_TOOLS` in `agent/graph.py`: logging, finding and changing transactions, income, summaries, `query_ledger`, categories, voice, the read-only `find_likely_moves` and `load_skill`); loading a skill adds its tools for the next five messages. A tool the model calls without its skill loaded still runs. The kernel refuses a payment only when Nexus is asked to make one ("can you pay…", "pay … now"); "pay X on a date" reaches the model as a bill to remember. Long-term memory: after each text message the service queues a `memory.update` job with the user's last three messages (their own words only, never tool results, emails or receipts). A small model (`MEMORY_MODEL` on OpenRouter; unset, the main model) adds, updates or deletes memories, of three kinds: facts, preferences and dated episodes, at most 300 per user with the oldest episodes dropped first. The job's payload is emptied when it finishes, so the jobs table keeps no copy of what was said. Each turn the model is given the user's facts and preferences, plus the episodes that match the message and the latest few, and follows preferences quietly; nothing remembered can override its rules. Reply style (length, emoji, tone, humour) lives in the voice settings (`set_voice`), not in memory: the memory writer doesn't store it, and the agent ignores an older remembered style that disagrees with the voice. Users see and delete memories under Settings → What Nexus remembers. Emails from the last two weeks still waiting for an answer (newest five) open the money snapshot, numbered, and the core `answer_email` tool logs one (as an expense, a repayment or income) or skips it after the usual confirmation, so "that transfer just now was Wei Ming paying me back" works straight after an email question. Repayments by name ("Wei Ming paid me back") match names the same loose way. On the web, each line under Who owes you has **Paid back**, which records the amount still owed as money in from that person today; deleting that transaction reopens the IOU. Memory needs the job runner (on in production; `JOBS_ENABLED` elsewhere); without it nothing is remembered. With Telegram on and no usable model configured, the app refuses to start. Totals count the user's own money. What a friend paid back comes off the bill it repaid (in that bill's month, category and budget), and money in that only repaid a bill isn't income; anything paid beyond what was owed still is. A share nobody has paid back yet still counts as the user's spending, so totals never assume money that hasn't come back. Deleting either side undoes it. Cash flow is the exception: it shows money as it actually moved, the full bill out and the repayment in, to match the bank. The ledger keeps the trail both ways: a split bill shows the user's share and, for each person, "paid back ✓" (linking to the repayment) or what they still owe, and a repayment shows "↩ Paid back for" the bill, linking back. The same lines appear in the transaction's edit sheet.

Amounts the app writes itself (confirm cards, tool results, Telegram and web messages) come from `str(Money)` and have thousands separators and the currency's minor units: "1,240.00 SGD", "125,000 JPY", "-1,240.50 SGD"; the reply style asks the model for the same ("1,800", "1,850.00"). Anything a program reads back must not use that text: exports, ids and keys, button data, stored JSON and the API's money fields use `Money.amount` (the API sends `{"amount": "1240.0000", "currency": "SGD"}`). Amounts typed or echoed by the model in tool arguments may carry commas ("1,240.50"); `parse_money` removes them.

Statement import (web: Settings → Import a statement, or Ledger → More → Import statement; `/settings/import`) reads a bank or card CSV up to 2 MB and 5,000 rows. It finds the header row below any account details, suggests which column is the date, description and amount (one signed column or separate out and in columns), and remembers a layout the user saves by the file's header row. The preview saves nothing and marks each row new, a possible duplicate (same amount and direction within a day of a logged transaction), already imported, or unreadable; only the ticked rows are added, in one transaction, with `source=import`. Each row's fingerprint is claimed as its source id, so the same file never adds a row twice, even after an undo. Money in is filed as income, never salary. An import can be undone as a whole from the same page. PDF statements (up to 10 MB, 60 pages) are read with pypdf, keeping each row's text on one line; a locked PDF asks for its password, which is used for that request only. A transaction line starts with one or two dates and ends with an amount: on a card statement a plain amount is spending and "CR" a credit; on an account statement the running balance says which way each amount moved. Dates without a year take the statement date's (a December charge on a January statement is last year's), foreign-currency lines are added to the description, and reference, balance and total lines are left out. The rows are checked against the statement's own previous and closing balances, and the preview says whether they add up. The rows then go through the same preview and import as a CSV; the PDF itself is never stored. A scanned statement (under 60 characters of text a page, up to 10 pages) is rendered page by page with pdfium to greyscale JPEGs, and the photo model, without reasoning, copies each page's text line by line, four pages at a time with a minute each. The page is treated as data, never instructions. The same reader then parses the copy, a page break keeps one page's header off the last row of the page before, and the totals check catches a misread amount; the preview tells the user it was read from a scan and to check each row. Neither the images nor the copy are stored or logged. Without a photo model a scan is refused, pointing to the bank's CSV export.

**The chat window remembers.** The web chat opens on the running conversation: the user's messages and Nexus's replies from the web and Telegram alike, newest last, with **Earlier messages** for more (`GET /api/chat/history`, 40 lines a page, `before=<id>` for older). It's the same single conversation as Telegram, not separate chats. The lines are kept in `chat_log` (migration 0032) as the user saw them: text messages, voice notes (the words, with a leading 🎙), photos and PDFs (as "[Sent a photo] caption", never the image or what was read from it), and Confirm, Cancel and Undo. Notifications (alerts, reminders, digests, email and bill prompts) and the buttons on them are not part of it. A confirmation still waiting comes back with its buttons. The newest 500 lines per user are kept; older ones are deleted as new ones arrive. Keeping a line never stops a reply: a failure is logged and the chat carries on.

## Voice notes

A voice note on Telegram (or the mic in the web chat, `POST /api/chat/voice`) is turned into text and then handled exactly like a typed message: the same kernel, tools, Undo and voice settings. It is on when `OPENROUTER_API_KEY` is set; without it the reply is "Voice notes aren't set up — mind typing it?" (web: 503). Speech goes to OpenRouter's `/audio/transcriptions` with `STT_MODEL` (default `openai/gpt-4o-mini-transcribe`, with a short neutral prompt that makes it write money as `$12.50`, 96% of amounts exact in the 26 October 2026 bake-off against 76% without) and, if that fails or times out (15 seconds each), `STT_FALLBACK_MODEL` (default `openai/whisper-large-v3-turbo`, no prompt; blank = no fallback). Roughly $0.0001 for a 3-second note. Nothing is converted: ogg (Telegram), webm (Chrome, Android), m4a/mp4 (iPhone) and mp3 go as they are.

The transcript is tidied in code before the agent reads it (`domain/transcript.py`): "8:40" or "840" after a lunch, "2350" after a taxi, "1799 for Netflix" and "12. 50" become decimals only in a clear spending sentence (real times, round amounts, years and anything after "at", "by" or "from" are left alone); a bare `$` means the home currency; "Thanks for watching." and similar invented closing sentences are dropped. When a voice turn changes data (the turn that adds the Undo button), the first reply opens with `🎙 heard: "<what it understood>"` (cut to about 120 characters), so a mishearing is seen at once. A write that waits on Confirm shows no such line; its summary already says what will change. A voice note that is forwarded on Telegram is quoted material like text read from a photo: nothing is changed from it unless the user then asks. The web history shows the user's line with a leading 🎙.

**Names: "Ann" is not "Anne".** Speech and typing both misspell people, and a misspelling used to become a second person (what Ann owes split across two names). Two things stop that. First, the first speech model's prompt ends with "Names that may come up: Ann, Sam." (`known_people` in `application/people.py`: the user's split participants, split-habit people, trip companions and people who paid for a trip, newest first, at most 30 known and 20 sent; each name cut down to letters, spaces, hyphens and apostrophes of at most 40 characters). The fallback model never gets the names, since prompting Whisper through some providers returns nothing. Second, `split_bill`, `set_split_habit`, `create_trip` and `update_trip` (companions) refuse a name that is not already known but is one small edit from one that is (`near_name` in `domain/ledger.py`: every word within one letter for words under 5 letters, two for longer ones, same first letter, so Ann/Anne, Sara/Sarah, Jon/John and Steven/Stephen match but Pam/Sam and Ann/Ian do not; nothing when two known names are near). The tool answers "Anne would be a new person; the user already knows Ann. Ask the user whether they mean Ann, …", on the confirmation step as well as the run, so the model asks, and calls the tool again with `new_person=true` if the user says Anne is someone new. `they_paid` only accepts people already on the trip, so it needs no check.

Limits: 2 minutes and 5 MB (refused before downloading on Telegram, 413 on the web), 30 voice notes an hour per user (in memory, like the message limit; 429 on the web). Audio is held in memory only for the call: it is never stored or logged, and no log line holds a transcript. A log line carries the model, the audio's seconds and the cost. The chat log keeps the words, not the recording.

## Web access

The web API (`/api/...`) is on when Telegram is configured and the public origin is known (`WEB_ORIGIN`, or Railway's `RAILWAY_PUBLIC_DOMAIN`).

- **Sign-in** uses the Telegram Login Widget. The signature is checked with the bot token and must be less than a day old. The bot's domain must be set with @BotFather `/setdomain`.
- **Inside Telegram (Mini App):** the bot's menu button ("Open Nexus", set at startup) and the `/app` command open the web app inside Telegram. It signs in with the launch data Telegram signs for the Mini App (checked with the bot token, less than a day old), so there is no widget or phone number step. The same access rules apply. These sessions use a `SameSite=None; Partitioned` cookie because Telegram's web clients show the app in an iframe, and the CSP allows only `https://web.telegram.org` to embed it.
- **Who can sign in:** the owner (`ADMIN_TELEGRAM_CHAT_ID`) always can. Anyone else needs a single-use invite, valid for 24 hours, from the owner (`/invite` in the bot, or `POST /api/invites`). Tokens are stored only as hashes.
- **Sessions** are HttpOnly, Secure, SameSite=Lax cookies (Mini App: see above) lasting 30 days, and can be revoked by logging out.
- **Writes** must come from the app's own origin and carry the session's `X-CSRF-Token`.
- **Every route** takes the user from the session. Another user's data returns 404.

## Shared trips

A trip's owner can let other people edit its plan (`/api/travel/trips/{id}/members`, `/invites` and `/activity`, `PUT /api/travel/trips/{id}/notes` and `POST /api/travel/invites/{token}/accept`; the screens are People in the share sheet, Shared with you on Trips and the activity line on the trip).

- **Inviting:** the trip's owner makes a link (`POST /api/travel/trips/{id}/invites`) that looks like `/trip-invite/<token>`. It adds one person, works once, and expires after 7 days. The link is shown only when it is made (only its hash is kept); the owner can list the links still open (without the links) and cancel one that hasn't been used. At most 10 are open at once, and a trip takes up to 10 members. Making links and trying one are rate limited (20 an hour, 20 in 10 minutes).
- **Joining:** whoever opens the link signs in with Telegram and is on the trip. Signing in with the link (`trip_invite` on the login request) reports the trip as `joined_trip` in `/api/me`; someone already signed in accepts it with `POST /api/travel/invites/{token}/accept`. A link that is unknown, used, cancelled or expired is a 404. The owner opening their own link joins nothing and gets `200 {"trip_id", "new": false, "own": true}`, so the page can open their trip; the link is not spent. The Telegram Mini App signs in the same way: `POST /api/auth/webapp` takes an optional `trip_invite` beside `init_data` and treats it exactly like the widget's (an existing account joins; someone with no account becomes a guest only if the app's owner made the link), and the web app sends it when it is opened at `/trip-invite/<token>` inside Telegram. `GET /api/me` and the sign-in answers carry `user.display_name` (the Telegram first name and last initial, or null), which the guest header shows beside Sign out.
- **What a member can do:** change the plan. That is days and their names, bookings and plans on the itinerary, ideas and moving them to a day, stops, how the trip gets about, packing, to-dos, cover and documents (never what a cover cost), notes (through `PUT .../notes`, which changes nothing else) and the prep tab. They can also read the places, hops, weather and activity.
- **What a member can't do:** see or change any money (budget, set-aside, spending, who owes what, what an entry cost, splitting and settling up), edit the travellers, dates or destination, share the trip's read-only link, make invites, or delete the trip. Their trip page has no money in it at all, not hidden but never worked out; a cost on an entry is refused with a 403 and a member's edit keeps the cost it had. The trip is the owner's, so an edit is the owner's trip being edited. A person with no part in a trip is told there is no such trip.
- **Guests:** an invite the app's owner made (not one from a member of the app) can also bring in someone with no account, who gets a guest account. A guest can only open the trips they are on, and sign out: no chat, no Telegram bot, and every other route refuses them. A guest stays a guest, and an existing account is never made one. A link made by anyone else only adds people who already have an account.
- **Chat on a shared trip:** a member with a full account can use the chat on someone else's trip, under the web's rules. Every trip tool finds a trip by name among the user's own trips and the ones they were added to (`application/trip_access.find_trip`, which asks `open_trip` for the access; with no name, the one that's on or next of all of them). If a name matches several trips and one of them is someone else's, the tool returns the candidates ("2 trips match 'japan': Tokyo, Japan (10 Dec 2026 to 18 Dec 2026, Alex's); Kyoto, Japan (…, yours). Ask which one.") and the agent asks; several of their own are picked as ever (the one on or next). `list_trips` also lists shared trips, marked with whose they are. On a shared trip the plan tools run as the owner and note the change in the trip's activity (so the owner's summary fires, as for a web edit): `add_to_itinerary`, `change_itinerary_entry` (including moving a plan), `remove_from_itinerary`, `label_trip_day`, `add_trip_todo`, `add_trip_cover` (a cost is dropped, as for an entry), notes (`update_trip` with only `notes`), `find_places`, `find_ideas` and `place_info`, and `trip_status`, which gives the member's plan view (days, bookings, places to visit, stops, what the trip still needs) with no money and no ledger query. A cost a member gives on an entry is dropped, never stored, and the reply says so ("I left the price out: only Alex can add costs on a shared trip."); a change to an entry keeps the cost it had. Everything with money or the trip's details refuses before reading or changing anything, with "Only <owner> can change money or the trip's details on a shared trip.": `update_trip` with anything but the notes (budget, set-aside, travellers, dates, destination, currency), `delete_trip`, `add_to_trip`, `remove_from_trip`, `split_trip_costs`, `they_paid`, `settle_up` (even to look) and `research_to_trip`. Neither ledger is touched. Making invites and the read-only link have no chat tool. A trip screenshot sent in chat with a caption that names exactly one trip the user was added to (and none of their own) is read onto that trip as the owner's, with prices left out (`with_costs=False`) and noted in the activity; any other screenshot goes where it always did (their own trips, by dates). The web's Type it in the add sheet and Ask Nexus about this trip are therefore shown to members (never to guests, who have no chat).
- **Removing and leaving:** the owner removes a member (`DELETE .../members/{id}`), and a member removes themselves to leave; access ends at once.
- **Activity:** a trip with at least one member keeps a log of what changed in the plan ("added Dinner at Sushi Ten", "changed the notes"), the latest 20 newest first, and anyone on the trip can read it. It never holds money. People see each other as their Telegram first name and last initial ("Alex T.").
- **Telegram summary for the owner:** when a member (never the owner) changes a trip, its owner gets one Telegram message, at most one per trip every 30 minutes: "Alex and Sam changed Tokyo: added Dinner at Sushi Ten, moved Senso-ji to Day 2". It lists the first 5 changes (the same change twice counts once) and then "and 3 more", names the people ("Someone" for a person with no name) and has an **Open the trip** button. It never holds money. The first member edit queues a `trip.activity_digest` job for 30 minutes later (dedupe key `trip.activity_digest:<trip>:<last summary or "first">`, so every edit meanwhile shares it); the job reports everything by others since the previous summary (`trips.activity_digest_at`, migration 0047), queues the message as a `telegram.send` of kind `trip_activity` (level `now`, so quiet hours and the daily cap apply; with its Open the trip button it is sent on its own, not folded into a digest), and queues the next job if edits arrived after it started. It is one transaction with the trip row locked, so a retry sends nothing twice. Nothing is sent when the owner's setting is off or they have no Telegram chat, and those changes then count as told, so turning it on never replays them. A trip deleted meanwhile is a no-op; a member removed meanwhile is still reported. The setting is `users.trip_activity_alerts` (on by default), `GET`/`PUT /api/trip-alerts` with `{"enabled": bool}`, and the switch "Tell me when someone changes a trip I share" under Travel on Settings.

## The Prep tab: to-dos, cover and documents

Migration 0048: `trips.todos` and `trips.prep_dismissed` (JSONB, like `packing`) and the `trip_covers` table. The rules are in `domain/prep.py`, the use cases in `application/prep.py`, the routes in `channels/web/travel_api.py` and the chat tools in `agent/tools.py` (`add_trip_todo`, `add_trip_cover`, the trips skill). Every route goes through `open_trip` and runs as the trip's owner, like packing: the owner, a member and a guest read and edit to-dos and cover, and what they change is noted in the trip's activity ("changed the to-do list", "added Harbour Cover to cover and documents"). Someone with no part in the trip gets the same 404 as for a trip that isn't there.

- **On the page:** the Prep tab opens with **Getting ready**, one list of what's still to sort (with its button), the suggestions (**Add** and **Not needed**) and the to-dos (a checkbox each; the done ones sink to the bottom, struck through; a date gone by and not done reads "Overdue · Tue 8 Dec"), with a field, "By (optional)" and **Add** under it. **Cover and documents** follows, then the packing list, the weather and the notes. A cover row shows its name, one line ("Insurance · TX-4471 · 2–9 Dec"), **Call** and **Copy**, and for the owner its cost with **Log it** (it asks first, then reads **Logged**). **Add cover or a document** (and the + button, which asks "Add to prep": A to-do, Cover or a document, Something to pack) opens the cover's form. On Money, **Bookings paid** lists covers that cost something, after the bookings.
- **To-dos** (`PUT /api/travel/trips/{id}/todos`, `{"todos": [{"id"?, "text", "due"?, "done"}]}`): the whole list replaces the old one, as packing does. Each is at most 80 characters, there are at most 50, a repeat (same words, any case) is dropped, and card and passport numbers are hidden. A to-do keeps its short `id` across saves (a new or repeated one is given a new id), which is what keeps a reminder from going out twice. In the bookings reminder job a to-do with a due date that isn't done gets one message, "Tomorrow: {text} for {destination}", from 08:00 local time the day before; the dedupe key is the trip, the to-do's id and the due date, so moving the date earns a new reminder. Done to-dos and those of a finished trip stay quiet. A cover gets no reminder.
- **Suggestions** (`prep_suggestions` on the trip page, worked out in code with no model): for a trip abroad (spent in another currency than the owner's home one, as for packing) travel insurance (until there is an insurance cover), entry rules for the country (until there is a visa cover or a to-do mentioning "visa" or "entry rule"), passport validity (until a to-do mentions "passport") and, for a trip of a night or more, the bank and a travel card (until a to-do mentions money, cash or card). `POST /api/travel/trips/{id}/prep/dismiss` `{"key"}` is "Not needed" (insurance, visa, passport or money; anything else is a 422) and `DELETE .../prep/dismiss/{key}` brings it back. Both, and the to-do save, answer `{todos, covers, prep_suggestions}`. A suggestion's `action` says what its button does: `add_cover` opens the cover form, `add_todo` adds its text as a to-do.
- **Cover and documents** (`POST /api/travel/trips/{id}/covers`, `PUT` and `DELETE .../covers/{cover}`): a kind (insurance, visa, document or other), a name (80), a reference (60; the user's own policy or visa number, kept as booking references are), a phone (30; digits, +, spaces, - and brackets), the dates it covers, a cost and a note (200); at most 30 a trip. A reference, phone or note holding a card or passport number is refused (the name and note are masked as the notes are), and so is a reference on a cover called "passport". An edit sends the whole cover.
- **Money:** a cover's cost is the owner's. A member never sees it or whether it was logged (`cost` null, `logged` false), can't give one (403) and keeps the cost a cover had when they edit it. An unlogged cover's cost counts in the trip's `booked` and `booked_unlogged` exactly as a booking's does (home currency at the rate for the day it was added; no rate means it is left out, as for a booking), so it reduces `to_spend`; the Money tab lists it under Bookings paid from `covers`. `POST .../covers/{cover}/log` (owner only) records the cost as an expense through the same ledger code as settling up (category Travel, the cover's name as the counterparty, linked to the trip) and sets `logged_transaction_id`. It is a 409 when it is logged already (unless that expense was deleted since), and a 422 for a cover with no cost. Deleting a cover leaves its expense. Nexus only records: it never pays for cover or makes a claim.
- **The read-only link** never includes to-dos, cover, suggestions or any reference (`SharedTripOut` has no such fields).

## Exchange rates

Foreign amounts convert to the user's home currency at the [Frankfurter](https://frankfurter.dev) (European Central Bank) reference rate published on or before the transaction's local date, never a later one. With no rate, the conversion is reported as unavailable rather than guessed. A past day's rate is fetched once and kept in the database (`fx_rates`, migration 0035, shared by all users since it's public reference data), so it isn't looked up again, even after a restart; today's rate isn't kept, because the day's rate may not be published yet. If the database can't be read, rates come straight from Frankfurter.

A lookup waits at most 2 seconds in all (`LOOKUP_SECONDS` in `infra/fx/frankfurter.py`; chat turns and background jobs share it, since both fall back on a kept rate). A lookup that fails (timeout, network error, an HTTP status other than 200 or 404, or an unreadable answer) is remembered in memory for 10 minutes per currency pair and day, so the next turns don't wait on it again; a 404 (pair or day not covered) is still remembered for good for past days. Today's rate, once found, is also kept in memory for 10 minutes rather than fetched every turn. When Frankfurter has no answer, the newest rate kept in `fx_rates` for that pair whose effective date is on or before the day asked for answers instead, never a later one, and it carries its own effective date, so the app and chat show which day's rate was used. That fallback is not kept as the asked day's rate, so the real one is fetched once Frankfurter is back. With nothing kept, the conversion is reported as unavailable as before. Rates one summary needs are fetched together (at most 4 at a time), once per currency and day.

The `turn took` log line splits a turn's time: `turn took 34.4s (context 20.1s, model 12.0s, tools 2.3s): 1 model calls, tools: none`. Context is building the money snapshot and memories before the model runs; the rest is the database, prompt building and waits between steps.

**Model hiccups in a turn (`agent_node`, `tools_node` in `agent/graph.py`).** A turn takes at most `MAX_STEPS` (8) model steps; past that the user gets "I stopped partway. Already done: …" if a tool wrote something, else "that's taking too many steps". A model reply with no text and no tool calls is a hiccup, not the user being unclear: the model is called once more in the same step, with "Your last reply was empty. Reply to the user, or call a tool." added as a last system message. The retry is not a step (it doesn't count against `MAX_STEPS`) but is a model call in the `turn took` line. Each empty reply logs a warning (`model returned an empty reply`), and another says when the retry worked. If the retry is empty too, a turn that already wrote answers "Done: …" (what was written, with Undo); otherwise "Sorry, I didn't get that." A call to a tool that doesn't exist (often `log_expense_placeholder`) gets "Error: there is no tool called 'x'. Did you mean …?" with up to 3 of the tools offered this turn, matched after dropping a `_placeholder`-style suffix; nothing is suggested when none is close.

## Background jobs

Budget alerts, bill reminders and the payday check-in run on a Postgres-backed job queue inside the app process: `JOBS_ENABLED`, which defaults to on only when `ENVIRONMENT=prod`.

- **Exactly once:** each job is claimed with `FOR UPDATE SKIP LOCKED` under a 20-minute lease, and recurring work is queued once per time slot under a unique dedupe key. Overlapping instances during a deploy don't double-send, and no leader election is needed.
- **Throughput:** up to 5 jobs run at once, one user's jobs always in order, and a full batch is followed straight away by the next. Each job has 90 seconds; one that runs longer is abandoned and retried like a failure. Measured numbers are in [`RUNBOOK.md`](RUNBOOK.md).
- **Retries:** failures back off (2, 4, 8… minutes, capped at an hour) and stop after 5 attempts.
- **Quiet hours:** Telegram messages wait out the user's quiet hours in their timezone, 23:00–08:00 unless they change it (`notification_settings.quiet_start` and `quiet_end`, migration 0050; Settings, `PUT /api/notifications`, or "don't message me after 10pm" in chat). A window may cross midnight or sit within a day (01:00–06:00); the same time twice means no quiet hours. What is not held: a message queued with `anytime` (a summary the user timed, the morning summary) or at the `urgent` level (a stop on a stock they hold), which are sent at once. Everything else follows the notification policy below. The sender reads the user's hours when the job runs. `quiet_until(local, start, end)` in `domain/planning.py` is the pure rule.
- **Notification policy and record (migration 0053).** Every Telegram message is a `telegram.send` job whose payload has a `level` (`urgent`, `now` or `digest`), a `kind` (a short stable name, the table below) and optionally a `link` (a web path that opens what it is about, shown in the record). `decide(level, now_local, quiet_start, quiet_end, sent_today, cap, has_buttons)` in `domain/notifications.py` is the pure rule, and `application/messaging.py` applies it when the job runs. *Urgent*: sent at once, quiet hours or not, and not counted toward the cap. *Now*: in quiet hours it is held until they end; otherwise it is sent, unless `sent_today` has reached the cap, when it goes in a digest, except that one with buttons is sent anyway (its buttons must work) and still counts. *Digest*: never sent alone; held for the next digest. `anytime` stays a separate flag for a message the user timed (the daily summary, the morning market summary): sent at once, never capped, not held. The older flags still work for jobs queued before levels: `urgent` is the urgent level, a payload with neither is `now` with kind `message`. *The cap*: `notification_settings.daily_cap`, 6 by default, 3 to 20 (`GET`/`PUT /api/notifications` as `daily_cap`; a number outside the range, or a fraction, is a 422 and changes nothing; Telegram updates on Settings has the field). `sent_today` counts the user's messages with status `sent` and sent in their local day (midnight to midnight in their timezone, so a day when the clocks change is 23 or 25 hours), not urgent and not of the kinds that are never capped: `daily_summary`, `market_summary`, `transaction_update` and `timezone` (the hourly, three-a-day and as-it-happens summaries the user chose). *The digest*: a `notify.digest` sweep every 10 minutes looks for each user's held messages without buttons whose `held_until` has passed, and, if the user isn't in quiet hours, folds them into one message, "While you were away:" and a bullet per item (oldest first, each on one line of at most 200 characters, 12 lines, then "and N more — see Notifications on the web"), queued as a `telegram.send` with `anytime` and the key `digest:<user>:<first item's id>`. The items are marked `digested` (with a shared `digest_id` and `sent_at`) in the same transaction that queues it, so a digest is never made twice and the digest message itself is not recorded again. Digests go when quiet hours end each day (08:00 unless changed) and at 19:00 local for what was held outside quiet hours, unless 19:00 falls in them; with no quiet hours, 19:00 only. `next_digest_at` is the rule, and a held message's `held_until` is its next digest time (for one held in quiet hours, when they end). A held message *with* buttons (a bill reminder, a receipt question, a "Track it?" prompt) is not folded in: it is queued again as its own `telegram.send` for its `held_until` (key `notification:<id>`) and sent then, if the cap or quiet hours allow it again, as it would have been before. A user with no Telegram chat (or who unlinked it) gets the record with status `dropped` and nothing is sent. *The record*: `notifications` (user, kind, level, text, link, has_buttons, created_at, status `sent`/`held`/`digested`/`dropped`, sent_at, held_until, digest_id; indexed on user and time) keeps each message for 30 days, scanned and pruned by a daily `notify.prune` job. `GET /api/notifications/history` gives the signed-in user's own, newest first (up to 500) as `{id, kind, level, text, link, status, created_at, sent_at, held_until}`; guests get 403 like any route outside shared trips. The web app shows it as the Notifications page (`/settings/notifications`, from the bell on Home or the Notifications card in Settings): the last 30 days a day at a time, each message with its time and a status chip. (The settings route `GET`/`PUT /api/notifications` already existed, so the list is under `/history`.) Replies in the chat, department progress messages and anything that isn't a `telegram.send` job are not part of the policy or the record.
- **Subscriptions:** every 6 hours a sweep looks at each user's expenses from the last 800 days. When a merchant's latest three charges (reference numbers ignored, one per day, same currency) came weekly, monthly or yearly, each within 20% of the latest, and the next is still due, the user is asked once: **Track it / No**. At most 3 new questions per sweep. A tracked subscription follows new charges; a change of more than 1% is a price change, told once. A "No" or "Stop tracking" keeps the row as dismissed so it's never proposed again. Nothing is ever cancelled.
- **Cash flow** (`GET /api/cashflow?month=YYYY-MM`, the Cash flow page, the `cash_flow` chat tool): per day, logged in/out/net in the home currency up to today (foreign amounts at each day's rate; ones with no rate listed separately), and from today the expected bills (not yet marked paid), tracked subscriptions and payday (with the usual salary, if set), converted at today's rate. Up to 62 days per request. Items without an amount are listed but not counted. Movement only, never a balance.
- **Telegram updates:** every 5 minutes a sweep checks whether each user is due a message. The default is a summary at 21:00 local time; users can move it to any time they like ("send my summary at 11:59pm", or the time picker on Settings), and because they chose it, it goes even within quiet hours. A summary sent just after midnight is headed with the day it covers. Users can choose hourly (08:00–21:00), 3 times a day (09:00, 14:00, 20:00), as it happens, or off. A summary covers what was logged since the last one, in the home currency, plus receipts from email still waiting. Nothing is sent when nothing happened. Updates as they happen only cover what the chat didn't already confirm, such as web entries and payday logging. With them on, each new receipt from email is asked about right away; otherwise receipts wait for the next summary. The first check for a user only starts counting, so turning updates on never replays history. Settings live in `notification_settings`; no row means the default.
- **Budgets:** monthly limits in the home currency, overall or per category, with no rollover. Every 10 minutes a sweep records each 50/80/100% threshold reached once per budget per month (`budget_alerts`), and messages the highest new one.
- **Scheduled payments** (the Budgets page section, formerly Bills): a name the user chooses, whether it counts as spending (`bills.spending`, migration 0039; on by default), an optional amount, a next due date, and a repeat of once, weekly, monthly or yearly. Monthly bills on the 29th–31st land on the last day of shorter months and come back afterwards. Every 30 minutes a sweep sends the most urgent reminder reached (7, 3 or 1 days before), once each. Reminders carry **Mark paid** and **Snooze 1 day** buttons. Snoozing re-sends the reminder a day later. An unpaid bill shows as overdue for a week, then rolls on to its next due date. Marking a bill paid (the button, the Bills card, or `mark_bill_paid` in chat) records it and logs the bill as an expense today, under Bills & Utilities, so it counts in the month's spending; nothing is paid. It isn't logged twice: if an expense for the same amount with a matching name is already in the ledger within a few days (from email, a statement or typed in), that one stands and the reply says so. A bill with no set amount is logged only with an amount: the Bills card asks for one (or **Just mark paid**), and in chat the user can say it. A payment that doesn't count as spending (a regular investment, a transfer to savings, family or another account) works the same way for reminders, snoozing and Cash flow, but its button is **Mark done**, and marking it done logs nothing, so it never counts in spending, categories or budgets. In chat, `add_bill` takes `counts_as_spending`, and the transfer refusal points to setting a reminder instead.
- **Salary:** only what the user reports. The pay schedule is one of three: a day of the month (clamped to short months), the last weekday, or every two weeks from a date. Weekend paydays move to the Friday before. On payday, from 09:00, there is one check-in. With a usual salary set, it has **Log** and **Not yet** buttons, and Log records the usual amount once per payday. When the user reports a different salary, the bot asks before changing the usual amount; nothing changes silently.

## Time zone that follows you

`users.timezone` is the user's **current** time zone: every "their day" (summaries, reminders, quiet hours, what "today" is) reads it, so everything follows when it changes. `users.home_timezone` is where they live and what they go back to (backfilled from `timezone` by migration 0055; a new user's two are the same). `users.timezone_source` says what set the current zone (`home`, `phone`, `chat` or `trip`) and `users.timezone_set_at` is when their phone or they last said where they are (null if never; a trip never touches it).

- **The rule** (`decide` in `domain/whereabouts.py`, pure and unit-tested): the phone and the user (chat, or picking a zone in Settings) apply at once, the newest winning. A phone that repeats the zone they are already in only refreshes `timezone_set_at`. A trip applies only when neither has spoken in the last 24 hours. When no trip is on and the trip is what moved them (`timezone_source = trip`), they go back home. A zone equal to the home zone always has source `home`. Zones are checked with `ZoneInfo`; an unknown one is a 422 / a tool error and changes nothing.
- **The use case** (`report_zone` in `application/whereabouts.py`) takes the user, a zone, a source (phone, chat, home or trip) and the time, applies the rule under a row lock, saves, and returns `{user, changed, old, new}`. When the zone itself changed it queues ONE `telegram.send` (kind `timezone`, level `now`: it keeps to quiet hours in the new zone, so a switch the trip sweep makes at 3am waits for the morning, and it is never counted toward the daily cap): "🕑 Switched to Madrid time (UTC+2)." or, going to the home zone, "🕑 Back on Singapore time." (the city is the last part of the zone name, `America/Argentina/Buenos_Aires` is "Buenos Aires"; the offset is the one in force that day). A phone report that changes nothing sends nothing. The chat tool and Settings pass `notify=False`: the reply already says it.
- **Trips**: the hourly `whereabouts.follow` sweep looks at each user with a trip not over (and anyone the trip moved) and applies the trip signal. For a trip that is on in the user's own day, the place is that day's stop (the trip's stops, else the ones the hotels suggest; on a travel day the stop arrived at), else the destination; its zone comes from `Weather.zone_of(place)`, which reuses the weather geocoding (Open-Meteo's `timezone`) and its 30-day cache, gives up after 3 seconds and returns nothing on any error. A place whose zone cannot be found changes nothing (it is never taken for "no trip"). One user failing does not stop the others.
- **Web**: `GET /api/me` has `user.home_timezone`, `user.timezone_source` and `user.timezone_set_at` beside `user.timezone`. `POST /api/me/timezone` with `{"timezone": "Europe/Madrid", "source": "phone" | "manual"}` (the phone's own zone, or the user's pick in Settings, kept as source `chat`) and `POST /api/me/timezone/home` answer `{"timezone", "home_timezone", "timezone_source", "timezone_set_at", "changed"}`. An unknown zone or another `source` is a 422. Only a phone report sends the Telegram message.
- **Chat**: the core tool `set_timezone` (`place` as the user said it, or `home: true`) takes a zone name directly or finds a city or country's zone with the same geocoding. "I'm in Madrid now" and "we landed in Tokyo" call it; "what time is it here" and a city named in an expense ("¥1200 ramen in Tokyo") do not. The system prompt shows the home zone beside the current one when they differ.

## Categories

New users get twelve defaults: Dining Out, Groceries, Transport, Shopping, Bills & Utilities, Socialising, Health, Travel, Activities, Subscriptions & Software, Income and Other. Migration 0014 gives existing users the same set: Food & Drink becomes Dining Out and Entertainment becomes Activities (unless the user already has a category by the new name), and missing defaults are added. Migration 0015 folds the old bot's Dining into Dining Out and General into Other: their transactions and rules move over (a budget too, unless the new category already has one), and the old category was archived (0041 later deleted it if empty). No undo history is written for it. Migration 0016 adds Subscriptions & Software for everyone and regroups the rest of the old bot's categories (those with imported transactions) by keyword into the defaults, or Other when nothing fits; Personal Care is kept, and categories users added themselves are left alone. Users can also merge one category into another (Settings, `POST /api/categories/{id}/merge`, or chat): its transactions, rules and budget (unless the target has one) move over and the source is deleted. Deleting one (Settings, `DELETE /api/categories/{id}?move_to=<uuid>`, or `delete_category` in chat) moves its transactions and rules to the category the user picks (Other by default), deletes its budget, then deletes the category for good. Other and Income can't be deleted, as they are the fallbacks for new expenses and money in. `GET /api/categories` returns `{id, name}` and `PATCH` takes the name only. Migration 0041 (`delete_archived_categories`) deleted archived categories that held no transactions (with their rules and budget), turned archived ones that still held transactions back into normal categories, and dropped `categories.active`. Names are unique per user regardless of case; a clash is a 409.

**Split habits follow their category.** A split habit (`split_habits`, migration 0057: "I always split dinners with Ann") names its category by text, any case, so renaming, merging or deleting a category moves the user's habits for it to the new name in the same transaction (`follow_habits` in `application/categories.py`, `rehome` in `domain/split_habits.py`). Merge, and delete into a chosen category, send them where the expenses go; a delete that falls back to Other drops them, since a habit on Other would split every stray expense. A person has one habit per category: if the person already has one on the new name, that one stays and the moving one is dropped. Other users' habits and habits for any category are never touched.

Possible duplicates already in the ledger (by the same rule, among live transactions) show on the Ledger as "Possible duplicate of …" with **Merge** and **Not a duplicate**. Merge keeps the one a split, repayment or receipt hangs on (otherwise the one logged first) under the more readable name and deletes the other, which can be restored; a pair that are both part of split bills is left to delete by hand. Not a duplicate is remembered in `duplicate_dismissals` (migration 0020), so the pair isn't flagged again. In the chat, `find_duplicates` lists them and `combine_duplicate_transactions` merges a pair after the usual confirmation (the duplicates skill).

**Departments.** The chat agent is the front desk; the teams behind it are declared in a registry (`application/departments.py`). Today that's Accounting, which owns every chat skill. A department whose work takes minutes runs it as a *run*: a typed task, a list of steps and a typed result. Each step is its own `department.step` job with a 70-second limit; its output is saved before the next step is queued, so a redeploy resumes a run rather than restarting it. A failing step is tried once more a minute later, then the run fails. A user can have 2 runs going, start 20 a day and spend US$1 a day on their model calls; each kind also has a spend cap per run. Progress is one Telegram message edited in place, with Cancel while it runs (cancelling lets the step that's going finish and starts nothing after it); a finished run's message carries its one-line result. The web app reads `/api/departments` and `/api/runs` (and `/api/runs/{id}/cancel`). A run's progress message starts with its department ("📈 Investment: …") unless it's Accounting. Asking "what are you working on?" (or "anything running?", "my jobs", "job status") lists what's running and the last few finished, with a Cancel button for each one going; the kernel answers it, so it needs no model.

**Images and files on Telegram.** Every photo is looked at first, then routed by code. No model decides the route.

1. **The first look** (`agent/image_look.py`). One call returns:
   - what the image is: receipt (paid), bill (to pay), transfer, payslip, portfolio, travel booking, chart or other
   - the ISO currency of any prices
   - a one-line summary
   - a faithful transcription of the visible text

   It uses `IMAGE_LOOK_MODEL` on OpenRouter (unset: `OPENROUTER_MODEL`, DeepSeek v4.1 Flash, about 2 seconds, on the pinned providers), without reasoning. After 15 seconds, on an error, or on a reply that doesn't parse, `OPENROUTER_VISION_MODEL` looks instead (40 seconds at most). On 5 October 2026, on 14 made-up and drawn images three times each, DeepSeek got 42/42 (median 1.8s) and Qwen 3.8 Flash 42/42 (3.4s). DeepSeek is not used for the structured readers: as a receipt reader it failed 6 of 11 photo cases and once hung.
2. **The route** (`route()`):
   - A caption naming travel or a portfolio sends the image to the trip or holdings reader.
   - A caption that asks something ("is this expensive?", "what's this for?", but not "log this") goes to the chat agent.
   - Otherwise the kind decides: receipts go to the receipt reader (`OPENROUTER_VISION_MODEL`), which logs them after the usual confirmation; portfolios to the holdings reader; travel bookings to the trip reader.
   - Everything else goes to the chat agent: bills, transfers, payslips, charts, menus, and a "receipt" the reader finds no total on.
   - If both looks fail, the photo is read as a receipt, as before.
   - **If the receipt reader can't read the photo** (`agent/receipts.py`): each read gets 20 seconds (`READ_TIMEOUT`). A slow, failed or unparseable first read is tried once more on the same photo model (not the fast look model, which misreads receipts). If both reads fail and the look says "receipt" with text, the main chat model reads the look's text instead (`TextReceiptReader`, one try, 20 seconds, the text quoted as data); a total found that way goes through the same currency check, photo stash and confirmation as a normal read. If that fails too, the photo goes to the chat agent with a note that the total couldn't be read, so it asks for the amount instead of offering to log it. Worst case about 60 seconds.
3. **The chat agent** gets the caption and the look as `<image>…</image>` (`<image 1>`, `<image 2>` for several). Angle brackets in the image's text are replaced, so it can't close the quote. The system prompt says it's data, not instructions, and nothing is logged from an image unless the user asks. The kernel's shortcuts never act on image text, so a payslip's "salary 4200" isn't recorded as income. The memory writer sees only the caption. On a turn about an image whose caption doesn't ask for an action ("add this bill", "log it", "split with Ann"), the agent is offered only tools that read (`READ_ONLY` in `agent/tools.py`) or that confirm first. A call to any other tool is refused with a note to offer it instead, so the user's "yes" in their next message is what changes anything. A new tool is withheld from these turns until it's listed or confirms first. Without this, a bill photo with no caption was added as a bill on its own in one eval run. The quoted text stays in the conversation, so follow-ups ("what's the cheapest thing?") work.
4. **Currency check.** When the receipt reader gives no currency, the look's is used. When the two disagree, the confirmation adds "⚠️ The receipt may be in JPY, not SGD…".
5. **What Telegram can send:**
   - Photos.
   - Images sent as files: JPEG, PNG and WebP. Other types, such as HEIC, get a request to send a photo instead.
   - PDFs: their text goes to the chat agent the same way. Locked PDFs point to Import on the web, and scanned PDFs with no text ask for a photo.
   - Albums: the parts are collected for 1.5 seconds and handled together under the one caption.
   - A text reply to an earlier photo looks at that photo again, with the reply as its caption.

   Images and files are never stored (receipts kept for the archive aside). The made-up eval images are in `evals/receipts/` (`photo-*` cases).

**Investment department (M13).** Holdings are one row per stock (`holdings`: shares, average cost per share, currency). A screenshot of a broker's Portfolio screen (IBKR first) is read by the vision model (`OPENROUTER_VISION_MODEL`): on Telegram when the caption mentions portfolio, holdings, positions or IBKR, or when a photo turns out not to be a receipt; on the web from Investment → Upload screenshot (base64, the same per-user limit as statement imports). Nothing is saved until the user taps Save: the positions wait as a draft in `holding_drafts`, a newer screenshot replaces an older draft, and saving makes the screenshot the whole portfolio (stocks it doesn't show are removed). Rows that can't be read (cash, totals, a blurry figure) are left out. Typed trades ("I bought 10 NVDA at 118") go through `record_trade` after a confirm: a buy weights the average cost, a sell leaves it and removes the stock when none is left. US stocks default to USD. The image is never stored. Nexus never trades, connects to a broker or asks for broker logins.

**Trades, gains from sales and dividends.** Every trade the user records (chat `record_trade`, or Investment → Trades on the web, `POST /api/investments/trades`) is kept in `trades` (migration 0031) with its date (today unless told) and price. A sale with its price records what it locked in against the average cost, as brokers show it; one without a price is kept, with that left unknown. Screenshots still set positions outright and add no trades. Daily prices now carry Tiingo's `divCash` (the dividend per share going ex that day, `market_bars.div_cash`); a stock stored before this is fetched in full once more (`market_symbols.dividends`). After each price refresh that fetched something, dividends that went ex in the last 30 days are recorded (`dividends`) for each user who held the stock at the close before, worked back from today's shares through the trades after that day, but only from when Nexus knew of the holding (its first save or the first dated trade): before that it can't know they held it. Each is recorded once and the user gets a Telegram note with gross, tax withheld and net. US dividends have 30% withheld (Singapore residents, no treaty); others none. The portfolio totals add what sales locked in, dividends received after tax, and the total return (held, sold and dividends), all in the home currency at the latest close's rate. `GET /api/investments/dividends` and `show_dividends` list dividends received and the next 12 months if each holding pays what it paid in the last 12, with the yield on price and on cost; `trade_history` lists trades with what each sale locked in. Dividends aren't added to the ledger as income.

**Prices and values (M13a).** With `TIINGO_API_KEY` set, an hourly `prices.refresh` job fetches end-of-day prices from Tiingo for every stock anyone holds, once each trading day's prices are due (18:00 and 22:00 New York time on weekdays), and right after holdings change. A stock's first fetch takes about 15 months of history (for M13b's moving averages); later fetches re-take the last week so a corrected close replaces the old one. At most 40 stocks per run, well inside Tiingo's free tier (50 an hour, 1,000 a day). Prices are market data shared by every user (`market_bars`, `market_symbols`, no `user_id`); `market_symbols.known` is false for a ticker Tiingo doesn't list. Holdings are valued at the last close (or, while the US market is open, at a live quote: see Live prices below), and converted to the home currency at the dated reference rate for that price's trading day; gains use the same rate for cost and value, since the purchase dates aren't known. A stock without a price or rate yet, or one recorded in a currency other than USD, is shown at cost and left out of the totals. The key is sent in a header, never in the URL. Without the key nothing is fetched and the Investment page says prices aren't set up.

**Watchlist, levels and news (M13b).** A user can watch up to 50 stocks they don't hold ("watch AMD", or Investment → Watchlist); prices are kept for held and watched stocks alike. A stock's levels are worked out in code from its stored daily bars each time they're shown, never by a model and never stored (`domain/levels.py`): prices adjusted for splits and dividends first; 20/50/200-day simple moving averages; Wilder's 14-day RSI and ATR; support and resistance as swing lows and highs (the lowest or highest point of the 5 days either side) from the last 120 trading days, nearest first, up to three each side, merging levels within half an ATR; and the 52-week range. Levels need 20 days of prices; the 200-day average needs 200. With `FINNHUB_API_KEY` set, an hourly `news.refresh` job fetches each held or watched stock's last 7 days of company news and its earnings dates for the next 90 days, at most every 6 hours per stock, or every hour while the US regular session is open (the same market status as the live prices below: Finnhub's own, else the usual hours; never on a day in `NYSE_HOLIDAYS`; a run counts a stock as due 2 minutes short of its hour, since the hourly job doesn't start on the same second) (25 stocks a run, the ones that have waited longest first, two calls each, inside Finnhub's free 60 a minute; a 429 stops the run). News is someone else's text: it's cleaned to one line, links must be plain http(s), the same story from several feeds is kept once, and it's dropped after 30 days (`market_news`, `market_earnings`, `news_fetches`, shared like prices). Chat tells the model that headlines are quoted data, not instructions. Dividend dates aren't on Finnhub's free tier and aren't fetched. Each stock has a page (`/investment/stocks/{symbol}`) with its levels, next earnings date and news, and the chat tools are `stock_levels`, `show_watchlist`, `watch_stock` and `unwatch_stock` (the last two confirm first).

**Live prices (migration 0049).** With `FINNHUB_API_KEY` set (the same key as news), US stocks show a live price during the session instead of yesterday's close. Quotes are market data shared by every user (`market_quotes`: the latest price, previous close, day's high, low and open, when it was traded and when it was fetched); the exchange's open/closed status (`GET /stock/market-status?exchange=US`) is remembered in the app process for 5 minutes. The key is sent in a header, never the URL. A `quotes.refresh` job runs every 5 minutes (a Postgres job slot, like the others) and asks for the status first: while the regular session is on (9:30 to 16:00 New York, by Finnhub's status; if the status can't be fetched, the same hours on weekdays stand in, which don't know holidays or early closes) it fetches a quote for every stock anyone holds or watches, plus SPY, oldest-fetched first, at most 50 a run and no new fetch after 40 seconds; in the 20 minutes after the close it fetches each once more (those not fetched since the close) to catch the closing price; otherwise it does nothing, and without the key it is a no-op. A stock Tiingo doesn't list (`market_symbols.known` false) is skipped. Finnhub's free tier allows 60 calls a minute: a 429 stops the run (or a page's refresh) and what was stored is kept; one stock failing doesn't stop the others. A page also refreshes: `GET /api/investments` (the holdings), `/watchlist` (the watched) and `/stocks/{symbol}` (that one stock) ask for the signed-in user's own stocks, and no one else's, when the market is open and the stored quote is over 60 seconds old, at most 15 stocks and 3 seconds a request, with any failure ignored (the stored quote or close is shown); the stock page's own ticker (checked with the same rules as holdings: a ticker, not free text) may be one the user neither holds nor watches, so it is limited to 30 a user every 5 minutes. Which price is shown is decided in code (`domain/market.pick_price`): during the regular session with a quote traded today, the **live price** (day's change against the quote's previous close); after the close, with a quote from a trading day newer than the latest stored close, the quote's last price as a **provisional close** until Tiingo's end-of-day bar for that day arrives (18:00 or 22:00 New York time) and replaces it; otherwise the last close. A quote from a past day while the market is open, from before the open, no newer than the latest close, or stamped in the future is ignored. So is one stamped outside the regular session on its own day once the session is over (before 9:30, or more than 5 minutes after 16:00, `CLOSE_PRINTS`, which leaves room for the closing prints): if Finnhub's quote includes extended-hours trades, a 7pm quote is not shown as the close, and the last stored close stands until the day's bar arrives. To learn whether it does, every quote store (the job, a page, a plan run) logs at INFO, once per store and only when there is one, `quotes: N of M stamped outside regular hours (latest HH:MM ET)`, with no symbols or users. Values and day changes in the home currency use the rate of the price's trading day, as for a close (today's rate isn't cached). The API carries `price_kind` (`live`, `provisional_close` or `close`) and `price_at` (when it was traded; null for a close) on each holding, watchlist row and stock page, and `as_of_at` and `price_kind` (live if any holding is, else provisional, else close) on the portfolio totals; `as_of` stays the latest trading day. The web pages label each price ("Live · 10:42pm", "Close (provisional) · 4:00am", "Close of Fri 16 Oct", in the browser's timezone) and, while a price is live and the page is in view, refetch every 60 seconds (and on window focus); a close is never polled. The stock page's `now_vs_levels` is up to three short facts on that price against the levels (the nearest support below and resistance above within 5%, and the percent from the 50- and 200-day averages). In chat, `show_portfolio`, `show_watchlist` and `stock_levels` say when each price is from, in the user's timezone ("at 10:42pm (live)", "at the close (provisional)", "at the close on Fri 16 Oct"); chat reads the stored quotes (the job keeps them within 5 minutes) and the usual hours for the market, and doesn't fetch. Levels and a plan's numbers are still worked out from closes only, though a plan run reads the live price too and says when it is already past them (see Research plans); the market alerts below watch the live price in between.

**Market alerts, the morning summary and what moved today (migration 0050).** Everything here is Telegram or chat, for users with a Telegram chat, and research only. *Settings* (on `notification_settings`; a user with no row has the defaults): `quiet_start` 23:00 and `quiet_end` 08:00 (see Quiet hours), `move_alert_percent` 5.0 (1 to 20, one decimal; a check constraint and `domain/notifications.move_percent` both refuse others) and `market_summary` true. `GET`/`PUT /api/notifications` carry them with `frequency` and `daily_at` (every field optional on PUT, what is left out stays; 422 for a value outside the limits or an unreadable time), and the chat tool `set_market_alerts(move_percent?, morning_summary?, quiet_start?, quiet_end?)` (investments skill; with nothing given it shows them) changes them. The existing `transaction_updates` tool is only for how often transactions are summarised. *Alerts during the session* (`application/market_alerts.py`): after each `quotes.refresh` run that fetched something, and only while the regular session is on (the exchange's status, or the usual hours, and never on a day in `NYSE_HOLIDAYS`), every user's open plans with alerts on and every held and watched stock are compared with the stored live quote (only a quote traded today and no newer bar counts, as for prices): a plan not yet entered whose price is at or below the top of its buy zone but above its stop is `plan_entry`; a plan that is entered (or about a stock already held, or about a stock the user holds) at or below its stop is `plan_stop`, **urgent when the user holds the stock**; at or above its first target is `plan_target`; a held or watched stock up or down by `move_alert_percent` or more against the quote's previous close is `big_move` ("📉 NVDA −5.4% today at 10:42pm, 182.40"). A plan alert uses the plan's own wording (`plans.event_text`; the stop says the price is at or below the stop, as the follow's "closed below" would be untrue), with the "Stop alerts for this plan" button. Each is kept once per user, stock, kind and New York trading day (`market_alerts`, unique on those four, so a second plan for the same stock adds nothing); one that is new is sent now (a `telegram.send` job with the key `market-alert:<id>`, `sent_at` set) unless it falls in the user's quiet hours and is not urgent, when it stays unsent (`sent_at` null) for the morning summary. A user who turned the morning summary off has the alert queued instead, and the sender holds it as the notification policy says (a big move for the next digest, a plan alert with its button until quiet hours end), since nothing else would ever tell them. A failure of the check is logged and never fails the refresh. *The evening follow* (`plans.follow_plans` on daily bars, unchanged in what it saves) first looks for an alert of the same stock, kind and day in `market_alerts` and skips the event when there is one, so a buy zone told at 11am isn't told again at 6pm; otherwise it records the event in `market_alerts` too, sent under the old `plan:<id>:<event>` key, or held for the morning summary when it falls in quiet hours and the summary is on. A plan that ran out has no live version and is sent as before. *Morning summary* (`application/market_summary.py`): a `market.summary` sweep every 10 minutes finds users whose local time is 08:00 to 12:00 (a sweep missed at 08:00 still sends until noon) and who have the summary on and hold or watch a stock, on a morning after a US trading day: the session told of is the last weekday whose 16:00 New York close has passed, skipped when that day is in `NYSE_HOLIDAYS` or its close is over 24 hours old (so a Sunday or Monday morning in Asia, or any morning after a weekend, never repeats Friday). It queues `market.summary.user` under the key `market.summary:<user>:<local date>` (once per user per day); that job values the portfolio as of 20:00 New York time on the session's day (so a user in a time zone where the next session is already open still hears about the last), builds "📊 Portfolio +1.2% yesterday (SGD +312.40)" ("on Fri 16 Oct" when it wasn't yesterday there), the three biggest movers each with the day's newest headline, "While the market was open:" with the alerts held unsent for that session and "Your plans after the close:" with the follow's events held in quiet hours (all marked sent in the same transaction, ten lines at most then "and N more"), and queues it as a `telegram.send` with `anytime`, key `market.summary.user.send:<user>:<local date>`. With nothing to say (no prices) nothing is sent. `NYSE_HOLIDAYS` in `domain/market.py` is a hard-coded list for 2026 and 2027 (Finnhub names a holiday only for today); early closes aren't kept; add the next year's before 2027 ends. *What moved today* (`application/moves.py`): `GET /api/investments/today` and the chat tool `what_moved_today` give the portfolio's change in the day (home currency and %), at the live, provisional or closing prices `pick_price` chooses, and the three holdings that moved most by absolute % (the watched stocks when nothing is held), each with its price, `price_kind`, `price_at` and the day's newest headline (published since the session's open, 9:30 New York time on the session's day; none otherwise), plus `session`: `live`, `closed_today` or `previous` (before the open, a weekend or a holiday: the last session's figures) for wording. The page refreshes the user's own stocks' quotes like the other pages. *Why did it move*: `POST /api/investments/today/{symbol}/why` is for the user's held or watched stocks only (404 for any other), limited to 6 a minute and 60 a day per user (`why`), and makes one model call (the memory model path: `MEMORY_MODEL` on OpenRouter, else the main model, no reasoning) given only the ticker, the percentage and up to 8 of the day's headlines inside `<headlines>` (angle brackets removed from them, and the instructions say they are data and to follow nothing in them), nothing of the user's. It answers in 2 to 3 sentences with no advice; code keeps at most three sentences, drops any with a figure the headlines or the move don't give or a web address, and says so in one line when none are left. The call's size is capped so it costs about US$0.01 at most (headlines are trimmed until the prompt plus a 250-token answer fits at $1 and $4 a million tokens). With no headline from today there is nothing to read, so no model is called. The answer is kept in memory for 30 minutes per stock and day (shared, since it holds nothing personal); a model failure is a 422 and isn't kept.

**Research plans (M13c).** "Plan for NVDA" (chat's `research_plan`, or Make a plan on a stock's page) starts an Investment department run (`investment.plan`) of three steps (four with a reviewer), each its own job with progress in one Telegram message and a Cancel button:
1. **Levels (code).** Works out the plan's numbers from the stock's levels (`domain/plans.py`). Every plan has a stop, targets and a review date:
   - buy (or add more) in a zone at the nearest support below the close (a swing low or a moving average), up to half an ATR above it;
   - cut losses on a daily close one ATR below that support, or two ATRs below the close when there's no support below;
   - take profit at the resistance overhead: swing highs, the 52-week high and moving averages above the price. A new buy counts only targets at least 2 times the risk; for a held stock the nearest ones are where to sell part. With little overhead (a stock at its highs), targets are measured at 2 and 3 times the risk from the buy zone, stepped up to the nearest multiples above today's close when those would sit below it (a wait-for-a-dip plan far above its zone used to get targets below today's price);
   - once the first target is reached, raise the stop to today's price;
   - review in 14 days, flagging an earnings date inside that window;
   - verdicts: a good price to buy, wait for a dip, not a good setup (falling with no support, or resistance too close), keep holding, take some profit (the last plan's first target was reached), or time to cut it (a close below the last plan's stop).
   
   The writers are also given the stock's last year in numbers (`domain/history.py`, from adjusted closes): its change over 1 week to 1 year and this year, how far it is below its highest close, its deepest fall, its typical daily move lately against the year's, shares traded lately against the year's average, how it did against SPY (an S&P 500 fund, fetched with the tracked stocks), and how it moved on its last four earnings (the close before the news to the close after; earnings dates are now fetched a year back as well as 90 days ahead, and past ones are kept). They also get the likely ranges and the next earnings date. All of it is percentages and dates, so none of it reads as a price; it's shown on the stock page ("Its last year") and folded under the plan's numbers.

   The numbers become a game plan (`playbook`): Buy / Add more, Take profit, Cut losses, After the first target, and Hold until / Valid until. Each step is a plain sentence carrying its own prices and percentages from today (and from the user's average cost for a held stock). That's what Telegram, the chat and the web show.

   **It reads today first.** Before anything is worked out, the step fetches the stock's news and earnings dates fresh (the same two Finnhub calls as the hourly `news.refresh`, `research.refresh_symbol_news`) unless they were fetched in the last 15 minutes, and, while the regular session is on or in the 20 minutes after the close, refreshes its quote (`quotes.refresh_symbol`: one call, 3 seconds at most) unless the stored one is under 60 seconds old. A source that fails, is over its limit or isn't set up is logged and the stored news, quote or close is used; a plan is never held up by it. The brief's **price now** is the one `domain/market.pick_price` chooses (live, provisional close or close), with when it was traded ("Price 182.40 at 10:42pm (live)", in the user's timezone, from `describe_price_time`), and it joins the figures the writers may quote. The verdict, buy zone, stop and targets still come from the code maths on daily closes, unchanged; but when the price is live or provisional and a plan that makes a call (buy now, wait, hold, take profit) finds it already past them, code adds a plain note (`domain/plans.price_notes`, kept in the plan's `notes`, given to the writers as "Note: …", shown with a ⚠️ in Telegram's plan message and in chat): "The price is already in the buy zone" (only for a wait-for-a-dip plan whose close was above the zone), "The price is already under the buy zone" or "The price is already under the stop", each with the live price and the figure, and "check where things stand before acting" (a held stock's zone is the "add-more zone"). A plan keeps the price it used as `price`, `price_at` (when it was traded; null for a close) and `price_kind` (`live`, `provisional_close` or `close`) on `plans` (migration 0051), plus `atr` (a typical day's move) in its body. The plan API carries `price`, `price_at` and `price_kind` on every plan brief (the list, the detail and the stock page's latest plan; null on plans made before), and the chat's `show_plan` opens on "Price 182.40 at 10:42pm (live)". Telegram's plan message has the notes but no price line, since it has no timezone to show the time in.
2. **Analysts (model, two calls at once).** The technical analyst reads trend and momentum from the figures. The news analyst says what changed; each point must cite a headline id that exists, or it's dropped. Headlines are passed inside `<headlines>` as quoted data. With `TAVILY_API_KEY`, the levels step also reads the articles behind the four newest headlines (investment's share of the web credits, kept a day, at most 20 seconds) and the first 1,500 characters of each, on one line, go under its headline in the same quoted block; without the key, past the share, or when a page won't read, the analysts get the headline alone. The checks don't change: a point must cite a headline id, and no price from the news survives `keep_supported`.
3. **Lead analyst (model).** Writes the case for and against (bull and bear), the summary and what would prove the plan wrong. Then the plan is saved in `plans` (migration 0025, status `open` until M13d scores it).
4. **Review (optional, off by default).** With `RESEARCH_REVIEW_MODEL` set (an OpenRouter id, run with low reasoning), a stronger model reads the figures, the headlines and the draft and corrects the chart reading, both cases, the summary and what would prove it wrong; then the plan is saved. It has one 45-second try (`REVIEW_TIMEOUT`); if it fails, the draft is saved as it was. Its text goes through the same number check.

**Speed and failures.**
- **No reasoning.** The writers run without reasoning (`RESEARCH_MODEL` / `RESEARCH_LEAD_MODEL`, else GPT-6 Luna Pro, through `_quick`). On 5 October 2026 production plans with reasoning on took about 3 minutes, and the debate step often ran past the 70-second step limit ("it took too long"): five failures in two days. Measured with DeepSeek v4.1 Flash on a made-up stock:
  - reasoning on: each write-up 7–94 seconds, a plan 165–200 seconds and about $0.065;
  - reasoning off, in this design: 8–10 seconds a plan and about $0.005, reading just as well.
- **Call limits.** Each model call has 25 seconds (`CALL_TIMEOUT`) and one more try (`CALL_TRIES`), well inside the step limit.
- **Failed writers.** A writer that still fails leaves its part out and the plan is saved anyway, since its prices never depend on a model. `incomplete` lists the missing parts ("the chart reading", "the news", "the case for and against"). Telegram adds "⚠️ The write-up is missing … this time; the prices and game plan are complete", and the plan page shows the same note.
- **Plans already running.** A plan started before this change and still running when it deploys finishes its lead step without the analysts' text.
- **Which model writes (5 October 2026).** Eleven models wrote plans for three made-up stocks (traps included: a headline quoting an analyst's price target and one carrying an instruction), judged blind by Claude Sonnet 5.5 out of 20. GPT-6 Luna Pro scored 13.2, faithful 3.7 of 5, in about 8 seconds for $0.0016; DeepSeek v4.1 Flash scored 11.2 and wrote twice as many words. Luna Pro is the default.
- **With history and the tighter rules**, on a year of made-up prices (9 plans per setup, judged by Sonnet 5.5 and Grok 4.7): Luna Pro alone 14.1 to 14.2 (Sonnet) and 15.9 to 16.2 (Grok), 11 seconds and $0.002 a plan; with GPT-6.1 Sol reviewing, 14.0 and 17.4, 23 seconds and $0.012. The reviewer helps by one judge's reading and not the other's, for twice the wait and five times the cost, so it stays off by default.

The analysts get no tools. Any sentence a model writes that quotes a price the plan and its levels didn't work out is dropped, so every figure the user sees traces to code. A plan needs 20 days of prices. Each run's model spend is estimated from token counts at a deliberately high rate ($1/M tokens in, $4/M out) and capped at US$0.10, inside the department caps (2 runs at once, 20 a day, US$1 a day). `RESEARCH_MODEL` and `RESEARCH_LEAD_MODEL` (OpenRouter ids) choose the analysts' and lead's models; unset, both use GPT-6 Luna Pro (without OpenRouter, the main model). `RESEARCH_REVIEW_MODEL` adds the review step. Plans are listed under Investment → Plans. Each one opens on the verdict, coloured go, wait or stop, then the game plan step by step and what would prove it wrong. Below that come a chart of 90 days' closes with the buy zone, stop, targets and the user's cost drawn on, and why: what's going for it, what could go wrong, and the news with linked sources. The analysts' chart reading and the raw levels are folded away. The analysts are told to write for someone who isn't a trader: complete sentences, every market term explained the first time, nothing about the past beyond the history figures, no price from a headline, and never against the verdict or game plan. The number check also lets through names and dates with numbers in them ("S&P 500", "200-day", "27 Oct 2026"). `show_plan` reads the latest one in chat.

**Alerts and a track record (M13d).** Open plans that make a call (buy now, wait for a dip, keep holding, take some profit) are followed after each US close. The hourly `plans.follow` job runs, and also runs straight after a price refresh brings new closes. `domain/plans.follow` walks the trading days since the plan, or since its last check, oldest first:
- **Bought:** a buy plan counts as bought from the first day whose low reaches the top of the buy zone. A held stock counts from the day the plan was made.
- **Stopped:** after that, a day that closes below the stop ends the plan as stopped. The stop is checked first, the cautious reading of a day that touched both.
- **Target:** a day whose high reaches the first target ends it as a hit.
- **Ran out:** a plan still open after its valid-until date ends as ran out.

Results are measured from the middle of the buy zone, or from the plan day's close for a held stock. A buy plan that never reached its zone has no result and counts as "never bought". Each event (buy zone reached, target, stopped, ran out) queues one Telegram message, once per plan and event, as a `plan_event` (see the notification policy). While the market is open the live price can say the same thing sooner (see Market alerts above): an event already alerted that day isn't sent again, and one that falls in quiet hours is held for the morning summary when that is on. The message carries a "Stop alerts for this plan" button while the plan is still open; the web plan page has the same switch. The plan stays in the record either way. Migration 0026 adds `entered_on`, `checked_through`, `outcome_price`, `outcome_day`, `result_percent` and `alerts` to `plans`. The Plans page opens on the track record: hit target, stopped out, ran out (with how many were never bought), the average result and how many are open. Every plan shows its status, and `plan_record` reports the same in chat. "Not a good setup" and "time to cut it" plans aren't followed or scored.

**Keep this plan fresh (migration 0051).** A switch on an open plan (`plans.keep_fresh`, off by default) that has Nexus make the plan again by itself when it goes stale, and replace the old one. It is set from chat ("keep my NVDA plan fresh", "stop refreshing my NVDA plan": `keep_plan_fresh(symbol, on)` in the investments skill, which finds the newest open plan for the stock; no confirmation, as turning alerts off has none) and by `PUT /api/investments/plans/{id}/keep-fresh` with `{"on": true}` (204; the user's own plans only, so another user's is a 404 as for alerts; 422 for a plan that has finished). `GET /api/investments/plans` and the plan detail carry `keep_fresh` and `refreshed_from` (`{id, created_at}` of the plan this one replaced) on every plan brief, and the plan detail also carries `replaced_by` (`{id, created_at}` of the user's newest plan whose `refreshed_from` is this one, else null). On the web, an open plan's page has a "Keep this plan fresh" switch (under the verdict, styled like the alerts switch, with "Nexus re-runs it when the price moves a lot, after earnings, or once a week."): it changes at once, is put back with the server's reason if refused, and is left out of a plan that has finished or been refreshed. The Plans list tags an open plan that has it on with "Fresh", and labels a replaced plan "Refreshed" (the list still returns it; only the track record leaves it out). A refreshed plan's page says "Refreshed from the plan of 7 Oct" with a link back, and the old plan's page says "A newer plan replaced this one" with a link forward (found from the plans list). The plan page also opens on the price the plan was written with ("Price 182.40 · Live · 10:42pm") and shows the notes about a price already past the buy zone or the stop.
- **When.** The hourly `plans.refresh` job (`application/plan_refresh.py`) looks at each open plan with the switch on and starts a refresh when, checked in this order (`domain/plans.refresh_reason`): (1) it has expired, its `valid_until` before today's New York date; (2) the live or last price (`pick_price` on the stored quote and bars) is more than 1 ATR from the price the plan was written with (its close, for a plan made before prices were kept), using the plan's own `atr` (today's, from the bars, for an older plan); (3) the stock reported earnings after the plan was made and that day (New York) is now past; (4) the plan is 7 days old or more. The reason is kept in the run's task (`refresh_why`: "price moved 2.3 ATR", "it had run out", "earnings are out", "it was a week old").
- **Limits.** At most one automatic run per plan every 24 hours (`plans.last_refresh_check`, set when a run starts; a plan made by a refresh in the last 24 hours also counts), at most 10 a user in 24 hours (the plans whose `last_refresh_check` is that recent), and none while a plan run for the same stock is already going. It starts through the same `start_plan` as the user's own request, so the run caps (2 at once, 20 a day) and the day's spend cap apply: a run that can't start (a cap, too few prices) leaves the plan untouched and unmarked, and is looked at again next hour. A refresh is a plan run like any other for those counts.
- **Expiry and the follow.** For 3 days after its valid-until date (`KEEP_FRESH_GRACE`, on the date `follow_plans` uses), `plans.follow_plans` doesn't close a plan with the switch on as expired (it stops short of the valid-until date), so an expired plan is still open when `plans.refresh` looks, whichever job runs first, and is refreshed instead of just running out. Its other events (buy zone, stop, target) are followed as usual. If a refresh can't start (a cap, too few prices) it is tried again every hour for those 3 days; after that the plan is followed as any plan and runs out with the usual message ("Your NVDA plan ran out on ..."), so a kept-fresh plan never stays open for ever. Turn the switch off and the next follow runs it out at once.
- **The run is silent.** An automatic run shows no progress message and sends none when it is done (`plans.is_automatic`; `TelegramProgress` skips it); it still shows in the runs list. When it saves, the new plan links to the old (`refreshed_from`, a composite foreign key with `user_id`, so the database refuses another user's plan; deleting the old one only unlinks), takes over its `keep_fresh` and `alerts` settings as they are then (so a switch turned off meanwhile stays off), and the old plan is closed with the new status `refreshed` (`closed_at` set, `keep_fresh` off). A plan that finished meanwhile (stopped, target) keeps its own outcome and is linked all the same.
- **The message.** Only if the verdict changed, or the entry (middle of the zone), the stop or the first target moved by more than half an ATR (or appeared or went), the user gets one Telegram message through the normal `telegram.send` (key `plan-refresh:<plan id>`, level `digest` so it waits for the next digest, no buttons, a link to the plan): "NVDA plan refreshed (price moved 2.3 ATR): now Wait, was Buy. Entry 170–174, stop 165. First target 180." (or "still Wait." when only the numbers moved). Otherwise nothing is said; the new plan is simply there.
- **The record.** A plan closed as `refreshed` never finished, so it is left out of the track record: not a hit, a stop or a run out, not counted as open, not in the odds check or the average result. The plan that replaced it is scored in its own right, from its own date. `plan_record` and the Plans page don't list it among the finished. Migration 0051's downgrade turns `refreshed` plans back into `expired` ones.
- **A plan by hand takes over.** When the user asks for a plan themselves (chat or the web) and has open plans for the same stock with the switch on, the new plan replaces them the same way: it links to the newest (`refreshed_from`), keeps Keep fresh on and takes over its alert setting, and every such plan is closed as `refreshed`. No Telegram message, since they just asked for it. A plan with the switch off stays open, as before.
- **Untracked stocks.** `tracked_symbols` (the stocks the prices, quotes and news jobs fetch) also includes a stock with an open plan with the switch on, so a plan kept fresh for a stock the user no longer holds or watches still gets current prices, quotes and news. The per-run caps (40 price fetches, 50 quotes, 25 news) are unchanged: the rest wait for the next run.

**Likely ranges and plan odds.** All of this is worked out in code (`domain/odds.py`); the model only explains it. It uses the last year of daily moves from adjusted closes (up to 252), and needs at least 60.

- **Likely ranges.** The stock page (the "Likely range" card), `stock_levels` and the plan show where the close could be after 1 week, 1 month and 3 months, two times in three and nine times in ten. Each range comes from the stock's own daily volatility with no drift, so it is centred on today's close and has no view on direction.
- **Plan odds.** Each plan that makes a call gets odds, from 2,000 replays of the plan's window (trading days from the plan's close to its last day). Each replay starts from the middle of the buy zone, or from the close for a stock held, and draws week-long blocks of the past year's moves with their average taken out. The odds show how often each target closed before the stop, how often the stop came first, and how often neither did in time. The replays are seeded by the symbol and day, so the same prices always give the same odds.
- **Where the odds appear.** They are in the plan's `odds` (with `ranges`), the analysts' brief, the "🎲" line in Telegram and the plan page's Odds card. The starting price joins the allowed figures for the number check.
- **Odds check.** The track record checks the odds against what happened: for finished plans that were bought or held and had odds, it compares the average chance given to the first target with how many reached it (`odds_plans`, `odds_said` and `odds_happened` on `GET /api/investments/plans/record`, and the "Odds check" sentence in `plan_record`). Under 10 such plans it says it's too few to judge.

These are base rates from past swings, not forecasts. They ignore news, earnings and gaps between closes.

**Travel department: trips (M11a).** A trip (`trips`, migration 0027) has a destination, first and last day, the currency spent there, and optionally a budget, an amount to set aside each payday and a plan by category, all in the home currency, plus who's going. Up to 50 trips and 120 days each. A trip's spending is found, not filed: confirmed money out in the trip's currency whose local date falls within the trip counts, plus anything added by hand (`trip_links.included`), less anything taken off by hand (`included = false`, which keeps it off even though its date and currency match). Expenses in another currency, such as flights paid at home months before or a home-currency card charge abroad, only count when added by hand. The user's own share counts: the bill less the shares in its splits. Each expense is converted to the home currency at the rate for the day it was spent. The trip page (`/travel/trips/{id}`) has a **Where it goes** section on its Money tab: spent so far and how much of that was before the trip, what's left of the budget, today's spend, the average per day so far, what's left per remaining day, and categories biggest first against what was planned. It's a section to look at; no daily message is sent. After the trip a **Planned against actual** table compares the budget and each planned category with what was spent. **Settle up** lists open IOUs from the trip's split expenses, by person.

Setting money aside needs a pay schedule. Each payday after today and before the trip shows in the cash-flow forecast as an expected outflow (`trip` kind, "Set aside for …"). The trip page says how much should be put aside by now (paydays since the trip was made, at the planned amount), how much by the day before the trip, whether that covers the budget, what each remaining payday would need to be to cover it, and whether the cash-flow forecast to the trip stays above zero with it (the window is capped at 62 days). Nexus doesn't move money: "set aside" is a plan, not a transfer.

**Needs you, in order, and the setup checklist.** `application/home.py` builds the list; `GET /api/home` returns it sorted, and each item carries `when`: `"now"` (urgent), `"today"` (about something today and not urgent) or `"soon"` (the rest). The order is `now`, then `today`, then `soon`; inside each group by department (accounting, investment, travel), and as found inside a department. The older fields (`department`, `kind`, `text`, `link`, `urgent`, `actions`) are unchanged. Every query is the signed-in user's own. The items, by `kind`:

- Accounting (unchanged): `email`, `duplicates`, `budget` (urgent at 100%), `missed_move` (with buttons), `bill` (urgent when due today or overdue).
- Investment, from `market_alerts` (migration 0050) and the earnings dates. **"Today" for these is the New York trading day** (`market_alerts.day` is that date, so it is the one the table keys on; it does not follow the user's own date, and an alert from an earlier day is not shown). `plan_hit`: an alert of kind `plan_entry`, `plan_stop` or `plan_target` today, as "NVDA reached its stop (182.40)", "NVDA reached its buy zone (124.00 to 125.00)" or "NVDA reached its first target (130.00)" (`when` is `now` when the alert is urgent, which is a broken stop on a held stock, else `today`). The alert row doesn't name its plan, so the item links the user's plan page (`/investment/plans/{id}`) and gives the price only when exactly one of their plans for the stock was running that day (dated on or before it and not past `valid_until`) and has that price; otherwise it links `/investment/stocks/{symbol}` and says "NVDA reached its stop". `big_move`: a `big_move` alert today, "AMD −6.2% today" (the change is read back from the alert's text, `domain/alerts.moved_in`), `today`, links the stock. `earnings`: a stock the user holds or watches whose next earnings date (`market_earnings`, a New York date) is today (`today`) or tomorrow (`soon`), "MSFT reports earnings tomorrow". One query each for the alerts, the user's plans (only if a plan alert exists), holdings, watchlist and earnings.
- Travel, from the user's own trips and their bookings on them (the same scope as `next_trip`: a trip someone else shared with the user is not included). Dates are the user's local date; a flight's or train's time is its own local departure time, as in the reminders. `booking_soon`: a flight or train departure (one item per leg, "Flight SQ12 to Tokyo tomorrow 09:40", "Train N700 to Kyoto today 18:30") or a hotel check-in ("Check in at Hotel Sakura today") today (`now`, urgent) or tomorrow (`soon`); a leg that has already left today is not listed, a booking with no trip is not (it is still the `booking` item), and neither are plans. Links the trip. `prep`: a trip starting today or within 7 days with to-dos not done, "3 things to sort before Tokyo", `soon`, links `/travel/trips/{id}?tab=prep`.
- Travel (unchanged): `trip_budget`, `booking`, `settle_up`.

**Setup checklist** (`application/setup.py`; `GET /api/setup`, `POST /api/setup/dismiss`). `GET /api/setup` answers `{dismissed, items: [{key, label, done, link, ask}]}` with four items in this order, each worked out from what the user already has and never stored: `payday` ("Set your payday": a salary schedule is set, link `/accounting/budgets`), `receipts` ("Get receipts in automatically": a Gmail account or forwarding address is connected and working, so one that needs reconnecting is not done, link `/settings/email`), `investments` ("Add your stocks": any holding or watchlist entry, link `/investment`) and `budget` ("Set a monthly budget": any budget, link `/accounting/budgets`). `ask` is one sentence the web can send to the chat to do the step there ("Help me set my payday"). `POST /api/setup/dismiss` (204) records `users.setup_dismissed_at` (migration 0052; null while shown) and is safe to repeat (the first time is kept); the items still come back with `dismissed: true`. Owners and members each have their own; a guest (trip invite) is refused with 403 like every route that is not a trip route, and a signed-out request gets 401.

**Bookings from email (M11b).** The email screen also says whether an email confirms a flight, hotel or train booking (paid or not); the Gmail search and forwarding catch "itinerary", "reservation" and "e-ticket" too. A booking is read by a third model call into flight or train legs (number, from, to, local departure and arrival) or a hotel (name, street address, check-in and check-out). The reader also gives the booking reference (confirmation number or PNR) and where it was booked (the airline, the hotel or an app such as Agoda or Klook). The reference is the user's own: it's shown to them, with a Copy button on the trip page, and is in `trip_status` so "what's my hotel booking number?" works. The reader is told never to give card numbers, PINs, passport numbers or anyone's name, and code hides any card number (15 or 16 digits passing the card checksum, shown as "•••• 1234"), card security code or labelled passport number that still appears (`domain/trips.hide_private`), in every field and in notes. Dates the model writes out ("10 Dec 2026 08:25") are read as well as ISO ones; a booking without any date is dropped. Bookings are kept in `trip_bookings` (migration 0028), one per email. Each lands on the trip whose dates, or the day before, include its first day. With more than one such trip, or none while trips are coming up, a Telegram message asks which (`trip:book:` buttons, up to three trips and "Not for a trip"), and Needs you lists bookings from email that aren't on a trip; the Trips page lets the user put one on a trip or forget it. A booking email with a payment is asked about like any receipt ("a flight booking (ZZ12, SIN → NRT, Thu 10 Dec 08:25), SGD 820.00 at Acme Air on 27 Sep. It's on your Tokyo trip. Log the cost?"); once logged (or matched to an expense already logged), the expense is added to the booking's trip by hand, so it counts whatever its date or currency, and moves if the booking moves. One without a payment is kept as a booking with nothing to log. The trip page's Plan tab lists its bookings on the itinerary, and the Money tab's Where it goes shows what's booked (and how much of it isn't logged yet) and what's still to spend: the budget less what's spent and what's booked but not logged. Deleting a trip keeps its bookings, without a trip.

**Itinerary and notes by hand.** Besides bookings read from email, the user can add itinerary entries themselves, on the trip page (the + sheet's short forms for a booking, a plan or an idea) or in chat (`add_to_itinerary`, `remove_from_itinerary`, which save at once with an Undo button on the user's own trip, and ask to confirm when the entry has a cost or the trip is someone else's; the confirmation is short, the name with its day and time and no street address): a plan (`activity` kind: a name, a day, and optionally a time, place, note and cost), or a flight, train or hotel. They're kept in `trip_bookings` with no `email_id` (migration 0029), up to 100 a trip, and any entry, from email or by hand, can be edited or removed (in chat, `change_itinerary_entry` changes only what the user names, such as a hotel's check-out; a hotel added in chat without dates is taken as the whole trip). On the trip page, a new entry starts on the trip's dates, and a hotel shows on its check-in day and as "Staying at" on each night after it (`POST /api/travel/trips/{id}/bookings`, `PUT`/`DELETE /api/travel/bookings/{id}`). An entry's cost counts as booked until it's logged. The itinerary shows the trip day by day ("Day 3 · Sat 12 Dec"), each day's entries in time order. A trip also has free notes (up to 2,000 characters, set from the trip form, edited in place on the Prep tab (saved with the whole trip as the form sends it, `PUT /api/travel/trips/{id}`) or set with `update_trip`), shown on the trip page and in `trip_status`. Notes and entries keep booking references; card numbers, security codes and passport numbers are hidden, as in bookings from email. A new trip picks up bookings already read (from email or a screenshot) whose dates fall in it.

**A time for a plan added in chat.** A plan `add_to_itinerary` puts on a day with no time (and no end) is given one, so it isn't left last in the day after dinner (`application/day_slots.py`, `domain/itinerary.pick_slot`); a time the user gave always wins, and with `minutes` but no end it gets an end. The time is the first free gap, in the user's time zone: it starts no earlier than now when the day is today, else 09:00 (or, with `after`, the end of the plan named there, a plan with no end taking its category's usual length, plus the way to get there), on the next quarter hour, clear of every timed entry that day, flights and trains included (an overnight flight's landing day counts from midnight until it lands) and hotels not, and ends by 23:00. How long it takes is `minutes` (10 to 600) when the model gives it, else by category: Sight 90, Food 60, Shopping 60, Nature 120, Nightlife 90, anything else 60. Room is left to get to the plan from the entry before it and on to the one after it: the Routes API's time between the two Google places (walking when close, else the trip's usual way, as for a day's hops; a train or flight counts as its station when that's known) when both are linked and Routes is set up, asked for in at most 2 seconds for the whole add; otherwise, or on any error, 15 minutes. If nothing fits, the plan is added as before (last, no time) and the reply says so. The reply and the confirmation (a cost, or someone else's trip) name the time and what it sits before or after. Nothing about confirming or Undo changes: it is the same one add. The plan keeps no `order`, so the day's time order places it.

**Arranging a day.** Plans can be put in the user's own order within a day (`PUT /api/travel/bookings/{id}/move` with `{"day": "2026-12-12" | null, "after": <entry id> | null}`: onto a day right after another entry there, first, or back to Ideas), and in chat (`change_itinerary_entry` with `after`: "put the sushi place after the castle"; it saves at once, with Undo, on the user's own trip, as `change_itinerary_entry` does). Flights, trains and hotel nights stay where their booking puts them. The order is kept on each plan (`order` in its `details`, no migration) and the day's plans are numbered afresh on each move; a plan moved to another day by an edit goes where its time fits there. Until a day is rearranged it runs by time as before (a hotel check-in at 15:00, a plan with no time first); after that, plans keep the user's order, and flights, trains, check-ins and plans added later slot in after the last entry with an earlier time (a plan with no time goes last). A plan with no time that's moved keeps its spot among the timed entries too: the move notes the time of the last timed entry before it (`follows` in its `details`), so a car pickup put right after a 09:15 landing stays ahead of the 15:00 check-in, and a dinner put after the check-in stays after it; giving the plan a time drops the note. The rules are in `domain/itinerary.py`; travel times follow the same order. Plans can also have an end time ("10:00 to 12:30", after the start), any entry a link (a booking page or menu: a public https address only, like research sources), and a place to visit a list ("Eat", "Rainy day"; at most 12 a trip; one saved in chat with an idea's kind, Food or Sight, is filed under it). An edit that doesn't mention the place, end time, link, list or order keeps them. The trip detail gives each day's entries in order with its notes (`days`: clashes, "Tea ceremony (14:00 to 15:30) runs into Castle tour at 15:00" or two things starting together; a plan after a later one in the user's order; three hours or more of free time between 09:00 and 21:00 on a day with anything timed, a plan with no end taken as an hour) and the ideas (places to visit, no day yet) in order (`places_order`); `trip_status` lists the notes in chat. The itinerary shows a day at a time (`web/src/pages/DayCarousel.tsx`): swipe sideways between days (CSS scroll snap), tap a day's pill above them, or use ‹ and › ("2 of 4"); it opens on today while the trip is on, else on its first day. The day open is the page's one day picker: the pills, the swipe, the map and the day view (while the trip is on) all follow it, and it is kept in the address (`?day=`). The day's box is the same height every day (room for three or four plans: 27rem, or up to 34rem and 68% of the screen on phones); a busier day scrolls inside it, fading at the bottom while there's more below. Every day stays on the page, so links, moves and focus reach any day (focus moving into another day brings it into view), and travel times are asked for the day in view and the days either side. On the trip page (`web/src/pages/TripArrange.tsx`, with dnd-kit) each plan has a grip: drag it within its day, onto another day's pill to put it at the end of that day (held there, the day opens, to put it in its place), (a long press on the grip on phones); on the Ideas tab the grip puts ideas in order; dragging only scrolls the page up and down, never across the days; a line shows where it will land, the page shows the new order straight away and the server's once the move is saved, even when that's unchanged (one `move` call per drop). From the keyboard, Space on the grip picks the plan up, the arrow keys step it through every gap (first on each day and after each entry, then Ideas; on Plan the day picker follows it), Space puts it down and Escape leaves it; each step is read out. Tapping a plan opens it in place (address, Google Maps, link, note, reference and **Change**; a second tap folds it; a press that moves more than 8px, or lands while the days scroll, is ignored) and **Change** opens it to change in place, where **Move to…** (or **Add to day** on an idea) opens the day picker, below. Each day shows its notes under its heading, free time with **Find something to do** (the place finder, saving the place onto that day at the free time's start). The entry form has Until for a plan's end time (shown as "14:00–15:30"), Link for any entry (shown as **Open link**, in a new tab) and List for an idea; ideas can be filtered by list once there are two or more (an entry's list, else its kind), and ideas saved from guides go under their kind. The day view, the map's numbers and lines, and the read-only link follow the same order. **Travel days.** A flight or train is on every day one of its legs leaves or lands (`itinerary.on_day`, `days_of`): an overnight flight shows where it leaves on its first day and, on the next, a 🛬 **Land BCN 09:15** line at its arrival time (a later leg of the same booking, like the flight home, shows on its own day). On a day it lands with a hotel check-in at least two hours later, the day's note says so ("Land 09:15, check-in at Hill Lodge from 15:00: 5 h 45 min to fill…"); once the way from the airport has a travel time, the page words it as "Arrive around 10:45 (land 09:15, then 1 h 30 min) · check-in from 15:00 · about 4 h 15 min to fill, or ask about checking in early". That day gets no free-time notes, and neither do days outside the trip's dates (packing at home before an evening flight). The day view shows the landing too; the read-only link lists each booking once, on the day it leaves. Below the itinerary, **Getting around** picks public transport or a hire car for the trip (`PUT /api/travel/trips/{id}/getting-around` with `{"by": "transit" | "car"}`, `trips.getting_around`, migration 0038): with a car, hops beyond walking distance drive. Below it, **Directions open in** picks Google Maps, Apple Maps or Waze for every hop's Directions link, kept in this browser only; Apple Maps and Waze get only the entries' names and addresses as saved on the trip, never coordinates or Google place ids.

**The trip page.** One page for the trip (`web/src/pages/Trips.tsx`, `TripStage.tsx`, `TripIdeas.tsx`, `TripMoney.tsx`, `TripPrep.tsx`): a compact cover (destination, dates, a when-pill, companions, the photo credit) with **Share** (below) and a ⋯ menu for Edit trip, Another photo / No photo and Delete trip, then a **Next up** strip, then four tabs. The words: a **booking** is a flight, stay, train or ticket (it sits at its time on its day and its time isn't ours to move, so it shows a padlock); a **plan** is something to do on a day (a time is optional); an **idea** is a place saved with no day yet. **Next up** (`nextUp` in `TripStage.tsx`) is the one thing to do next, with its button: while planning, the first gap (nights without a place to stay, no flight or train, no budget, each with its one fix), then the first free day ("Day 4 is still free. 3 of your ideas could fill it.", whose button, Find ideas, opens that day's Ideas tab); in the last week the next booking (Open day) or what's left to pack; while the trip is on what's next today; after it, who still owes you (Settle up, which opens Money). Fill it from your ideas, or leave it open." **Tap an entry to open it, then Change** to change it in place: a plan's name, day and time with **More details** (where, link, reference, note, cost), **Move to…** (the day picker: Viewing, then All days with each day's label or "Free day" and how many plans, and **Take it off Day N** to make it an idea again) and **Remove**; a booking opens the same form without Move to…. **Add to Day N** at the foot of each day opens the add sheet on that day. On a wide screen (1024px and up) the pills run down the left, the day is in the middle and the map on the right, and the tab's + is a button beside the tabs; on a phone the + floats (it steps aside while the page scrolls down) and the tab row stays at the top. **Ideas** has a **Find ideas** button at the top, which opens the finder in a sheet (Google Maps, plus guides and articles for a query that asks for ideas; a **Look in** chip picks the whole trip, a stop or near a day, and the results stay listed with a **Saved** mark so several can be kept), the lists as chips once there are two (and **Show planned** for ideas that are now on a day), and each idea as a quiet row with a coloured dot for its list, its name and one line (where it is, its kind, how near a day), and **Add to day**, which opens the day picker ("Put on a day", with **Keep it as an idea**); tapping a row opens its note, a Google Maps link, the rating, **Change** and **Remove**. **Arrange** turns on the grips, to put ideas in order by dragging; an idea can also be moved with the keyboard while it is on. **Money** is a summary card, a **To do** card and a **Details** list. The summary is for the stage: spent and booked against the budget in one bar, with what is planned and what is left (before the trip), spent so far with what's left a day (while it's on), the trip cost against the budget (after it). **To do** (only when someone else is going and there is something to do; first on the page after the trip) has the costs to split and the people to settle with, each confirmed in place. **Details** is one section open at a time: **Where it goes** (spending by category, each opening to its expenses; after the trip, planned against actual), **Planned costs** (the + adds one, a name and an amount; it is saved with `PUT /api/travel/trips/{id}`, sending the whole trip as the trip form does), **Setting money aside** (before the trip), **Bookings paid**, **Expenses** (each with **Take off**), **Paid by others** and **Travellers**; a section with nothing in it is left out. **Prep** is open at any time, however far off the trip is: **Still to sort** (the gaps above), the **Packing list** (suggested, ticked off, added to; the tab's + goes to its add field), the **Weather** and the trip's **Notes**, a text box saved with the Save button or when it's left (the whole trip is sent, `PUT /api/travel/trips/{id}` with `notes`). One + opens one sheet, named for the view it shows, with three choices (**A booking**, **A plan**, **An idea**) each a short form with the rest under **More details** (a booking's kind is one of Flight, Stay, Train, Ticket; a plan has a name, a day and a time; an idea a name and a list, from the chips or a new one typed), and three quick ways: **Type it** (a sentence to Nexus without leaving the trip, sent with the trip's name and dates, so "Thursday" means this trip's; what Nexus reads is shown and anything it changes waits for Confirm, as in the chat), **Screenshot or photo** and **Find a place**. The + on each tab is named for what it does there: Add to Day N, Add an idea, Add a planned cost, Add to packing. The gaps' Add buttons and Next up open the sheet with that kind already chosen. A new trip (the **New trip** button on the Trips page, or Add a trip) asks only where and when: the currency is filled in from the place (`GET /api/travel/currency?place=`, the country from Open-Meteo's place search and a table of countries' currencies in `domain/currencies.py`), and is asked for only when the place or its country isn't known; budget, who's going, set-aside, planned amounts and notes sit under one optional fold. Day labels (`PUT /api/travel/trips/{id}/days/{date}`, `trips.day_labels`, migration 0030), ideas (`trip_bookings.start_on` may be empty, migration 0030) and the chat tools (`add_to_itinerary`, `change_itinerary_entry`, `label_trip_day`, `trip_status`) are as before. Travel has one page, so it shows no tab bar of its own.

**Stops, day names and the Ideas map.** A trip can cross several cities, each day usually has an area or a theme, and ideas get placed on the day that is nearby.
- **Stops.** A stop is a place the trip is in, with the days it is there (`{"name", "start", "end"}`; `trips.stops` JSONB, migration 0044, default empty). Until the user saves their own, stops are suggested from the hotel stays (`domain/stops.py`, `suggest_stops`, returned as `suggested_stops` on the trip detail): a run of stays in the same place is one stop, named by the stay's linked Google Maps place's city, else the last part of the stay's address (postcodes and numbers dropped), else the trip's destination; a trip with no stays is one stop, the destination, over the whole trip. The first stop starts with the trip and the last ends with it. The day one stop ends and the next starts is the **travel day** (shown with a plane, train or arrow on its day pill). Stops show above the day pills with their dates and nights; a tap opens the stop's first day, and the day pills carry a dot in the stop's colour. **Edit stops** (`PUT /api/travel/trips/{id}/stops` with `{"stops": [...]}`, which returns the trip; the chat's trip description names them too) renames, moves dates, adds or removes stops. They are saved from then on and no longer follow the hotels; saving an empty list (the sheet's **Use suggested**) goes back to the suggestions. A saved list must have 1 to 40 characters per name, at most 10 stops, dates inside the trip, in order and not overlapping (one stop's end may equal the next one's start); otherwise it is a 422 with the reason. Moving a trip's dates so a saved stop falls outside them clears the saved stops.
- **Suggested day names.** A day with no label of its own shows a suggestion with a "Suggested" chip, worked out in the page (`suggestLabel` in `TripBits.tsx`) from the day's linked places: the area most of them are in (Google's sublocality, else neighbourhood, else locality, fetched with the place), then the one or two commonest kinds (temples, food, museums, nature, shopping, nightlife) from the place's kind or the entry's category: "Gion · temples & food", "Gion", "temples & food", or nothing. Hotels and flights count for the area but not the kinds. The suggestion is never saved by itself: the pencil opens it pre-filled and saving keeps it as the day's label (`PUT /api/travel/trips/{id}/days/{date}`). A label the user typed always wins, and the suggestion goes.
- **The Ideas map.** With `GOOGLE_MAPS_BROWSER_KEY` set (the same key as the Plan map), the Ideas tab has a **List / Map** switch on phones, and shows the list and the map side by side from 1024 px wide (`web/src/pages/TripIdeasMap.tsx`). Without the key there is no Map option. Each idea with a position (a linked place, or its own pin) is a pin coloured by its list; ideas with no position are listed under the map as "Not on the map: link a place to pin it". Each day with plans on the map has a translucent ring centred on those plans and named like "Day 6 · Gion" (its saved or suggested name); the day open on Plan is stronger. With several stops the map shows one stop's ideas and days at a time, with a switcher. Tapping a pin opens the day picker.
- **Nearest days.** Distances are straight-line (haversine, in `web/src/geo.ts`; the server has the same formula as `metres_between`), worked out in the page from the places fetched for the trip, never stored, and never from road routes: "1.2 km", not minutes. In the day picker, **Closest days** lists the days whose plans are within 15 km of the idea, nearest first, with the distance and plan count; then the day open on Plan, **Free days** in the stop the idea falls in, **In <stop> instead** for the other stops, and **All days**. An idea with no position keeps the old order. An idea's row says "On Day 3" once planned, "Near Day 6 · 1.2 km" when the nearest day's plans are within 3 km, and "Fits free Day 4" for an empty day in its stop.
- **Dropping a pin.** Holding the Ideas map for about half a second drops a pin: a small prompt asks for a name ("Dropped pin" by default), saves it as an idea in the list being viewed (`POST /api/travel/trips/{id}/bookings` with `lat` and `lng`), and opens the day picker for it. A dropped pin is the user's own coordinate, so it is stored: `lat` and `lng` live in the entry's `details` (no migration), only on a plan with no Google Maps place (validated as a real position; they are dropped when a place is linked, since the place then has its own), and come back on the booking as `lat` and `lng`. They are the only coordinates Nexus stores. Google's coordinates are fetched with each place and never kept.
- **Area and city.** `Place.area` and `Place.city` come from the place's `addressComponents`, asked for in the search and detail fields (billed in the same tier as the address, so no extra cost), and are fetched with the place like the rest: nothing about them is stored.


**Sharing a trip.** **Share** on the trip's cover makes a read-only link for companions (`POST /api/travel/trips/{id}/share`, `{"renew": true}` for a new one, which stops the old; `GET` to see it, `DELETE` to stop sharing; one link a trip, `trip_shares`, migration 0036). The sheet says what the link shows and never shows, and has the bookings setting (see Share settings). Whoever opens `/shared/{token}` sees the trip without signing in (`GET /api/shared/trips/{token}`, the cover from `/api/shared/trips/{token}/photo`): the cover (a photo with a "Shared with you · read only" chip, the title and one line of dates and stops) and its credit, one card a day ("Day 2 · Wed, Nov 11", the label or stop in the serif, rows with a time column) with "Free day" on an empty one, flights and trains with their times, places to stay with addresses (unless bookings are hidden), and plans with times and addresses, each with a Google Maps search link; while the trip is on it opens at today. It never shows prices, the budget or spending, booking references or where something was booked, notes, ideas without a day, or who's going, and nothing on it can be changed. A link that's wrong, replaced or stopped says it doesn't work any more. Views are rate-limited per link (60 a minute, 2,000 a day). Its foot says that no money, booking references, notes or travellers are shown. Deleting the trip deletes its link.

**Travellers, splitting and settling up.** The trip page's Money tab keeps the money between the user and the people they travel with. Nexus never moves money here: everything below only records what the user says happened.
- **Travellers.** The people going are the trip's `companions` (names only, up to 12; "You" is always in it). The Money tab's Travellers section (in Details) adds and removes them (saved with the same `PUT /api/travel/trips/{id}`); the trip form's "Who's going" is the same chip field. Nothing links a traveller to another Nexus account.
- **Split costs evenly** (`trips.split_evenly`, default on, migration 0045; `PUT /api/travel/trips/{id}/split-evenly` with `{"on": true|false}`). The switch is in the Travellers section. With it on and another traveller on the trip, the To do card says "N costs to split", and **See costs** lists **To split**: the trip's own expenses (money out, not repayments) that aren't split yet and weren't marked **Just mine**. Nothing is split until the user says so: **Split** on a row splits that cost, and **Split** beside the count (named Split all evenly) asks first, in the card ("Split 6 costs (SGD 2,140.00) evenly with Alex and Sam? Each share is about SGD 356.67.", with **Split evenly** and **Not now**) and then splits every row. Both go through `POST /api/travel/trips/{id}/split` with `{"transaction_ids": [...]}` or `{"all": true}`, using the same equal split as chat (the user's share comes first and takes any leftover cent), so "owes you", budgets and "your share" keep working. A cost that became split meanwhile is skipped and reported. With the switch off, nothing is offered; a bill can still be split in chat.
- **Just mine.** `POST /api/travel/trips/{id}/keep-mine` with `{"transaction_ids": [...], "keep": true}` keeps costs out of To split (`trips.not_split`, a list of transaction ids); `"keep": false` offers one again (a kept cost shows a Just mine tag in the Expenses section, with Offer again). Splitting a cost takes it off the list. A cost recorded by settling up is added to it, so it is never offered.
- **Someone else paid.** The + on the Money tab asks "A planned cost" or "Someone else paid" once someone else is going; the payment is listed in the Paid by others section. The payment (`trip_paid_by_others`, migration 0045; `POST`, `PUT` and `DELETE /api/travel/trips/{id}/paid-by-others[/{payment_id}]`) has who paid (a traveller), the amount, currency, what it was for, the date, and who shares it (everyone by default; the user is always in it). **Your share** is the equal share of the bill (rounded like a split, the user first) and is what the user owes them. It does not touch the ledger or the trip's spending: the user hasn't spent anything yet. A settled payment can't be changed or removed.
- **Balances.** Each person has one balance: what they owe the user (open IOUs on the trip's expenses) less what the user owes them (open shares of what they paid), each converted to the home currency at today's exchange rate and netted per person, matching names the way splits do (case and spacing aside). "Alex owes you SGD 768.00" or "You owe Sam SGD 40.00"; opening a row shows the items behind it. If a part has no exchange rate yet there is no single total, so each currency is shown side by side rather than guessed. The trip detail carries `to_split`, `paid_by_others`, `balances`, `just_mine`, and the older `owed`. After a trip, the Next up strip says who is left to settle with.
- **Settling up records, gross not net.** **Settle up** on a person's row in To do asks first, in the card ("Settle up with Alex", with **Mark settled** and **Not now**) and then calls `POST /api/travel/trips/{id}/settle` with `{"person", "log"}`. It records each item separately rather than the net amount: each of their open IOUs on this trip is marked paid back, which records the money in, exactly as marking an IOU repaid anywhere else does; and each open payment they made is marked settled. When the user owes them something, **Also record my share as spent** (`log`, on by default) also records the user's share of each as an expense out, dated the day it was paid, in Travel and counted towards the trip; off, the payment is marked settled and nothing is added to spending. The checkbox is not shown when they only owe the user. The status says what was recorded ("Settled with Alex: 2 IOUs from Alex marked paid back, SGD 768.00 recorded as money in; 1 payment you owed Alex marked paid, SGD 40.00 recorded as spent."). It is safe to repeat: what is already settled is left alone. Nexus doesn't send or receive any money; the user pays each other back outside it.
- **In chat.** `split_trip_costs`, `they_paid` and `settle_up` do the same (the first two and settling with a person ask for confirmation; `settle_up` without a person only reports who owes what).

**Share settings.** The share sheet (above) has one setting, **Show bookings (flights, stays, tickets)** (`trip_shares.show_bookings`, default on, migration 0045). It is chosen before the link is made (`POST /api/travel/trips/{id}/share` with `{"show_bookings": false}`), and can be changed on a link that exists with the same call; a call without it, and a new link from "Make a new link", keep the choice, and a link made after stopping starts with bookings shown. With it off the shared page leaves out flights, stays, trains and anything with a booking reference or a place booked (the user's own plans, ideas and days stay), says "Bookings aren't shown on this link.", and a day only a hidden booking falls on reads "Travel day" rather than "Free day". What is never shared, whichever way the setting is: money (prices, the budget, spending, who owes whom), booking references and where something was booked, notes, packing, who's going, and ideas without a day. The sheet says so: "Shows the days, plans and ideas. Never money, booking references, notes or who's going."

**Screenshots of bookings and plans.** A photo sent in Telegram is read as travel when its caption says so ("my hotel booking", "itinerary", "flight", "tickets") or when the receipt reader marks it as a booking confirmation, ticket or itinerary; the trip page also has **From a screenshot**. A separate reader (`agent/trip_reader.py`, the photo model with reasoning off: 6 to 9 seconds a screenshot, against 13 to 20 with it on, and as accurate on the evaluation screenshots) lists every entry in the image: flights with their legs, hotel stays, trains and plans (tours, tickets, restaurants), each with dates, times, address, reference, where it was booked, price and a short note; dates without a year are the next one from today. Entries without a date are dropped. Each lands on the trip whose dates include it (from the trip page, on that trip), or the user is asked which with the usual `trip:book:` buttons (at most three questions a screenshot); with no trip on those dates they wait under Trips until a trip is made. An entry already on the itinerary (same kind, first day, title and reference) isn't added twice. A price is kept as the entry's cost, counted as booked but not logged. The image isn't kept. `POST /api/travel/trips/{id}/screenshot` (base64 PNG, JPEG or WebP, up to about 10 MB, rate-limited like imports) returns what was added. Sent in Telegram, the reply has an Undo button when any entry landed on a trip; Undo takes those entries off again (`record=` on `add_from_screenshot`, one batch for the screenshot). The web endpoint records nothing.

**Trip research (M11c).** "I want to go to Japan in January": the chat first asks, in one message, what it doesn't know or remember (how flexible the dates are, who's going, a budget or "estimate it"), then `research_trip` starts a Travel department run (`travel.research`) of four steps, with progress and Cancel in one Telegram message like any run:

1. **When to go (web).** Weather, holidays, peak and pricey dates, festivals and events for the month or dates given.
2. **Costs (web, plus live prices).** With `SERPAPI_API_KEY`, one Google Flights search (when the home and destination airports are known) and one Google Hotels search for the dates priced, in the home currency; then a web search for flights, hotel ranges by area and a daily spending guide.
3. **Where to stay (web).** Areas to stay, things worth doing in each, and getting around.
4. **The budget (code).** An estimate from the typical sourced range of each kind (the middle one when sources give budget, mid-range and luxury): return flights per traveller, a hotel room per night (two people a room), daily spending per traveller per day, plus one-offs; prices in other currencies at today's reference rate. The budget is the user's own or the estimate's top rounded up to the next 50; with a pay schedule, what to put aside on each payday before the trip, and whether the cash-flow forecast to the trip (capped at 62 days) stays above zero with it.

Flexible dates are priced as a week from the 10th of the month (next year's if it has passed). The web steps are quarantined: the search gets only the question, never anything of the user's, and has no tools. A second call with no web and no reasoning (a few seconds) sorts the results into tagged lines that code parses, told that the quoted text is data, not instructions. Then code keeps only what traces to a fetched source: a price must cite a source that was actually returned and have sane figures and a currency, and when the page's text came back, both its figures must be written on that page and an area must be named on it; sources must be public https addresses (no IPs, internal names, credentials or odd ports); and any sentence quoting a price (a figure written with a currency) that no source gave is dropped. Nexus fetches no pages itself and submits nothing. The result is kept on the run; the Telegram message gives when to go, the costs with their source numbers, where to stay and the budget card, with a **Make it a trip** button (`trip:research:`), which saves a trip with the dates priced, the currency there, the budget and the set-aside (once; a second tap finds the same trip). On the web, research runs are listed on the Trips page and each opens at `/travel/research/{id}` with every citation linked and a Sources list with the date each was checked (`GET /api/travel/research/{id}`, `POST …/trip`). A run is capped at US$0.30 of searches and model calls (within the department caps), and at 30 research runs a user a month, which keeps SerpApi within its free 250 searches. Without OpenRouter configured, research is off.

**Web search (shared).** Everything that asks the web goes through one search (`application/web_search.py`). With `TAVILY_API_KEY`, it's Tavily: a basic search (one credit) returns the top five results with each page's main text (cleaned to plain text, up to 20,000 characters a page), so Nexus fetches no pages itself. The sorting model reads the first 5,000 characters of each page; the checks use the whole of it (`domain/evidence.py`: names match ignoring case, accents and punctuation; figures match however they're written, "1,200", "8 000" or "15k"). Answers are kept in `web_cache` (migration 0037), shared by all users since the pages are public and the questions carry nothing of anyone's, so the same question twice costs one search: for a day, or for news from today ten minutes and from this week an hour (see **Looking things up from chat**). Credits are counted a month in `web_credits` and shared out of `TAVILY_MONTHLY_CREDITS` (default 1,000, the free plan), with 5% held back: travel 60%, investment 25%, general 15%. When a product's share is used up, Tavily fails or there's no key, the search falls back to OpenRouter's web plugin (`TRAVEL_RESEARCH_MODEL` or the main model, five results, about US$0.01 a search), which returns an answer and links but no page text; the checks that need a page then don't apply. The free plan stops at its allowance rather than charging, so the share-out only keeps one product from using up another's. The logs give each search's provider, time, sources, pages read and credits, never what was searched for. Trip research, quick ideas and chat's `web_search` use it.

Pages can also be read by address (`KeptReader`, Tavily's extract endpoint: a basic read costs one credit for every five pages it reads, and nothing for a page it can't read). Each page is kept a day in `web_cache` like an answer, a page that wouldn't read as well, so it isn't tried again on every plan; credits count against the product's share, and past it nothing new is read. Without `TAVILY_API_KEY` nothing is read by address. Research plans use it for their news (see Research plans above).

**Looking things up from chat.** `web_search` (`application/web_lookup.py`) is offered on every turn, for current facts the app doesn't hold ("what's the day-tripper fee for Venice?"), and answers in about 10 seconds. One search (general's share, kept a day unless it is for recent news: see below) is read by the research model with no tools and nothing of the user's (`TRAVEL_RESEARCH_MODEL` or the main model, no reasoning), which answers in at most five sentences citing the numbered pages; it reads the first 4,000 characters of each. Code then drops any web address written in the answer and citations of pages that weren't found, and, with the pages, keeps a sentence that gives a figure only when a page it cites has every figure in it. Only public https pages it cites are listed as sources. From the fallback search (no page text) its own answer is used, without the addresses. The agent is handed it as quoted data and asked to say where it came from. The tool asks the agent never to put the user's own details in the question. Five lookups a minute and 20 a day per user.

**Searching for what's happening now.** `web_search` takes two optional arguments for anything happening now or today (a protest, a strike, transport disruption, a closure, a weather warning, an event tonight). The agent is told to use them (a rule in `agent/graph.py`, a bullet in the trips skill) and to name the city or area in the question.

| Mode | Tavily request | Answer kept | Credits |
|---|---|---|---|
| default | `search_depth: basic`, no `topic` | 24 hours | 1 |
| `recent: "today"` | adds `topic: "news"`, `time_range: "day"` | 10 minutes | 1 |
| `recent: "week"` | adds `topic: "news"`, `time_range: "week"` | 1 hour | 1 |
| plus `local_query` | the same, run a second time with the question in the local language, at once | as its `recent` | 2 |

- **Local language.** Local news is written in it (Spanish or Catalan in Barcelona), so the agent gives `local_query`, picked from the user's current time zone or the trip's destination. Both searches run together (`asyncio.gather`) and their results are merged in turn (so neither crowds out the other), repeats dropped by address, and at most 8 pages are read in all (`MAX_MERGED`). If only one of the two fails, the other answers. A `local_query` that is the same words as the question, or under three letters, is dropped before searching.
- **Dates.** News results carry Tavily's `published_date`. The tool lists each source as `[2] Title (published 2h ago / 2026-10-24 17:40): url`, with the time in the user's zone and "ago" worked out from the time of the turn, and tells the agent to say when the sources were published. If no source it cites is dated within the day (or week) asked for, it says so and tells the agent to say plainly that nothing from then was found and not to present older pages as current. The same goes for an answer with no sources at all. Pages the provider gives no date for are listed without one.
- **Cache.** The key includes `recent` and `local_query` (a plain search keeps its old key), so a news search never answers a plain one or the reverse. Pages that came with a search are kept inside its answer, so they expire with it. `KeptReader.read(urls, recent=...)` keeps a page read for a news search under its own key for the same short time, so fresh news is never served from the day-long page cache.
- **Credits.** A `local_query` costs a second search: the credits the provider reports are added up (normally 2) and counted against general's share. With fewer than two left the main question is still asked and the local one is skipped (logged, not an error); with none left, or if both fail, the OpenRouter fallback answers the main question alone. That fallback can't filter by date and returns no publication dates, so its answers are marked as undated and the agent is told not to call them current.

**Quick ideas.** "Where should we eat in Osaka?", "best ramen", "rainy day in Seoul": `find_ideas` in chat and `GET /api/travel/trips/{id}/ideas?q=` on the web (`application/ideas.py`). One web search (as above, travel's share) and the destination's Wikivoyage guide (`infra/guides/wikivoyage.py`: its See, Do, Eat, Drink and Buy sections, from `prop=extracts`, no key, kept in memory a day; the first place in "Tokyo, Kyoto") are read together, in about 10 to 20 seconds. The sorting model (no tools, nothing of the user's; told the pages are data) lists up to 10 named places with an area, a kind (Food, Sight, Shopping, Nature, Nightlife, Museum, Activity), why in the source's words and the source number. Code keeps a place only when its source was returned and is a public https page, and the page's text (or, from the fallback search, its written answer) names it; repeats are dropped and at most 8 kept. Each is then matched to Google Maps when that's set up (the top result, only when it shares a real word with the name); one Google says has closed for good is dropped. Nothing is saved until the user picks one: on the web, **Find a place** in the + sheet (and the Find ideas button at the top of the Ideas tab, which opens the same finder in a sheet) searches Google Maps at once and, for a query that asks for ideas ("best", "where", "rainy", "cheap eats", four words or more), reads guides and articles alongside, merged into the same list as they come in (see **Finding by stop, day or theme**); a name ("Ichiran") goes to Google Maps alone, with a button to ask for ideas too. Each idea shows its source as a link (`rel="noopener noreferrer nofollow"`), and **Save to Ideas** keeps it as an idea, with its Google Maps place when matched. Wikivoyage text is CC BY-SA and credited by its link. Six searches a minute and 40 a day per user. Without travel's web search (no OpenRouter), ideas are off and the trip page shows Google Maps search only.

**Finding by stop, day or theme.** A search can look in the whole trip, in one of its stops, or round one day, and can start from a theme. Both searches (`GET /api/travel/places/search` and `GET /api/travel/trips/{id}/ideas`) take the same two optional parameters, which need the trip (`trip_id` on the place search) and give a 422 otherwise: `stop`, one of the trip's stops (as saved, or as its stays suggest; matched ignoring case and extra spaces), and `day`, an ISO date inside the trip (and inside `stop` when both are given). The work is `search_scope` in `application/places.py`, shared by the web routes and the chat tools.
- **Whole trip.** Today's behaviour: the trip's destination goes in the search text.
- **In a stop.** The stop's name replaces the destination in the text, for Google Maps and for quick ideas alike. The web offers "In <stop>" only when the trip has two or more stops, and begins on the stop of the day open on Plan.
- **Near a day.** The text is the day's stop with, when its places agree, their most common area ("Gion, Kyoto"), and Google Maps also gets a **location bias**: a circle of 2 km round the middle of that day's places (the plans linked to a place, from their Google coordinates, and the user's own dropped pins). Google treats it as a lean, not a limit, and a place named in the search still wins; it changes no billed field. The circle is worked out when the search is made, from details already fetched for the trip (`places.many`, the same in-memory cache), and is **never stored**: not in the database, and only the usual short in-memory cache keeps the answer. A day with nothing planned has no circle and is searched by its stop alone. The places cache keys a biased search on the circle, rounded to about a hundred metres, so the same place with a different bias is a different search. On Plan, each day's **Find ideas near here** opens the finder on "Near Day N", and its results can be saved as ideas or **Add to Day N** (the same plan the free-time prompt makes, with no time).
- **Themes.** Food, Sights, Museums, Nature, Shopping, Nightlife and Rainy day are chips that fill the search box ("Best food", "Rainy day") and run it. Each phrase asks for ideas, so guides are read too. What is then saved goes in a list named after the theme; with typed text it goes under the guide's kind (Food, Nightlife…) as before. Changing the scope runs the same search again.
- **Merged results.** The web shows one list, **Results**, with each place once (`mergeResults` in `web/src/pages/TripFind.tsx`). Google's results come first; guide ideas join as they arrive ("Looking in guides…" shows meanwhile). A guide idea for a place Google already listed (the same place id, else the same name ignoring case, accents and punctuation) joins that card, which keeps the rating and adds the guide's words and source link. Each card is tagged **Google Maps**, **From guides** or both. Without Google Maps set up, only guide ideas show; link mode (finding a place for an entry) is Google Maps alone.
- **The credit rule is unchanged.** Google results are instant; guides are read only for a query that looks like it wants ideas, or when asked ("Ideas from guides and articles"), so a name search costs no web credit. The same six a minute and 40 a day apply to guide searches, scoped or not, and the Google Maps caps (60 a minute, 200 a day, cached and shared answers free) are unchanged. A scope or a theme never adds a call by itself.
- **In chat.** `find_places` and `find_ideas` take optional `stop` and `day` ("find ramen near day 3 of my Japan trip", "things to do in Kyoto"), resolved by the same `search_scope`.

**Research areas into ideas.** A trip's research lists areas, each with things worth doing. The research page (`web/src/pages/Research.tsx`) has one primary, **Make it a trip** (a soft **Open the trip** once there is one), an **Estimated cost** card first (the range, the nights and travellers, "Fits your budget of …"), then when to go, **Costs**, where to stay and getting around, and the sources shut behind **Sources · N**. The Trips list shows research under the trips, and past trips under one shut **Past trips · N** button, below everything else. **Where to stay** on the research page has a "Save its ideas" box per area (all ticked), and the ticked areas' things can go onto a trip in two ways: straight after **Make it a trip** (a card asks "Add the ideas from these areas to the trip too?", **Add** or **Not now**), or with **Add to a trip…**, which lists the user's upcoming and ongoing trips. Both call `POST /api/travel/research/{run_id}/ideas` with `{"trip_id", "areas": [names]}` (`ideas_from_areas` in `application/travel_research.py`), which returns `{added, skipped, stop_suggestion}`; the page says "Added 9 ideas to Japan in spring (2 were already there)" and links to the trip's Ideas tab. The trip must be the user's and not over (404, 422); an unknown area is a 422, and at most 10 areas go at once.
- **What is saved.** At most 4 things per area, each an idea (an activity with no day) filed under a list named after the area (up to 30 characters), so they group on the Ideas list and map. A thing whose name matches an idea already on the trip (ignoring case and spaces), or that the areas name twice, is skipped and counted; so repeating the call adds nothing.
- **Google matching.** Each thing is looked up on Google Maps ("thing, area, destination") with the same `same_place` check quick ideas use, and keeps the place id only when one result clearly is it; anything else is saved by name alone. It uses the normal Google Maps caps, at most four lookups at once, and on a limit or an error the idea is saved unmatched, so Google being down never loses an idea.
- **The stop offer.** Areas never overwrite stops. When the research's place is none of the trip's destination or stops, the answer carries it as `stop_suggestion` and the page asks "Add Tokyo as a stop for <dates>?", showing what that would change ("Osaka would end on Sun 10 Jan") before anything is saved. Accepting saves the stops through `PUT /api/travel/trips/{id}/stops`: the research's dates clipped to the trip, the new stop kept whole, and each stop it overlaps made room (one that starts before it ends on its first day, one that ends after it starts on its last, one that is split by it becomes two, one inside it goes). When the dates don't fit the trip, or the result would break the stops rules (ten at most, in order, no overlap), the offer is left out or says so, and the stops can still be edited by hand. Nothing is changed without the click.
- **In chat.** `research_to_trip(run, trip, areas?)` does the same and asks for confirmation like other trip changes; the ideas it saves are recorded for Undo.

**Google Maps places.** With `GOOGLE_PLACES_API_KEY` (Google's Places API (New), in a Google Cloud project with billing on), trips show Google Maps data for plans, ideas and hotels; without it, none of this appears and nothing else changes.

- **What's stored.** Only the Google place id, as `place_id` in the itinerary entry's `details` (no migration). Ratings, hours, summaries and reviews are fetched when shown and kept in memory for 30 minutes, as Google's terms allow; they're never written to the database.
- **Linking.** `add_to_itinerary` matches a plan or hotel by name: it takes the top search result for the name (plus address and destination) only when the two share a real word, and the reply names the place it matched only when its Google Maps name differs from what was asked ("matched <name> on Google Maps"), never its address. The user can pick one from `find_places` instead (`google_place`), or link, change or unlink it on the web ("Find on Google Maps", "Not this place"). Edits that don't mention the place keep it. Flights and trains aren't linked.
- **In chat.** `find_places` searches near the trip's destination, one of its stops or a day (five results, with rating, price level and address). `place_info` gives one place's rating, regular hours and up to five reviews. Review text is other people's words: it's cleaned, angle brackets are replaced, and it's shown to the model inside `<reviews>` as quoted data.
- **On the web.** Each linked entry shows its rating, price level, a Google Maps link and a Details panel (summary, regular hours, reviews credited to their authors, "From Google Maps"). The Ideas tab has a Find ideas button (a sheet) to save results. `GET /api/travel/places/search?q=&trip_id=&stop=&day=`, `GET /api/travel/places/{id}`, `GET /api/travel/trips/{id}/places` (details for linked entries, with warnings) and `PUT /api/travel/bookings/{id}/place` (`{"place_id": null}` unlinks).
- **Warnings.** These come from Google's regular weekly hours, worked out in code (`domain/places.py`): "Usually closed on Thursdays" for a plan on a day the place doesn't open, an "Open 11:00 to 22:00…" note when the planned time falls outside its hours, and Google's temporarily or permanently closed status. Holiday hours aren't covered, and the skill says so.
- **Cost guard.** Searches ask only for the fields shown (Google bills by field). Lookups that reach Google are capped at 60 a minute and 200 a day per user; cached answers don't count. The minute window leaves room for a trip page and its map to load cold (after a deploy, when the 30-minute in-memory cache is empty); the daily cap is what bounds the bill. Views asking for the same place at the same moment share one Google call, counted once. A trip page looks up at most 30 linked places; when the limit is hit part way, it stops starting lookups, shows what it has and logs one warning line (asked, got, skipped for the limit) instead of one per place. Photos keep their own cap (60 a minute so a page's thumbnails can load cold, 100 a day). If Google fails, places are left out and entries are added unlinked.
- **Coordinates.** Searches and details also ask for each place's location (in the fields already billed), so the trip page can put linked places on a map: `lat` and `lng` on each place in the API. Like the rest, they're kept in memory only, never stored (Google allows coordinates to be kept only for a while). The one exception is a pin the user drops on the Ideas map: that is their own coordinate, not Google's, so it is kept (see **Stops, day names and the Ideas map**).
- **Travel times.** Between a day's stops, from Google's Routes API with the same key (its Google Cloud project needs the Routes API turned on; without it, hops come back without a time). A day's stops are its plans and hotels linked to a place, in itinerary order (by time, a hotel check-in at 15:00), from the hotel slept in the night before to the one slept in that night; a flight, a train or a plan with no place breaks the chain (`domain/routes.py`). A hop up to 1.5 km apart in a straight line is walked, a longer one (or one whose distance isn't known) goes by public transport, and driving when public transport finds no route; the user can ask for one hop another way. A hop is flagged as tight when it takes longer than the time between the two plans' start times. Only the two place ids are sent, asking for the duration and distance only (driving without live traffic, the cheaper kind). Answers are kept in memory only, for 30 minutes, like place details (Google content is never written to the database); calls that reach Google are capped at 60 a minute and 300 a day per user, and only a call that really reaches Google counts (an answer from memory doesn't), and a day has at most 12 hops. `GET /api/travel/trips/{id}/days/{day}/hops` and `GET …/hops/{start}/{end}?mode=walk|transit|drive`, each hop with a Google Maps directions link. A flight or train adds the airport or station it leaves from (the last stop before it) and the one it lands at (the first after it): each is looked up on Google Maps once by name ("BCN airport", "Kyoto station"; the first result whose kind or name says airport or station), and only its place id is kept on the booking (`stations` in its `details`; "" when Google had none, so it isn't asked again; a failed lookup is tried next time), kept across edits like a plan's place. The way picked for a hop is kept for the trip (`trips.hop_modes`, by the two entries' ids, at most 200) and used again in place of the default; without one, a hop beyond walking distance goes by public transport, or by car on a trip with a hire car, except on the way to a plan named as picking the car up or on from one named as handing it back ("Car pickup", "Car return — Barcelona Airport T1"; `without_the_car`), which go by public transport. The map shows the airports and stations too (✈ pins on the days they're used, in the route line from the airport to the hotel). A hop between an airport and a place within 3 km of it (a hire-car desk, an airport hotel) is part of being at the airport: it's marked (`beside_airport`), never sent to Google, and not drawn, and the arrival note counts the way to the hotel from that place. On the trip page each hop shows above the stop it goes to; one back to somewhere earlier on the day's list (tonight's hotel, checked into before going out) shows at the end of the day as "Back to Colectia Stays · 25 min by public transport". Each hop shows ("14 min walk · 940 m", Tight when it is), with a Walk / Transit / Drive choice for that hop and a Directions link; a day's times are asked for only once the day scrolls near the screen.
- **The map.** With `GOOGLE_MAPS_BROWSER_KEY` too (a second key, for the Maps JavaScript API only, limited in Google Cloud to the app's address, since the page sees it), the trip page shows a Google map (`web/src/pages/TripMap.tsx`; the script is loaded once, `web/src/maps.ts`): beside the itinerary on wide screens (sticky while it scrolls), a card above it on phones with **Full screen**. Every linked plan, hotel and place to visit with coordinates is a pin: plans numbered as on their day, hotels H, ideas grey with no number; pins take their day's colour from a fixed palette of 8, repeating. The map shows the day open on Plan (the page's one day picker) with its route as a line, from last night's hotel through the plans to tonight's (the same order as the travel times), so picking a day in the pills changes the map's day; the **All days** button on the map shows every pin, and **This day** goes back to the day open beside it. While a trip is on, Plan opens on today. Tapping a pin scrolls to its entry. Without the browser key there's no map and travel times still show; the server's Places key is never sent to the page, so a browser key set to the same value is ignored (the startup log warns); if Google refuses the key, the card says the map couldn't load. Google's terms don't allow Places data on another provider's map, so it's Google's map rather than OpenStreetMap. The content rules allow Google's map script and image hosts and inline styles (the map adds `<style>` elements; scripts stay strict), and pages other than shared trip links send other sites their origin only (`strict-origin-when-cross-origin`), which Google checks against the key; a shared link still sends nothing. Map loads are billed per page view: a trip page loads it once, and Google's free monthly allowance covers personal use.

**Kept answers (`external_cache`, migration 0061).** Trip weather from Open-Meteo is kept in Postgres for as long as the in-memory caches in front of it keep it (places 30 days, forecasts 3 hours, past years 7 days), so the first look after a deploy doesn't pay for the outside service again. The table is `external_cache(key text primary key, kind text, value jsonb, expires_at timestamptz)`, shared by all users and with no row-level security (like `web_cache` and `fx_rates`, it is in `SHARED` in `application/user_data.py`, so it is neither exported nor erased; the app's role gets it from 0056's default privileges). `key` is a SHA-256 hash of the kind and what was asked (coordinates and dates, a place name), never a user id; `value` is only the answer. The order of a lookup is memory, then the database, then the outside service; a value read from the database goes back in memory for what is left of its time. `application/external_cache.py` (`KeptAnswers`) never raises: a database that is down, slower than 1.5 seconds, or holding something unreadable is logged as a warning (`couldn't read a kept … answer`, `couldn't keep a … answer`) and the lookup carries on as if nothing were kept. Expired rows are never read (`expires_at > now`) and up to 200 are deleted each time one is kept, as for `web_cache`. To drop everything kept (a bad answer, a changed provider), `DELETE FROM external_cache`. Nothing from Google goes in it: Google's terms limit storing Maps content, so place details, coordinates and travel times stay in memory only.

**Trip header photos.** Each trip shows a famous, recognisable view of the first place it goes ("Tokyo, Kyoto" and "Japan and Korea" use Tokyo and Japan), in the season it goes, found once per place and season and shared by every trip there (`destination_photos`, migration 0033; `trips.photo_id`). The `travel.photos` job runs every 30 minutes and soon after a trip is added or changes where or when it goes; it gives up to 3 trips a photo per run. How one is found (`application/destination_photos.py`): Wikipedia's article for the place gives its latitude, and so the season (flipped in the south; one year-round photo inside the tropics); the small model (`MEMORY_MODEL`, else the main model) names three famous sights there; their articles' photos are gathered (each article's lead photo and photos whose name or caption names the season, such as "Kiyomizudera_Snow.JPG" or "November"); only wide (1.2:1 to 2.6:1), large (1200px+), freely licensed (CC BY, CC BY-SA, CC0, public domain) JPEG, PNG or WebP photographs with an author qualify; and the photo model (`OPENROUTER_VISION_MODEL`) picks the best of up to four 500px previews, or none (never maps, flags, paintings, old photos, interiors or close-ups of people). The pick is kept at 1280px in the database with its author, licence and Commons page, and the trip page credits it ("Photo: <author>, <licence>, via Wikimedia Commons", linking to the photo's page) as the licence asks. When nothing suits, that's noted and the place isn't searched again for that season for 30 days; meanwhile the trip shows the place's photo from another season, or a plain gradient. If Wikipedia doesn't answer (it rate-limits busy addresses with 429), the trip is tried again after 6 hours. Requests carry a User-Agent naming the app and repo, as Wikimedia asks; no key is needed. Photos are served from `GET /api/travel/photos/{id}` (signed in, cached by the browser for a year: a photo never changes) because the web app's content rules allow images only from its own origin. Google Places photos aren't used: Google's terms don't allow storing them. Only the place's name and the season are sent to the models. Up to three runners-up are kept with each pick (`destination_photos.rank`, migration 0034: 0 is the pick), so the cover's **Photo** menu can switch to **Another photo** (the place's photos in turn, this season's first, then other seasons') or **No photo** (`trips.photo_off`, a plain gradient; the photo job then leaves the trip alone), and back. `POST /api/travel/trips/{id}/photo` with `next`, `off` or `on`.

**Trip weather.** The trip page shows the weather for the first place a trip goes, from Open-Meteo (no key; CC BY 4.0, credited on the page): the forecast for the trip's days once the trip is within 16 days, and before that what the same dates were like, averaged over the last three years (mean high and low, the share of years it rained as the chance of rain, the most common weather). Places are found with Open-Meteo's geocoding by name. Answers are kept in memory and in the database (`external_cache`, migration 0061, see **Kept answers**) for the same time (places 30 days, forecasts 3 hours, past years a week), so a deploy doesn't empty them; a place is kept under a hash of its normalised name, a forecast or past years under a hash of the coordinates and dates. If Open-Meteo doesn't answer, the card is left out. Only the place's name and coordinates leave. `GET /api/travel/trips/{id}/weather`.

**Day panel.** One day of a trip in one panel, for use while travelling (`web/src/pages/Trips.tsx` and `TripDayHead.tsx`, from the trip's own data, nothing new on the server): the day's heading, its weather, where they're sleeping that night (**Maps**, **Copy address** for a taxi driver, and under a fold the address, check-out date and the booking reference with Copy) and the day's flights, trains, check-ins, check-outs and plans in time order, which are the editable itinerary list: a plan opens to its address (with Maps and Copy), note and reference. There is no separate read-only card for the day. While a trip is on, Plan opens on today. Maps links are plain Google Maps searches for the place's name and address, which open the Maps app on a phone.

**Packing list.** Each trip has a packing list (`trips.packing`, migration 0034: up to 80 things, 60 characters each, each once), ticked off on the trip page. **Suggest** adds the usual things for a trip like it that aren't on the list yet, worked out in code (`domain/packing.py`): a passport, adapter, insurance details, local cash and an eSIM when it's spent in another currency than the home one; clothes for its length; warm layers, gloves, sunscreen or an umbrella from the weather when it's known, else the season (the tropics count as hot and wet). Card and passport numbers are hidden as in notes. `PUT /api/travel/trips/{id}/packing`, `POST /api/travel/trips/{id}/packing/suggest`.

**Itinerary photos.** With Google Maps places set up, a plan, place to visit or hotel linked to a place shows Google's first photo of it as a thumbnail, credited to its author ("Photo by …, Google Maps", linking to them), on the itinerary and the stay card. The photo is fetched through our API (`GET /api/travel/places/{id}/photo`: Google gives a short-lived link, fetched without the key) and kept only in memory for 30 minutes, like the details; the browser keeps it for 30 minutes too. Google bills per photo: at most 60 a minute and 100 a day per user reach Google (cached ones don't count), and thumbnails load only when scrolled to.

**Travel reminders.** The hourly `trips.remind` job sends, once each (`trip_reminders`): the passport and visa between 27 and 30 days before a trip spent in another currency than the home one; online check-in from 24 hours before each flight's departure; and the hotel's name and address from 08:00 on check-in day. Booking times are local to where they happen and are compared with the user's own clock, so a reminder abroad can be a few hours off. Quiet hours apply as for any message.

Home's Travel card shows the trip that's on or next: a countdown or "day 3 of 9", spent against budget and the set-aside by then (`GET /api/travel/next`). Needs you gains an item when a trip that's on reaches 80% of its budget (urgent at 100%), and a settle-up item for 45 days after a trip while someone still owes for it. The API is under `/api/travel` (trips CRUD, `POST`/`DELETE /trips/{id}/expenses/{transaction_id}`). In chat the `trips` skill offers `create_trip`, `update_trip`, `delete_trip`, `add_to_trip` and `remove_from_trip` (all confirm first) and `list_trips` and `trip_status` (read only). Travel never books or buys anything.

Every new transaction gets a category, in this order: the one the user named, a matching rule, the model's (or the receipt or email reader's) best guess from the user's own categories, then Other for spending and Income for money in. Transactions logged before 0014 without a category keep none.

## Category rules

A rule files new expenses whose merchant or notes mention a word or phrase (whole words, any case). A merchant match beats a notes match, then the longest pattern wins. A category the user gives always wins, rules never touch income, and a rule always points at an existing category, since deleting a category moves its rules to the one the user picks. Each transaction records the rule that filed it, and each rule stores why it exists, so "why is this in Transport?" has an exact answer.

Rules change only when the user says so. Correcting an expense's category leaves the rules as they are and offers one ("Always file “grab” under Food?", or a change to an existing rule) that is saved only if accepted. Removing a rule archives it: expenses it filed keep their category and can still explain it. A rule never recategorises expenses already logged.

## Wallets

A wallet (`wallets`, migration 0042) is a named place money sits, kept as a label: Nexus tracks what moves in and out, not a balance. Every user has a **Spending** wallet, their main account and the one budgets watch (0042 gave existing users theirs). It can't be deleted or change kind. Others are investment, savings, card or other, with optional match words (up to 20), which the later statement and email imports will use. Names are unique per user, ignoring case.

A **move** is money between two of the user's own wallets: Spending to Investments, Savings to Spending, Savings to Investments, or Spending to a Card wallet to pay the card bill. It's a third direction in `transactions` (`move`, with `from_wallet_id`, `to_wallet_id` and an optional `received_amount` and `received_currency` when it arrived in another currency). The database requires a move to have two different wallets and no category, and in/out rows to have none. A move is never spending and never income, so budgets, spending, income, cash flow, trips, subscriptions and update-message totals leave it out. Card purchases are expenses and paying the bill is a move, so nothing is counted twice. Paying a friend ("transferred 50 to Alex for dinner") is not a move: it stays an expense with a split. Dividends and interest are income.

Three figures add moves back, in the home currency (converted as the other totals are): **put away** is moves into savings and investment wallets minus moves back out (savings to investments nets to zero); **saving rate** is put away over the month's income (none without income); **total out of Spending** is spending plus moves from Spending to every wallet except Card. They are shown with no alerts. `/api/summary` carries them as `put_away`, `saving_rate` and `total_out`; the Accounting overview shows a Put away tile once the user has a wallet besides Spending.

**Left to spend** (`GET /api/budgets/month`, shown on the Budgets card) is this month's income (received so far, plus salary still due after today) less total out of Spending so far, less what is still due this month from the cash-flow forecast: bills (including not-spending ones, today's scheduled moves), subscriptions and trip set-asides. Items with no amount or no rate are skipped and named. It sits next to **Budget left** when there is an overall budget, and the lower of the two is marked as the one to watch; the Home brief mentions it only when Left to spend is the lower. Scheduled moves are committed, not spent: they never count against a budget. The **plan check** warns when the overall budget plus monthly scheduled moves (not-spending bills, by cadence) is more than usual income: the salary baseline, or else the average of the last three complete months with income.

Deleting a wallet that has moves needs another wallet to point them at (`DELETE /api/wallets/{id}?move_to=`); moves between the two would go from a wallet to itself, so they are removed. This can't be undone. An existing entry can become a move with `POST /api/transactions/{id}/move` (money out moves from Spending to the wallet, money in the other way; the category goes, and undo brings it back). A bill split with others, or money in that paid back an IOU, is refused.

On the web, wallets are managed on a Settings card, the ledger has a Moves filter, the add sheet can log a move, and an entry's sheet offers "This was a move to…". The API is `GET`/`POST /api/wallets`, `PATCH`/`DELETE /api/wallets/{id}`, `GET /api/wallets/{id}/delete-preview?move_to=` and `POST /api/moves`. In chat the user can log a move ("moved 800 to my IBKR"), add, rename, delete and list wallets, and turn an entry into a move ("that was a move to IBKR"). An unknown wallet gets a question, never a new wallet. Nexus only records moves: "move 500 to savings" as an instruction is still refused.

**Scheduled moves** (migration 0043): a not-spending scheduled payment can point at a wallet (`bills.wallet_id`; never on a spending bill or the Spending wallet), for example a monthly IBKR top-up. Marking it done logs the move from Spending to that wallet, once per due date (external id `bill:<id>:<due>`), and not at all when a matching move is already in the ledger (same wallet, amount within 1%, within 5 days). A move confirmed after its due date is dated on that day, so it counts in the right month. Cash flow lists it as an expected move, and Left to spend and the plan check count it. In chat, "remind me to put 1,000 into IBKR every 25th" sets one up. If one hasn't shown up 3 days after its date (and up to 35 days back), Home asks "Did it go through?" with **It went through** (marks it done and logs the move) and **Skip this month** (`POST /api/bills/{id}/skip?due=`, which sets `bill_occurrences.skipped_at`). `PATCH /api/bills/{id}` links an existing not-spending payment to a wallet. Deleting a wallet repoints its scheduled payments too (cleared when the replacement is Spending).

**Recognising moves.** A wallet's match words are matched whole word or phrase, any case, like category rules; Spending never matches, the longest phrase wins and a tie matches nothing. A statement import proposes a matching row as a move in its preview (money out to the wallet, money in from it), and each one can be switched back to an ordinary entry before confirming; confirmed moves belong to the import, so undoing the import removes them. An email that matches a wallet is never logged on its own: Nexus asks "Was this a move to IBKR?" with Move / Expense (or Income) / Skip, and if that move is already in the ledger it asks "Same payment?" instead. Past entries that look like moves (they match a wallet's words, or go to the same payee for the same amount three or more months running) are listed for review on the Wallets card and by `find_likely_moves` in chat (`GET /api/wallets/likely-moves`); each one changes only when the user confirms it.

## Receipt archive

Receipt photos sent to the bot are kept in a private S3-compatible bucket. In production that's a Railway bucket, wired in with reference variables:

| Variable | Value |
|---|---|
| `STORAGE_BUCKET` | `${{<bucket>.BUCKET}}` |
| `STORAGE_ENDPOINT` | `${{<bucket>.ENDPOINT}}` |
| `STORAGE_REGION` | `${{<bucket>.REGION}}` |
| `STORAGE_ACCESS_KEY_ID` | `${{<bucket>.ACCESS_KEY_ID}}` |
| `STORAGE_SECRET_ACCESS_KEY` | `${{<bucket>.SECRET_ACCESS_KEY}}` |
| `STORAGE_PATH_STYLE` | `true` only if the bucket's Credentials tab says it uses path-style URLs |

Storage is all or nothing: a partial setup stops startup. With none, photos are still read and logged, but not kept.

- **Keys** are `receipts/<user id>/<receipt id>`, and the database checks that each key belongs to its row's user.
- **Downloads** go through `GET /api/transactions/{id}/receipt`, which checks the session's user owns the transaction, then redirects to a presigned link that expires in 5 minutes. Objects are never public.
- **Lifecycle:** a receipt is attached when its expense is confirmed. It's hidden while the expense is deleted, and comes back if the expense is restored. An hourly job erases it 30 days after the delete, and erases photos that were never confirmed after a day. The file goes first, then the row, so a failed delete is retried.

## Your data: export and delete

Under Settings → Your data, a signed-in owner or member can take all their data with them, or remove it. Guests get 403 on both, like on every route outside shared trips. The code is `channels/web/data_api.py`, `application/export.py`, `application/erasure.py` and, for both, `infra/db/user_data.py`; which table goes where is `application/user_data.py`.

**Export:** `GET /api/me/export` (no CSRF token needed, it only reads; at most 3 an hour per user, then 429) answers with a zip, `Content-Type: application/zip`, `Content-Disposition: attachment; filename="nexus-export-YYYYMMDD.zip"` (the date in the user's time zone). It holds only the user's own rows, deleted and archived ones too:

- `README.txt`, saying what is where; `ledger.csv`, the file the Ledger page's Export CSV makes (its latest 10,000 transactions; `transactions.json` has all of them).
- One JSON file per area (`AREAS` in `application/user_data.py`): `profile`, `transactions` (with splits, settlements, history, receipt details), `categories`, `category_rules`, `wallets`, `budgets`, `bills`, `subscriptions`, `imports`, `email`, `holdings` (with trades and dividends), `watchlist`, `trade_plans`, `research`, `trips`, `voice`, `memories`, `chat`, `notifications`, `costs` (what the AI models cost to serve them: counts, tokens and dollars, never text). A trip carries its bookings and plans, stops, to-dos, packing, cover and documents, costs others paid, share-link settings and its activity. Dates are ISO 8601; money is an exact string beside its currency code, never a float.
- `files.json` and `files/`: the receipt photos (the only stored files; trip documents are records, not files). If they total at most 50 MB (`FILES_LIMIT_BYTES`) they are in the zip under `files/`. Above that, `files.json` lists each with a presigned link that works for an hour (`LINK_TTL`). With no storage set up, or a file the bucket can't find, it lists the name, size and date only, with a note. This is the one thing that needs the bucket (`ReceiptStore.get`).
- Never in it: sign-in sessions, the encrypted mail grant, one-time link and invite hashes, share-link tokens (`NOT_EXPORTED`, and any column named like a token, hash, secret, password or CSRF is dropped whatever the table), other people's ids (a trip's members appear only as when they were added), and market data, news, quotes, FX rates, cached web answers and ops timings (`SHARED`: not anyone's own).

The zip is built in memory up to 8 MB and then on disk, and streamed; it is never kept.

**Delete:** `POST /api/me/delete` with `{"confirm": "DELETE"}` (exactly that; anything else is 422 and changes nothing). It needs the session's CSRF token and our origin like any write. It answers 204 and clears the session cookie.

1. In one transaction (`SqlUserData.erase`), the user's row is locked (`FOR UPDATE`, so a request still adding a row for them finishes first), then every row tied to them is deleted, children before the rows they reference, in `ERASE_ORDER`: queued jobs naming them (payload `user_id`, or their Telegram chat); the activity, members, invites, changes, links, covers, costs others paid, share link and bookings on their trips, then the trips (this removes other people's membership of their trips, and their own membership of other people's trips and the invites they used); mailboxes and the emails read from them; the ledger from the leaves in (settlements, splits, receipts, import keys, history, dismissed duplicates, transactions, rules, budgets, bills, categories, wallets); planning, notifications, memories, chat, investments, plans and research runs; sessions; the invites they made or used; the chat checkpoints of their thread (`user:<id>`, in LangGraph's `checkpoints`, `checkpoint_blobs` and `checkpoint_writes`); and the users row last. Nothing relies on a foreign key cascading. Any failure rolls back all of it.
2. After the commit, each best effort, logged, and never undoing step 1: their receipt files are deleted from the bucket; the Gmail grant is revoked and the AgentMail forwarding inbox deleted (`email.revoke_access`, the code Disconnect uses); the cookie is cleared. The keys, grants and inbox ids are read before step 1, since the rows that held them are gone after it. If some files can't be deleted a warning says how many (with the user's hash, not the id); they stay in the bucket under `receipts/<user id>/` until removed by hand, as no row points at them any more.
3. One audit line: `user data deleted (user <hash>)`, where the hash is the same keyed hash the ops events use, and the trace id is on the line like any other. No id, name, address or chat id.

What stays: shared market data and ops events (they hold a keyed hash for the user, never what they said or spent, and expire in 30 days). The deployment's owner can delete their own data too; signing in again makes a fresh account. A member who deletes needs a new invite to come back. Nothing in the chat can do either: the system prompt says it can't and points to Settings, so there is no tool to ask.

**A new table needs a decision.** `tests/unit/test_user_data_coverage.py` reads the schema and fails when a table with a `user_id`, a foreign key to `users`, or a foreign key chain to such a table (such as a trip's) isn't in `AREAS` or `NOT_EXPORTED`, or is in `SHARED`; when a table is in none of the three; when `ERASE_ORDER` doesn't cover exactly the user's tables, children first; or when a column that names a user isn't one the delete and export match on. A table that is not anyone's goes in `SHARED` with a reason; one that is goes in `AREAS` (and in the `trips` or other builder in `export.py` if it needs shaping) or `NOT_EXPORTED` with a reason, and in `ERASE_ORDER`. `tests/integration/test_your_data.py` puts a row for two users in every one of those tables and checks the export holds only the first user's and the delete leaves nothing of theirs and everything of the other's.

## Row-level security

A second safety net under the per-user queries (migration 0056). Every query in the app already filters by user; Postgres now also refuses the rest, so a query that forgets the filter, or a bug that reaches for another user's row, finds nothing instead of someone's money.

**How it works.** The app's connections log in as the database owner (Railway's `postgres`, the user that runs migrations) and immediately `SET ROLE nexus_app`, a `NOLOGIN` role that owns nothing and has only SELECT, INSERT, UPDATE and DELETE on the tables (and USAGE on the sequences), and only SELECT on `alembic_version`. The owner is not forced through the policies (`ENABLE`, never `FORCE`), so Alembic and the database shell, which don't switch role, see everything. Each user-owned table has a policy `nexus_user_rows` (`FOR ALL`, a `USING` and a `WITH CHECK`):

- With no user named for the transaction (`app.user_id` unset or empty), every row is visible and writable. That is a background job, a sign-in, an admin task.
- With a user named, only the rows tied to that user, by the same columns the data export and delete use (`user_id`, or `id` on `users`, `created_by`/`redeemed_by` on `invites`, `owner_id`/`member_id` on `trip_members`, `owner_id`/`actor_id` on `trip_activity`). Writing a row for someone else is an error (`new row violates row-level security policy`); changing or deleting theirs affects no rows.

**Who names the user.** `application/acting.py` holds the user in a context variable. The web `signed_in` dependency (so `Auth`, `TripAuth` and the ops routes) sets it once the session is checked; `AgentService` sets it for the turn (unless a web request already did) and the Telegram webhook sets it once the sender is known; `Tracing` and `handle_update` reset it when the request or update ends. `SqlUnitOfWork` reads it when a transaction begins and runs `SELECT set_config('app.user_id', :id, true)` (transaction-local, so it can never outlive the transaction or leak through the pool). Jobs and the session lookup that comes before the user is known never name one.

**A trip's other people.** A member's edit is the owner's trip being edited, so the rows keep the owner's `user_id`. `trips`, `trip_bookings`, `trip_covers` and `trip_changes` are therefore visible and writable to the owner and to the trip's members (`nexus_on_trip(trip_id)`, a `SECURITY DEFINER` function that reads `trip_members` without recursing through its policy), with the same rule for reading and writing. The owner's money on the trip (`trip_paid_by_others`, `trip_links`, `trip_shares`) is the owner's alone, like the ledger. `users`, `trip_members` and `trip_activity` can only be changed by the people they are about, but a second read-only policy `nexus_trip_mates` lets people on the same trip read them (the owner's name and zone, who else is on the trip, what they changed).

**Left without row security, and why.**

- `jobs`: queued work is written for other users by system code and names its user in a payload.
- `trip_invites`: someone signed in redeems an invite another user made, found by its token hash; the table holds hashes and no content.
- The LangGraph tables `checkpoints`, `checkpoint_writes`, `checkpoint_blobs`, `checkpoint_migrations`: keyed by chat thread (`user:<id>`), with no user column. They are granted to `nexus_app` like the rest; the checkpointer's own connection pool switches role too. The tables come from migration 0003, never from `setup()`, so the app needs no schema rights.
- Shared data (`SHARED` in `application/user_data.py`): not anyone's.

Sign-in sessions (`web_sessions`) and `invites` do have policies: the session lookup and the invite redeem run before anyone is named, so they see every row, and the policy only matters if code names a user around them.

**`DB_APP_ROLE`** (default `nexus_app`) is the role the app switches to. Empty turns it off, for a local database that is not yet at migration 0056 or that you want to query as yourself; production keeps the default. The migration creates the role if it does not exist and grants it to the migration user (`GRANT nexus_app TO CURRENT_USER`), which `SET ROLE` needs unless that user is a superuser. The migration therefore needs a user that can create roles: Railway's template `postgres` user is a superuser. `alembic upgrade head` never sets the role (`migrations/env.py` makes its own engine).

**A one-off admin query.** Connect as the login user from the database shell (see the runbook): it is not switched to `nexus_app`, so it sees every row. To see what a user's request sees, name them yourself:

```sql
BEGIN;
SET LOCAL ROLE nexus_app;
SELECT set_config('app.user_id', '<user id>', true);
SELECT count(*) FROM transactions;  -- only that user's
ROLLBACK;
```

**A new table needs a policy.** The default privileges give `nexus_app` access to every table the migration user creates, but not a policy. `tests/integration/test_row_security.py` fails until every table in `AREAS` or `NOT_EXPORTED` (except the exceptions above) has row security and a policy, and no other table has one. Add the `ENABLE ROW LEVEL SECURITY` and `CREATE POLICY` to the migration that creates the table, copying the expression for its tie from 0056.

**On deploy.** The pre-deploy `alembic upgrade head` creates the role, grants, functions and policies as the owner; the old code, which does not switch role, keeps working during the deploy. The new code switches role and starts naming users. Rolling back the code needs nothing: as the owner it is not held to the policies. Downgrading the migration drops the policies, the grants and, when no other database uses it, the role.

## Connect Gmail

Offered only when a user asks to automate logging ("can you log my expenses automatically?"). Nothing in the app suggests it otherwise.

**How it works.**
1. The bot's `connect_email` tool, or `POST /api/email/link`, makes a one-time link, valid for 10 minutes and stored as a hash. It opens in the phone's browser, because Google refuses sign-in inside in-app web views.
2. The `/connect/gmail` page names the Nexus account the mailbox will join, so nobody connects their mail through a link someone else sent. It explains Google's "unverified app" screen, then continues to Google's consent screen.
3. The callback spends the link, so a replay connects nothing. It stores the refresh token encrypted, queues a sweep and tells the user in Telegram.

**Sweeps.**
- Every 15 minutes, Nexus asks Gmail only for receipt-like emails, checking at most 25 new ones per mailbox per run.
- A cheap model screens each email, and the main model reads likely receipts into a draft. If the amount it reads can't be used, the one amount the email states with its currency ("A transaction of SGD 12.40 was made…", as on a card alert) is taken instead; with several or none, the email waits on the Email page for an amount.
- Each of the two model calls gets 25 seconds, and both run with the model's reasoning off (as does the memory writer): DeepSeek thinks by default, which made a read take 10 to 60 seconds and time out, so users saw emails that "couldn't be read". With it off a read takes 1 to 3 seconds. A run stops starting new emails after 30 seconds so it finishes inside a job's 90. An email that couldn't be read (the model was slow or failed) is tried again on the next sweeps, up to three reads in all; a read that works then asks the user as usual. Meanwhile, and after the third try, it can be logged from the Receipts by email page or the chat: with the one amount the email states, if it has one, or with the user's own.
- Each new receipt is a Telegram question with **Log it / Skip**. Bank alerts of money received ("You've received SGD 20.00 via PayNow… From: …") are read too, as money in. When the sender is someone who owes the user (names match in any case or order, and a shortened name like "Wei Ming" matches the bank's "TAN WEI MING"), the question is **Yes, paid back / Just income / Skip**, and "paid back" settles their IOUs oldest first. The first sweep instead sends one summary of the last 30 days, linking to the Email page.
- **One payment, two records.** Before asking, each receipt is checked against the ledger and the other emails still waiting: the same amount and direction within a day, by what looks like the same merchant (names share a word, "GRB" reads as Grab, and an entry with no name matches any), and not two of the same kind (two entries the user made, two statement lines, or two emails with the same subject are two payments). A match is asked as "This looks like Grab*…, already in your ledger. Same payment?" with **Same one / It's another / Skip**. Same one adds nothing: the entry takes the more readable name ("Grab Singapore" over "Grab* A-7KXP…") and the email's PDF if it had none, or, against another waiting email, that email takes the name and this one is marked a duplicate. Nothing is merged without the user's answer.
- Logged expenses use the `email` source with a dedupe key naming the mailbox and message. An email whose expense was deleted is never imported again, even after disconnecting and reconnecting.
- PDF attachments are kept in the receipt archive.
- If Google revokes access, the mailbox is marked for reconnecting and the user is told once.

**The Receipts by email page** (`/settings/email`, with an Open card on Settings under Connections, shown connected or not) lists every checked email from the last 30 days with its outcome. It can log, skip, supply a missing amount (also for an email that couldn't be read), or disconnect (which also revokes the grant with Google).

**One-time setup (owner).**
1. In [Google Cloud Console](https://console.cloud.google.com/), create a project and enable the **Gmail API**.
2. **OAuth consent screen:** choose External. Add the scope `https://www.googleapis.com/auth/gmail.readonly`. Then **Publish app** (In production).
   - Left in Testing, a connection expires after 7 days.
   - Unverified, users see Google's warning, and the app is capped at 100 users.
3. **Credentials → Create OAuth client ID → Web application.** Set the authorised redirect URI to `https://<your domain>/api/email/gmail/callback`.
4. On the service in Railway, set these variables:

| Variable | Value |
|---|---|
| `GOOGLE_CLIENT_ID` | the client ID |
| `GOOGLE_CLIENT_SECRET` | the client secret |
| `TOKEN_ENCRYPTION_KEY` | a Fernet key: `python -c "from cryptography.fernet import Fernet; print(Fernet.generate_key().decode())"`. Comma-separate several to rotate; the first encrypts. |
| `EMAIL_CLASSIFIER_MODEL` | optional: a cheap OpenRouter model for screening (needs `OPENROUTER_API_KEY`) |

Gmail settings are all or nothing, and a missing or malformed encryption key stops startup.

## Forwarding addresses (other mail providers)

For Outlook, iCloud, Yahoo, work email, or Gmail users who'd rather not sign in. Like Connect Gmail, it's offered only when a user asks to automate logging.

**How it works.**
1. The bot's `forward_email` tool makes the user's own inbox on [AgentMail](https://agentmail.to), with an unguessable address like `nexus-3f9a2c7e1b04@agentmail.to`. It's made the first time they ask; asking again gives the same address.
2. The tool gives step-by-step instructions for their provider, including a rule that forwards only emails whose subject says receipt, invoice, order, payment, transaction, paid or purchase. Forwarding a single receipt by hand works too.
3. The regular 15-minute sweep reads new mail at each address and treats it like Gmail: screened, read into a draft, and confirmed by the user. There's no 30-day look-back, because a new address starts empty.

**Setup help.**
- **Provider confirmations.** Gmail (and others) email the forwarding address to confirm it. Mail from Google, Microsoft or Apple whose subject mentions forwarding or confirming is passed on to the user in Telegram, with the code and a button for the provider's own link. Links to any other host are dropped.
- **Test my setup.** The `test_email_setup` tool asks the user to email themselves "Nexus test receipt", which passes the suggested filter. It then checks the address 1, 3 and 6 minutes later, and the user is told in chat when the test arrives.
- **Which senders to filter.** `email_status` lists which senders sent receipts and which sent other mail, for choosing what a filter keeps.
- **Quiet addresses.** If an address receives nothing for 14 days, the user is told once, until mail arrives again.

AgentMail leaves out spam and mail that fails sender authentication. Anyone who learns an address could send it mail, but nothing is logged without the user's confirmation. Disconnecting on the Receipts by email page deletes the inbox, so the address stops accepting mail.

**One-time setup (owner).**
1. Create an AgentMail account and an API key.
2. On the service in Railway, set these variables:

| Variable | Value |
|---|---|
| `AGENTMAIL_API_KEY` | the API key |
| `AGENTMAIL_DOMAIN` | optional: a custom domain set up in AgentMail; unset uses AgentMail's own |
| `TOKEN_ENCRYPTION_KEY` | as for Gmail (already set if Gmail is) |

A missing encryption key stops startup when `AGENTMAIL_API_KEY` is set.

## Observability

The app records **ops events**: what it did and how it went, never what anyone said, wrote or spent. Each is a kind, a name, whether it went well, how long it took, and details that are only counts, names, status codes and error types:

| Kind | Name | Details |
|---|---|---|
| `turn` | the channel (`telegram`, `web`) | model calls, time waiting on the model and the rest, tools used by name and count, model errors, whether the fallback answered, slow (15s and over) |
| `model` | the model id | error type, whether it was the fallback, tokens in and out |
| `tool` | the tool | `refused` when it answered "Error: ..." (the model's to fix), or the exception type when it crashed; whether it wrote |
| `job` | the job kind | attempt, error type, whether it gave up, deferred |
| `request` | the route template (`POST /api/chat`, never the path itself) | status |
| `http` | the outside host (`api.telegram.org`) | status; failed on 5xx, 401, 403, 429 and exceptions. Never the path or query, which can carry tokens |
| `log` | the logger | every warning and error: the message's template (a constant in the code, never its arguments), the exception's type (never its message), where in the code (`src/nexus/...:line`, the innermost frame in our code) and a fingerprint |
| `access` | `telegram` | a message from someone not on the allowlist |
| `agent` | the signal (`step_limit`, `empty_reply`, `unknown_tool`, `tool_error`, `undo`, `correction`) | tool names, counts, seconds and error classes only: see **Agent mistakes** below |

The user is a 10-character keyed hash (HMAC-SHA256 with `OPS_SALT`, else the webhook secret), so one person's events can be told apart without saying who. Every event in a Telegram update, web request or job carries its **trace** (`tg-<update id>`, a random id for web requests, sent back as `X-Trace-Id`, `job-<id>`), and so do the JSON log lines (`"trace"`), so a trace from the report finds the full log lines in Railway. Events are buffered and written every 5 seconds in one insert (`ops_events`, migration 0040), never blocking or failing the work; if the database is down the oldest of 20,000 are dropped. They're kept 30 days. `OPS_EVENTS=false` records none.

Logs are JSON lines with their real level: uvicorn's start and stop lines are printed once (they also went out as bare text, which Railway showed as errors), other libraries' warnings go out as JSON too, and pypdf's notices about small faults in a PDF it reads anyway are held to errors.

**The report.** `GET /api/ops/report?hours=24` (1 hour to 30 days; `&format=md` for Markdown) groups the window's events into **problems**, worst first. Each has a stable `id` (the same every time the same thing goes wrong, for opening a ticket once, updating it and closing it when it stops), a severity (high, medium, low), an area, a title, a count, first and last seen, where in the code when known, how many users it touched (by hash), up to three traces and a hint. An error logged during a failed turn, tool or job is folded into that failure, lending it its code location. What becomes a problem:

- warnings and errors by fingerprint (high for errors, medium for exceptions or 5 or more, else low)
- failed chat turns (high); replies over 30 seconds, with the share spent on the model and the tools used (medium); one reply in ten over 15 seconds (low)
- a model failing (high when a fifth or more of its calls fail), and the fallback answering a tenth or more of turns
- tools crashing (high), and a tool refusing 30% or more of 5 or more calls (the model keeps calling it wrongly)
- jobs that gave up (high) or keep failing; jobs stuck past their lease, waiting 30 minutes past their time, or a scheduled job that hasn't finished in three of its intervals (at least two hours) (high)
- routes answering 5xx (high); outside hosts failing 10% or more of 3 or more calls
- Telegram's webhook with 10 or more updates waiting, or an error delivering one in the window
- OpenRouter credit under $5 (from its key status), broken mailboxes, web search past 90% of the month's credits
- "Agent mistakes this week" (medium): 5 or more `agent` signals in the last 7 days, whatever `hours` is (see **Agent mistakes**)

The summary gives turn counts and times, model calls by model, tool, job and request counts, outside calls by host, the database's size and OpenRouter credit left. The owner can read it signed in; a script reads it with `Authorization: Bearer <OPS_TOKEN>` (unset: no token works). Anyone else gets a 404.

**Tickets.** With `OPS_GITHUB_TOKEN` and `OPS_GITHUB_REPO` (`owner/name`) set, the `ops.tickets` job runs every 6 hours (and `POST /api/ops/tickets` runs it now, for the owner or the ops token). It builds the report for the last `OPS_TICKET_HOURS` (default 72) and keeps one GitHub issue per problem at `OPS_TICKET_SEVERITY` (default `medium`) or worse, labelled `ops`, `ops:<severity>` and `area:<area>`, titled with the problem's stable topic ("[ops] Calls to api.frankfurter.app fail"). The problem's id is hidden in the issue (`<!-- ops-id: ... -->`), so each run finds its own issues:

- a new problem opens an issue: its counts, users touched, first and last seen, a link to the line of code, traces to search the logs with, a hint, and steps to fix it;
- a known one has its issue edited when anything but the window changed (edits notify nobody);
- one that comes back after its issue was closed as completed reopens it, with a comment;
- an open issue whose problem is gone from the whole window is closed, with a comment;
- an issue closed as "not planned" is left closed, however often it happens.

Issues hold only what the report holds, so they're safe in a public repository. The token needs only Issues read and write on that one repository (a fine-grained personal access token). Issue titles are stable, so a fix PR says "Fixes #N" and the issue closes on merge; if the problem recurs, the job reopens it.

**Agent mistakes.** The point is to learn every week where the agent gets things wrong from real use, without keeping or publishing anything a user said (the repository and its issues are public). Six signals are recorded as `agent` events (`application/mistakes.py` is the one place that emits them). The `detail` of each holds only the fields below; message text, amounts, names, merchants and error messages are never in an event:

| Signal | Recorded when | `detail` |
|---|---|---|
| `step_limit` | a turn used `MAX_STEPS` steps ("I stopped partway" / "too many steps") | `wrote` (did the turn change anything), `tools` (names of the real tools it called, at most 5) |
| `empty_reply` | the model sent no text and no tool call | `recovered` (did the one retry work) |
| `unknown_tool` | the model called a tool that doesn't exist or isn't offered | `tool` (the closest real tool, if any); the made-up name is never kept, since it can carry a person's name |
| `tool_error` | a tool the model called answered "Error: ..." or crashed (not tools the kernel calls itself) | `tool`, `error` (a coarse class from the exception: `InvalidInput`, `NotFound`, `Conflict`, `Forbidden`, `NothingToUndo`, `NexusError`; `Refused` when the tool returned "Error:" without one; the exception's class name for a crash), `crashed` |
| `undo` | an Undo that undid something: the button, typed "undo", the `undo_last_change` tool or the web app's | `tools` (the tool the undone change most likely came from, such as `split_bill`, `log_expense` or `add_to_itinerary`, worked out from the kind of change), `seconds` since that change, `quick` (within 2 minutes, a strong sign it was wrong) |
| `correction` | the user's message starts like a correction (`no`, `nope`, `not that`, `not what`, `I meant`, `wrong`, `that's not`, `actually`; not `now`, `nothing`, `no thanks`), checked by a small regex when the message reaches the graph | `matched`, `tools` (those the turn before used that changed something, else all of them). Not recorded when the turn before used no tool |

Alongside the user's hash and the trace, like any event. An Undo that follows a correction counts as both.

Every week's counts become one problem, **"Agent mistakes this week"** (stable id `fingerprint("agent-mistakes-week")`, area `agent`, medium), and so one ticket that the ops job keeps up to date. It only exists when the last 7 days hold at least 5 signals (`MISTAKES_MIN`), and closes itself when they hold fewer. It counts signals per kind and per tool, how many undos came within 2 minutes, and the top 5 (signal, tool) pairs, such as `undo after split_bill: 6`, `tool_error InvalidInput on change_itinerary_entry: 4` or `correction after log_expense: 3`. A signal that names several tools counts once for each. Below the pairs, **Suggested eval areas** maps each top pair's tool to the `area` of the cases in `src/nexus/evals/cases.py` (`TOOL_EVAL_AREAS` in `application/ops_report.py`: `split_bill` is `edit`, `log_expense` is `log`, and so on; a tool with no obvious area is left out until someone adds one). The ticket says again that it holds no user data, and has no traces, because there is no message to look up.

**Turning a top pair into an eval case.** There is no user text to copy, so write the case from the pattern alone:

1. Take the top pair, say `undo after split_bill`. It says people undid a `split_bill` change soon after making it, which suggests the model split a bill they didn't mean to split, or split it the wrong way.
2. Invent a request that could lead there, with made-up names, merchants and amounts, and add a `Case` to `src/nexus/evals/cases.py` in the suggested area (`edit` here). Say what a right answer is: the calls it must make (or `forbid`), whether it should ask first (`asks=True`), and the checks on the data afterwards. For a `tool_error InvalidInput on change_itinerary_entry` pair, write a request that needs that tool and check its arguments; for `correction after log_expense`, a two-turn case where the second turn fixes the first; for `step_limit`, a request that tempts a loop, with `at_most` on the tool; for `unknown_tool near X`, a request that should reach X.
3. Run it (`python -m nexus.evals --area <area>`, see [`EVALS.md`](EVALS.md)), fix the prompt, the tool's description or its arguments until it passes, and open a PR that says "Refs #N" for the ticket. Not "Fixes": the ticket closes itself once a week has fewer than 5 signals.

Never paste a real message, amount or name into a case, a PR or an issue: the signals are built so there is none to paste.

## Model costs

What the AI models cost, per user, feature and model, per day and month, for the owner. It is separate from ops events (those hold a keyed hash for the user and never what anyone spent); this one names the user, so the owner can see who costs what, and holds numbers only.

**What is recorded.** One row per UTC day, user, feature and model in `model_costs` (migration 0059): `calls`, `input_tokens`, `output_tokens` and `cost_usd` (`NUMERIC(14,6)`). Never a prompt, a reply, a transcript or a name. `user_id` is null for work done for no one in particular (the market-wide jobs, trip photos); a unique index treats all of those as one user, so they add up in one row. A row is added to (`INSERT ... ON CONFLICT DO UPDATE`), never rewritten.

- **Chat models.** Every chat model the factory builds (`infra/llm/factory.py`: the main model, fallbacks, vision, the quick no-reasoning variants for email, memory, screenshots, image look, research, trip sorting and web answers, the research reviewer) carries one `CostCallback` (`infra/llm/usage.py`). Structured output and fallbacks reuse the same model objects, so nothing at a call site changes. On OpenRouter every request also sends `"usage": {"include": true}`, merged into whatever `extra_body` that model already sent, and OpenRouter answers with `usage.cost` in US dollars. The callback reads tokens and cost from the reply (`llm_output["token_usage"]`, the message's `response_metadata` and `usage_metadata`; `cost`, else `total_cost`) and is tolerant: a reply without a cost counts the call and its tokens at $0, and a malformed number counts as 0. A call that fails costs nothing and is not counted. Gemini, DeepSeek and OpenAI models count tokens at $0 (they send no dollar figure). OpenRouter bills against your credit, so the numbers match its activity page.
- **Speech to text** (`infra/speech/openrouter.py`) records the `usage.cost` the transcription endpoint already returns, under the feature of the note.
- **Not recorded:** the eval runner (`python -m nexus.evals`) builds its own models and records nothing.

**Who and which feature** are context variables (`application/costs.py`), set where the work starts, not passed down: `chat` for a text turn (and for buttons, undo and anything else that reaches the agent), `voice`, `photo` (receipts, screenshots and images; also the trip and portfolio screenshot readers) and `pdf` in the agent service's handlers, with the actor as the user. A turn started by a voice note, photo or PDF stays under that feature. The job runner sets the feature to the job's kind (`memory.update`, `email.sweep`, `travel.photos`, `plans.refresh`, ...) and the user to the job payload's `user_id` when it has one; the sweeps that go user by user (email, budgets, bills...) narrow it to each user, and a research run's steps count under `department.step.<run kind>`. A call made anywhere else counts under `unknown`; for a web request it still gets the signed-in user.

**Never in the way of a reply.** A charge is added to an in-memory total per day, user, feature and model (a dictionary update), and `CostStore` (`infra/cost_store.py`) writes the totals every 5 seconds in its own transaction. A failed write is logged and swallowed and the totals are kept for the next flush, so a database that is down delays the numbers, never a reply. A user erased between a call and the flush loses only their own rows. The app flushes once more on shutdown, and the costs endpoint flushes its own buffer before reading. Rows older than 13 months (the current month and the twelve before it, whole) are dropped by the same loop once a day.

**The API.** `GET /api/ops/costs?days=30` (1 to 400 days; `&format=md` for Markdown). Owner signed in, or `Authorization: Bearer <OPS_TOKEN>`; anyone else gets a 404, like the ops report. It reads across users the way the report does (no user named for the transaction, so row-level security hides nothing). Money is a decimal string in US dollars. Lists run most expensive first over the `days` window; `month` is the current UTC calendar month to date whatever `days` is.

```json
{
  "currency": "USD",
  "month": {"start": "2026-10-01", "spent": "12.3456", "projected": "13.70",
            "days_elapsed": 28, "days_in_month": 31},
  "days": [{"day": "2026-10-01", "cost": "0.4123", "calls": 52}],
  "by_feature": [{"feature": "chat", "cost": "7.5000", "calls": 310, "share": 0.61}],
  "by_user": [{"user_id": "8d3f...", "name": "Ann", "cost": "6.1000", "calls": 280},
              {"user_id": null, "name": "System", "cost": "0.9000", "calls": 120}],
  "by_model": [{"model": "deepseek/deepseek-v4.1-flash", "cost": "9.0000", "calls": 700,
                "input_tokens": 2100000, "output_tokens": 180000}],
  "per_active_user_month": "3.10"
}
```

`days` has one entry per day, oldest first, zero-filled. `projected` is `spent / days_elapsed x days_in_month`, where today counts as a day. `share` is the feature's part of the window's cost (0 when nothing was spent). `name` is the user's display name, else `User <first 8 of id>`; `System` (with a null `user_id`) is work for no one in particular. `per_active_user_month` is this month's cost that belongs to users, divided by the users who used a model this month, projected to the full month the same way. Equal costs sort by calls, then by name.

**Your data.** A user's rows are in their export (`costs.json`, with `id` and day, feature, model and the counts) and deleted with them (and with the users row, `ON DELETE CASCADE`). They have row-level security like the user's other tables (see below); the system's rows (null user) are visible only when no user is named. Cost rows for an erased user are gone from the totals too.

## Evaluating the assistant

`src/nexus/evals` scores models on how well the assistant does what users mean. About 100 made-up requests (logging, clarifying questions, income, questions about money, edits, planning, categories, safety, follow-ups and memory) each start from the same seeded user: two months of invented Singapore spending, a split dinner, a budget, bills, a pay schedule, a rule and a subscription, with "now" fixed at Monday 28 September 2026, 2pm. The real agent (kernel, graph, tools and confirmations, which are approved unless a case says otherwise) handles each case, and grading checks the tool calls, confirmations, replies and the data afterwards. Cases the current assistant can't do yet name the M8 part expected to fix them.

```bash
OPENROUTER_API_KEY=... EVAL_DATABASE_URL=postgresql://nexus:nexus@localhost:5432/postgres \
  uv run python -m nexus.evals --model <openrouter model id> [--model ...] [--case q-] [--area ask]
```

It creates and drops its own database on that server, and writes a Markdown report and a JSON file per model to `eval-results/` (ignored by git): pass rate by area and by expected fix, reply time per turn, tokens and cost (from OpenRouter's public price list). The key is read from the environment and never printed. CI runs `tests/integration/test_evals.py` instead, with a scripted model: the cases are well formed, the seed's figures match what the cases expect, and grading passes and fails the right things. Real models are only called on demand. The `voice-*` cases (`--area voice`) play 13 clips from `src/nexus/evals/voice/` through the real speech model (`--stt-model`, default `STT_MODEL`) and the same path a voice note takes; the clips are synthetic, made-up phrases.

## Deploy (Railway)

The `nexus-app` service builds from the `Dockerfile`. Its settings live on the service in Railway, not in the repo (Railway no longer reads `railway.toml`):

- Pre-deploy command: `alembic upgrade head`, so migrations run before the new version starts.
- Health check: `/healthz`, timeout 60 s. Restart policy: on failure.
- Variables: `DATABASE_URL` referencing the service's own Postgres, `ENVIRONMENT=prod`, `PORT=8000`.
