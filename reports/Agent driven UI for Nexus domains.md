# Let Prime's tool calls open the panels

Nexus should treat "agent-driven app use" as a **routing problem, not a rendering problem**. The most accurate and cheapest design is to open domain panels deterministically from the domain tools Prime actually calls: if Prime runs a budget or trip tool, the matching hand-built Finance or Travel panel opens with the same parameters, filled from the same service code the tool used. Every serious production precedent works this way. In MCP Apps, the OpenAI Apps SDK, Vercel's AI SDK, LangGraph, Google's A2UI, Microsoft's Adaptive Cards and Apple's App Intents snippets, the model picks a tool or action, and code binds that choice to a pre-built UI. Fully model-generated interfaces, the one alternative, still take "a minute or more" to appear ([Google Research](https://research.google/blog/generative-ui-a-rich-custom-visual-interactive-user-experience-for-any-prompt/)). Under this design, surfacing accuracy equals tool-selection accuracy, and Nexus can measure it today. Its existing eval harness already asserts which tools each turn must call (`calls`, `used`) and must not call (`forbid`), so each case only needs expected-panel labels and set-based precision and recall scoring. The HCI evidence explains why accuracy is the success criterion: in adaptive interfaces, **accuracy affected performance more than predictability did** ([Gajos et al., CHI 2008](https://www.eecs.harvard.edu/~kgajos/papers/2008/gajos08predictability.shtml)), so a wrong panel costs more than no panel. Several domains open together because the panel set is the union of the domains Prime touched in a turn. "Can I afford the Japan trip?" therefore opens Travel and Finance without a separate classifier. The mobile path is a shared TypeScript panel registry and event protocol that a Capacitor or Expo client reuses later. The Singapore-first domain map is Finance, then Travel, Health (wellness-only) and Home & Family. It is constrained more by data access than by UI: no open-banking mandate, no public HealthHub API, the shutdown of Amadeus Self-Service, and MAS advice rules that make personalised product recommendations a legal question.

## Every major platform binds a model's tool choice to pre-built UI

The industry has converged on three layers. The first is an event transport between agent and client: AG-UI, LangGraph streaming, AI SDK message parts. The second is a UI description: either a fixed component catalogue that takes model-chosen data, or a sandboxed, developer-authored HTML iframe. The third, fully model-generated pages, exists only as an experiment. Across all of them, the decision about *which* UI appears runs through a tool or action that the model selects. The table summarises the precedents most relevant to Nexus.

| Precedent | Who decides what appears | How UI is rendered | Status (Nov 2026) |
|---|---|---|---|
| MCP Apps (SEP-1865), used by Claude and ChatGPT | Model calls a tool whose metadata points to a `ui://` resource | Host renders developer-authored HTML in a sandboxed iframe | Reported production-ready since Jan 2026 ([MCP blog](https://blog.modelcontextprotocol.io/posts/2025-11-21-mcp-apps/); [Alpic](https://alpic.ai/blog/mcp-apps-goes-official-claude-chatgpt-support)) |
| OpenAI Apps SDK | Tool call; `structuredContent` goes to model and widget, `_meta` to widget only | Iframe widget; new UI should use the MCP Apps bridge | Still labelled preview ([OpenAI](https://developers.openai.com/apps-sdk/mcp-apps-in-chatgpt)) |
| Google A2UI | Agent emits declarative JSON | Client renders natively from a trusted widget catalogue ("data, not code") | v1.0 spec; React, Flutter and SwiftUI renderers ([GitHub](https://github.com/google/A2UI)) |
| Vercel AI SDK UI | Each tool call becomes a typed `tool-<name>` part | Client maps each part to a React component | Production path; RSC `streamUI` paused ([AI SDK](https://ai-sdk.dev/docs/ai-sdk-ui/generative-user-interfaces); [RSC docs](https://v6.ai-sdk.dev/docs/reference/ai-sdk-rsc)) |
| LangGraph generative UI | Graph node calls `push_ui_message(name, props)` | Named components; same id updates in place | Stable API ([LangGraph reference](https://reference.langchain.com/python/langgraph/graph/ui)) |
| Microsoft 365 Copilot | Agent picks a plugin action | Developer-authored Adaptive Card template ([MS Learn](https://learn.microsoft.com/training/modules/copilot-declarative-agent-action-api-plugin-adaptive-cards-vsc)) | Production |
| Apple App Intents snippets (iOS 26) | System picks the intent | App's own SwiftUI view, whose buttons fire further intents ([Superwall](https://superwall.com/blog/app-intents-interactive-snippets-in-ios-26)) | Production |
| Gemini "dynamic view" | Model writes the whole page | Generated code | Experiment ([Google Research](https://research.google/blog/generative-ui-a-rich-custom-visual-interactive-user-experience-for-any-prompt/)) |

The two ways of rendering serve different owners. MCP Apps' sandboxed HTML exists so that *third-party* servers can show their own UI inside someone else's chat host. Templates are declared ahead of time, and the server only ever sees ordinary `tools/call` and `resources/read` requests ([Ruby SDK docs](https://ruby.sdk.modelcontextprotocol.io/extensions/mcp-apps/)). Google frames A2UI against this as "native-first": the agent can compose only widgets from a catalogue the client trusts, and the client keeps visual control ([The Decoder](https://the-decoder.com/googles-open-standard-lets-ai-agents-build-user-interfaces-on-the-fly/)). Nexus owns all of its UI, so the iframe model adds isolation, styling and caching costs and no benefit. MCP Apps matters to Nexus only if it later wants its domains to run inside Claude or ChatGPT.

On user outcomes, the one rigorous evaluation is Google's. Raters **strongly preferred generated UI over plain LLM text and the top search result, but ranked it below expert-designed sites**, and the study ignored generation time ([Google Research](https://research.google/blog/generative-ui-a-rich-custom-visual-interactive-user-experience-for-any-prompt/)). An academic study found task-specific generated interfaces preferred over chat replies in more than 70% of comparisons, with the largest gains in structured, information-dense domains ([arXiv 2508.19227](https://arxiv.org/abs/2508.19227v2)). Finance and travel are exactly such domains. Separately, full-page regeneration took 1 to 5 minutes per page in an accessibility study ([arXiv 2604.25455](https://arxiv.org/pdf/2604.25455)). Taken together, the evidence says *visual, structured answers beat text*, and *hand-built UI beats generated UI on both quality and latency*. Nexus gets both benefits by building good domain panels and letting Prime choose which one to show and with what parameters. No vendor has published widget engagement, wrong-UI or task-success data for ChatGPT apps, Claude apps, Copilot or Gemini, so Nexus has to produce its own accuracy numbers.

## Surfacing accuracy reduces to tool routing, which Nexus already measures

### Derive panels from tool calls; add an explicit tool only as a fallback

There are four ways to decide which panel opens. Deriving it from tool calls should be the primary mechanism, because it adds **no extra model decision, no latency and no new failure mode**. It also guarantees the panel shows the same data Prime grounded its answer on, which is the practical meaning of "the right information". The registry needs one entry per tool, saying whether the tool surfaces a panel and which `(domain, view)` its arguments map to. With that, `month_outlook(month=2026-08)` deterministically opens Finance › Month outlook for August. An incidental lookup, such as a currency conversion inside a travel answer, is marked non-surfacing, so it cannot drag the whole Finance dashboard open.

The weak spot is turns where Prime answers without calling a tool. Nexus's own eval set already contains such a case, where the next payday is answered from the context snapshot with "no tool needed" (`money-math-payday-visible` in `docs/EVALS.md`). The Berkeley Function Calling Leaderboard tracks the matching multi-turn failure as an "Empty Turn Response" ([Gorilla BFCL](https://gorilla.cs.berkeley.edu/blogs/8_berkeley_function_calling_leaderboard.html)). An explicit `show_panel(domain, view, params)` tool closes this gap and also lets the user say "open my budget". It should supplement derivation, never replace it. Anthropic reports that the most common tool-use failures are "wrong tool selection and incorrect parameters, especially when tools have similar names". It also found that adding one to five example calls per tool lifted accuracy on complex parameters from **72% to 90%** ([Anthropic Engineering](https://www.anthropic.com/engineering/advanced-tool-use)). If `show_panel` is added, it belongs in Prime's always-offered core set (`CORE_TOOLS` in `src/nexus/agent/graph.py`) with worked examples. Surfacing accuracy should not depend on a cheap model remembering to call a tool that does nothing functional.

### Keep one agent until distractor-domain evals say otherwise

Tool selection gets worse as unrelated tools pile into context. In Anthropic's internal MCP evaluations, deferring tools behind a search step raised Opus 4 from **49% to 74%** and Opus 4.5 from 79.5% to 88.1%. In one 58-tool example it also cut tool-definition context by 85%. Anthropic recommends keeping "three to five most-used tools always loaded" and deferring the rest once there are more than about 10 ([Anthropic Engineering](https://www.anthropic.com/engineering/advanced-tool-use)). RAG-MCP, a needle-in-a-haystack test, found that retrieving tools before selection **more than tripled selection accuracy (43.13% vs 13.62%)** ([arXiv 2505.03275](https://arxiv.org/abs/2505.03275v1)). LangChain's multi-agent benchmark added distractor domains to tau-bench retail. The single agent degraded sharply and used more tokens with each added domain. Swarm (handoffs) slightly beat a supervisor, whose sub-agents "translate" answers ([LangChain](https://www.langchain.com/blog/benchmarking-multi-agent-architectures); these findings come from a search excerpt because the page could not be fetched).

Prime's on-demand skills already isolate context against exactly this failure mode. Each `SKILL.md` lists its tools, and those tools are offered only while the skill is loaded. A supervisor would add a routing hop and the translation errors LangChain measured. The cost side is also clear: Anthropic's multi-agent research system used about **15x the tokens of chat**, which is worth paying only for high-value tasks ([The Decoder](https://the-decoder.com/anthropic-shares-blueprint-for-claude-research-agent-using-multiple-ai-agents-in-parallel/)). The trigger to change architecture should be empirical. Re-run the eval suite with Health and stub-domain skills bound as distractors, as LangChain did, and split into domain sub-agents only where Prime's selection accuracy breaks. If it comes to that, use the swarm pattern, in which the domain agent answers the user directly.

A pre-agent embedding router does have a role, but upstream: choosing which skills to load, and optionally pre-warming a panel skeleton. With labelled data, an embeddings classifier was **49.5% more accurate than the best LLM prompting** at 14x to 81x the speed ([Thumbtack, arXiv 2504.04277](https://arxiv.org/abs/2504.04277v1)). A hybrid that sends only uncertain cases to the LLM came within 2% of LLM accuracy at half the latency ([arXiv 2410.01627](https://arxiv.org/html/2410.01627v1)). A wrong pre-opened skeleton is visible flicker, though. Gate any pre-open at high confidence, and keep the router's training labels in the same eval cases.

### Score panels as sets, with multi-turn and silence cases

Multi-domain turns must be modelled as **multi-label** predictions (a set of panels per turn), never as a single winner. The multi-intent literature treats the problem as predicting how many intents a turn has and then which ([MIDLM, COLING 2025](https://aclanthology.org/2025.coling-main.179.pdf)), and LLMs now match specialist models on these benchmarks ([arXiv 2403.04481](https://arxiv.org/html/2403.04481v3)). The benchmarks build multi-intent examples from only four "X and Y" conjunction templates, so their scores overstate real-world ability ([BlendX, LREC-COLING 2024](https://aclanthology.org/2024.lrec-main.218.pdf)). Nexus's harder cases are *implicit* compositions such as "can I afford the Japan trip?". These need a trip lookup feeding an affordability check, so with derivation they test multi-step tool planning directly.

The eval design below extends the existing harness. Expected panels follow almost automatically from each case's expected tools through the registry, so labelling is cheap.

| Measure | What it catches | Precedent |
|---|---|---|
| Panel precision, recall, F1 (micro and macro) and exact-set match per turn | Wrong, missing or extra panels | Multi-intent SLU metrics ([arXiv 2403.04481](https://arxiv.org/html/2403.04481v3)) |
| Correct-silence rate on small-talk and general-knowledge cases | Over-surfacing | BFCL irrelevance detection ([Gorilla BFCL](https://gorilla.cs.berkeley.edu/blogs/8_berkeley_function_calling_leaderboard.html)) |
| Follow-up carry-over ("and last month?" updates the same panel key with a new period) | Lost context, flicker | BFCL multi-turn state errors |
| Distractor-domain stress run | The point where one agent breaks | LangChain, RAG-MCP |
| Proactive false-alarm rate | Unwanted unprompted panels | ProactiveBench ([arXiv 2410.12361](https://arxiv.org/pdf/2410.12361)) |
| Event order in traces: panel event at tool-call time, before final text; no close-and-reopen of a key within a turn | Late or flickering panels | AI SDK and assistant-ui loading states ([assistant-ui](https://www.assistant-ui.com/docs/guides/tool-ui)) |

The harness already runs `--repeat N` and flags flaky cases. Panel metrics should report mean and spread across rounds in the same way. Ground-truth labels need human review: Epoch AI's audit rated even BFCL v4 "Flawed" because of label noise in its irrelevance and multi-turn items ([Epoch AI](https://epoch.ai/benchmarks/berkeley-function-calling-leaderboard/review)). Use an LLM judge, built on a stronger model than Prime and calibrated on a few dozen human-labelled turns, only for the question set metrics cannot answer: was this the most useful thing to show at this moment? Online, five signals feed the offline set weekly as implicit labels: interaction rate, dismissals and time-to-dismiss (fast dismissals mark false positives), manual opens of panels Prime did not surface (false negatives), and re-asks such as "show me my budget" right after a budget answer.

### Proactive surfacing needs its own gate

Unprompted surfacing is a different and riskier problem. Horvitz's rule is to act unasked only when the expected value of acting exceeds that of inaction, after counting the cost of bothering the user ([Horvitz, CHI 1999](https://www.erichorvitz.com/chi99horvitz.pdf)). Modern LLM agents "succeed in assisting when the user needs it but fail to stay silent" when it is not needed ([ProactiveBench](https://arxiv.org/pdf/2410.12361)). Users rate proactively triggered information the least interesting, and they consider deleting apps that keep sending it ([Mehrotra & Musolesi](https://arxiv.org/pdf/1711.10171)). A cheap flash model is exactly the over-eager kind. Nexus should therefore trigger proactive panels only from deterministic signals, such as a bill due date, a flight tomorrow or a crossed budget threshold. It should show them as an ignorable chip rather than a takeover, gate them with a cost-weighted threshold in the style of PRISM ([arXiv 2602.01532](https://arxiv.org/html/2602.01532v1)), and auto-suppress any type a user keeps dismissing.

## Users forgive panels that stay put more than panels that guess

The adaptive-UI literature gives three consistent rules. First, adaptation helps only when it is accurate. Gajos and colleagues tested accuracy levels of 50% and 70%, and **accuracy had a stronger effect than predictability** on performance and on how much people used the adaptive part ([CHI 2008](https://www.eecs.harvard.edu/~kgajos/papers/2008/gajos08predictability.shtml)). Second, *add, don't move*. A "Split" interface that copied predicted items into a separate area while the originals stayed in place was significantly faster than the baseline, while moving items created "spatial instability" ([Gajos et al., AVI 2006](https://www.eecs.harvard.edu/~kgajos/papers/2006/kgajos-avi06.pdf)). Third, people prefer control. Most participants preferred user-adaptable menus to adaptive ones ([Findlater & McGrenere, CHI 2004](https://www.cs.ubc.ca/labs/edapt/papers/findlater2004.pdf)). Microsoft's HAX guidelines turn these into rules that map directly onto panels. Make undesired services easy to dismiss (G8) and correct (G9), and scope or disambiguate when uncertain (G10). Make clear why the system acted (G11), remember recent interactions (G12), and update cautiously (G14). Provide global controls (G17) and notify users of changes (G18) ([Amershi et al., CHI 2019](https://research.microsoft.com/%7Ehorvitz/Guidelines_Human_AI_Interaction.pdf)).

On desktop, those rules point to the layout ChatGPT Canvas, Claude Artifacts and Gemini Canvas converged on: a fixed chat column beside a persistent "stage" of panels. Canvas opened either on request or automatically "when needed" ([Tom's Guide](https://www.tomsguide.com/ai/chatgpt/openai-launches-chatgpt-canvas-an-ai-powered-writing-and-code-editor)). One comparison credited **version history** as the feature that made Claude's version the most pleasant to use ([BDM](https://www.blogdumoderateur.com/canvas-comparatif-ia/)). Reviewers disagree about which side of the screen holds the chat, so neither side is a standard; pick one and never move it. Each panel should follow a lifecycle: *suggested → open → pinned / dismissed → history*. Prime may replace an unpinned panel only in the same slot, and never one the user has pinned or interacted with. Each agent-opened panel carries a "why" caption that links back to the message that opened it, such as "Opened because you asked about March dining". Prime auto-expands a panel only for explicit requests. For ambiguous ones, such as "how much did I spend in Lisbon?", it opens both candidate panels with the second collapsed, or offers a chip. No study gives a validated maximum number of simultaneous panels. Working-memory estimates of roughly 3–5 chunks ([Smashing Magazine](https://smashingmagazine.com/2025/09/ux-strategies-real-time-dashboards/)) support a working budget of one expanded panel plus two or three compact ones. Nexus should test that budget with users rather than treat it as settled.

Trust design matters most in Finance and Health. Ding et al. found that citations raised trust **even when they were random**, and that trust fell once participants checked them ([AAAI 2025](https://ojs.aaai.org/index.php/AAAI/article/view/34550)). A citation badge therefore proves nothing. The defensible rule is that **the panel is the system of record**. Its figures come from deterministic service code, never from the LLM, and Prime quotes figures only from the same query the panel shows. The panel also states its query in plain words, for example "Checking, 1–31 Mar, Dining, 42 items, synced 2h ago". This extends the principle Nexus's money-math evals already enforce, that sums are done by tools rather than in the model's head. It also suits a sceptical audience: in a FINRA Foundation survey, 20% distrusted financial information attributed to AI, against 15% for a human professional ([FINRA Foundation](https://finrafoundation.org/sites/finrafoundation/files/the-machines-are-coming.pdf)). Panels that move money keep a confirm step that shows the exact consequence.

Classic navigation should stay. In an exploratory 2026 study, a chatbot cut navigation effort but gave no consistent performance gain over a dashboard, and the authors favoured hybrids ([arXiv 2605.31224](https://arxiv.org/pdf/2605.31224)). Apple's HIG asks for "a great experience even when generative features aren't available or people opt not to use them" ([Apple HIG](https://developer.apple.com/design/human-interface-guidelines/generative-ai.md)). The Money, Invest and Travel tabs should remain the stable map of the product. Agent-opened panels should be *the same components* as the tab views, deep-linked with filters applied, so that what Prime shows teaches users where things live. An "Open in Money" action and an "Ask Prime about this" action let users move between the two modes. Tracking tab-initiated against chat-initiated panel opens would also answer an open research question: whether users of agent-first products abandon classic navigation over time.

## A typed panel registry and three SSE events fit the current stack

The architecture needs four small pieces, none of them a rewrite. The first is a **panel registry**, the single source of truth. Each `kind`, such as `finance.month_outlook`, `finance.transactions` or `travel.itinerary`, has a Pydantic params schema and a mapping from the tools that surface it. Three things are generated from it: the tool-to-panel map, the backend validator, and TypeScript types for the React client. This is the transferable lesson from Airbnb's Ghost Platform, whose independent, reusable typed "sections" are placed by "screens" and wired up by typed "actions" ([Airbnb Engineering](https://medium.com/airbnb-engineering/a-deep-dive-into-airbnbs-server-driven-ui-system-842244c5f5)). The same lesson appears at DoorDash, whose server component ids map into a client component library ([DoorDash](https://careers.doordash.com/?p=5364)). Nexus should not build a full server-driven UI layout language. Its panels are coarse, hand-written domain components, and the client owns the layout.

The second piece is a **UI event in the existing stream**. `src/nexus/channels/web/chat_stream.py` already sends `step`, `replies` and `error` frames. Add `panel.upsert` (`panel_id`, `kind`, `params`, `as_of`, an optional `summary` of the figures Prime quoted, and `message_id`) and `panel.close`. Copy proven semantics rather than invent new ones: stable-id upsert as in LangGraph and the AI SDK, where pushing the same id updates in place ([AI SDK](https://ai-sdk.dev/docs/ai-sdk-ui/streaming-data)), and JSON Patch for state deltas as in AG-UI's `STATE_DELTA` ([AG-UI events](https://docs.ag-ui.com/sdk/python/core/events.md)). Emit the event when the tool call is made, not when the reply arrives, so the panel's skeleton appears before the text answer. Adopting AG-UI wholesale is a later option. It is the most complete open protocol, with a first-party LangGraph integration and roughly 17k GitHub stars ([AG-UI repo](https://github.com/ag-ui-protocol/ag-ui)), and TanStack AI already speaks it ([TanStack AI](https://tanstack.com/ai/latest/docs/protocol/chunk-definitions)). It would replace the current wire format, though, and its versions have churned. LangGraph's `push_ui_message` is useful for persisting open-panel state in the Postgres checkpoint so that reloading a thread restores its panels, but its React helpers assume the LangGraph Platform API, which Nexus does not use ([LangChain docs](https://docs.langchain.com/langsmith/generative-ui-react)).

The third piece is a **hybrid data path**. Panels fetch their own data through the existing TanStack Query endpoints, keyed by the event's params, and those endpoints call the same service functions as the agent's tools. Panels stay live, paginate and refresh, and they open identically from a tab. The inline `summary` seeds the query cache (`initialData`) for an instant first render. If the server's version is newer than `as_of`, the panel shows an "updated since" hint instead of silently contradicting the chat. No production source documents this exact hybrid; it is an inference that combines server-driven-UI and AI SDK practice.

The fourth piece is a **channel back to the agent**. Each chat request carries the list of open panels (ids, kinds, params, current selection), so Prime can resolve "drop that hotel" or "that category". Deterministic panel buttons call REST directly. Actions that need reasoning post a typed message into the thread. Money-moving actions stay as LangGraph interrupts, so the checkpointer holds the pending state, which matches Nexus's existing confirmation flow.

### Desktop to mobile: share the core, then choose Capacitor or Expo

The Telegram Mini App is already the mobile web client, and it has constraints. Telegram renders the app inside its own native bottom sheet, `viewportStableHeight` is the height to pin bottom UI to, and `expand()` or fullscreen gives panel-heavy views room ([Telegram Mini Apps docs](https://docs.telegram-mini-apps.com/platform/viewport)). On phones the pattern becomes chat as the base layer with the composer in the thumb zone, and the domain panel as a nonmodal sheet at peek height that turns modal when expanded. Sheets should never be stacked ([NN/g](https://www.nngroup.com/articles/bottom-sheet/)), and nested modals inside a sheet are "inaccessible and disorienting" ([eBay Playbook](https://playbook.ebay.com/design-system/components/bottom-sheet)). Several domains become swipeable cards inside one sheet, and the sheet collapses to a chip while the keyboard is up. Inside Telegram, avoid a custom sheet that fights Telegram's own drag-to-dismiss gesture.

| Path | Reuse | Main risk |
|---|---|---|
| PWA on the current app | ~100% | iOS push only after a Home Screen install ([MagicBell](https://www.magicbell.com/blog/pwa-ios-limitations-safari-support-complete-guide)) |
| Capacitor wrap | ~90%+ | Rejection under App Store Guideline 4.2 as a repackaged website unless it adds native depth ([Apple forums](https://developer.apple.com/forums/thread/812889)) |
| Expo / React Native | Types, API client, TanStack Query hooks, SSE logic; UI rewritten, with Expo DOM components reusing charts ([Expo](https://docs.expo.dev/guides/dom-components/)) | New UI layer to build |
| One shared UI (react-native-web, Tamagui, Solito) | Highest long-term | Rewrites the working web UI now |

The step to take today is portability. Move the panel registry types, SSE event parsing, the generated API client and the TanStack Query hooks into a DOM-free TypeScript package. Either mobile client then reuses it, and the desktop app loses nothing. Once old native binaries exist in the wild, the one hard server-driven-UI lesson applies: the client must declare the panel `kind@version` values it supports, param changes must be additive only, and the server must fall back to text or a generic table for unknown kinds. Choose Capacitor if speed to the store matters, and give it native push for proactive messages, biometric unlock, an offline read cache and the share sheet. Choose Expo if a native-feeling chat-and-sheet experience is the goal. Either way, Apple's **Guideline 5.1.2(i)** (13 November 2025) requires apps to "clearly disclose where personal data will be shared with third parties, including with third-party AI, and obtain explicit permission" ([Apple Developer News](https://developer.apple.com/news?id=ey6d8onl)). Nexus sends finance data to an LLM provider, so it should build an in-app consent screen that names the provider into web onboarding now.

## Finance anchors the map; data access, not UI, limits every domain

Demand data supports the order of the domain map. In a US poll, 32% use AI for personal organisation, 32% for health and fitness advice and 20% for trip planning ([Verasight](https://data.verasight.io/ai/at-home-people-mostly-use-ai-for-writing-and-recommendations)). In a separate survey, 34% use it to help manage childcare ([Menlo Ventures](https://www.menlovc.com/perspective/2025-the-state-of-consumer-ai/)). Only **14% of light users are comfortable using AI for financial tasks** ([PYMNTS](https://www.pymnts.com/?p=3324656)), so Finance is high-value but low-trust. Revolut shows the money-core-into-travel expansion in a shipped product: Stays, eSIMs, lounges, and RevPoints redeemable for travel ([Revolut](https://revolut.com/en-NO/travel)). Singapore-specific consumer usage data was not found; every figure above is US or global.

| **Home & Family** | Family calendar, childcare, groceries, home, vehicles, documents | User input plus calendar and email | Demand signals are strong (childcare 34%; Fambot launched Sep 2026 ([TechCrunch](https://techcrunch.com/2026/09/01/fambot-introduces-an-ai-chief-of-staff-for-families/))). Few regulatory constraints |
| **Agenda** (shared infrastructure, not a domain) | Calendar, email, tasks feeding every domain | Existing email reading | Gmail restricted-scope verification was not researched **[open]** |

Two cross-cutting constraints shape the panels themselves. First, salary, loan, credit and insurance data, and specified medical information, put Nexus in PDPA's **"presumed significant harm"** class: a qualifying breach must be notified to the PDPC within 72 hours ([PDPC guide](https://www.pdpc.gov.sg/-/media/Files/PDPC/PDF-Files/Other-Guides/Guide-on-Managing-and-Notifying-Data-Breaches-under-the-PDPA-15-Mar-2021.pdf)). Encryption, access logging and a breach runbook are therefore prerequisites, not polish. Second, consent should be scoped per domain, so that a multi-domain panel never pulls health data into a finance view without the user opting in. The Finance boundary also lives in the panels. Showing users their own data, factual prices with source and delay noted, and calculators driven by their inputs is low-risk. Personalised "buy X" or "switch to insurer Y" content is likely regulated advice, and one vendor notes that a disclaimer does not turn personalised advice into general information ([Arnifi](https://arnifi.com/blog/?p=28469)). The existing trade-plans feature should read as the user's own journal. Health has the same "every feature" trap: under Australia's wellness exclusion, one diagnostic feature fails the whole product ([TGA](https://www.tga.gov.au/resources/guidance/understanding-general-health-or-wellness-software-exclusion)). Health panels should show trends and goals, never interpretations such as "your HRV suggests…".

The most valuable multi-domain panels sit where the ledger meets another domain's events. These are a **trip budget** (planned against actual spend in SGD, card used, points earned), a timeline of **upcoming obligations** that merges bills, renewals, flights, appointments and passport expiry, and **health spending**. Each domain should expose typed entities (Transaction, Trip, Booking, Appointment, Metric) with shared keys such as date range, place, merchant and person. Prime can then compose a multi-domain view from the domains it touched, and the registry stays the only place a panel is defined. Some gaps remain open. SGFinDex access for non-bank apps in 2025–2026, SGX market-data licensing, broker APIs and the exact text of HSA GL-04 R3 were not confirmed. Each needs a check with a primary source or a Singapore lawyer before Nexus relies on it.

## Conclusion

The core finding changes what "agent-driven UI" means for Nexus. The quality of the experience lives in **the reliability of the turn-to-tool mapping**, not in a generative rendering layer, and that mapping is already instrumented. The highest-leverage next step is therefore not a UI framework. It is three additions to the existing eval cases: expected panels, correct-silence cases and implicit multi-domain cases. Together they give Nexus a panel F1 baseline on its flash model before any panel code ships, and the same suite run with distractor domains will show when Health's arrival forces a move to sub-agents. No public vendor data exists on wrong-panel or dismissal rates, so these numbers will be Nexus's own competitive knowledge.

The second implication is that domain expansion will be limited by data rails and regulation sooner than by interface work. Singapore offers no open-banking mandate, no public health API and, since July 2026, no self-service travel API. The defensible design is therefore one where Nexus owns the ledger: user-imported data, deterministic service-layer figures, and panels that act as the system of record. That same design is what keeps Prime's answers honest and its advice on the right side of the FAA. The advantage that compounds is a trustworthy cross-domain ledger that Prime can open at the right moment, not breadth of domains.
